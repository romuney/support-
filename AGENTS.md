# AGENTS.md — область Support

Контекст локальной папки `Support`. `CLAUDE.md` и `NESSY.md` рядом — симлинки на этот
файл. Правь только `AGENTS.md`.

## Что здесь

Две независимые системы разведены по папкам. Общее у них — только канал
`~hr-report-ask` и файлы в корне; кода они друг у друга не берут.

| Папка | Что | Как запускать |
|---|---|---|
| `bot/` | Бот поддержки: ядро, адаптеры, инструмент DD, промпты | `cd bot && python3 build_time_flows.py` |
| `telemetry/` | Сборщик данных: лог событий канала, метрики процесса | `cd telemetry && python3 build_telemetry_flows.py` |
| `executive-support/` | База знаний HR-домена, git + GitLab. Свой `CLAUDE.md` со своими правилами — читать перед любой правкой внутри | — |

**Пути в скриптах относительны рабочего каталога**, поэтому сборщики и тесты
запускаются **из своей папки**, а не из корня. Из корня они упадут на
отсутствии `Support Bot DD.json`. Обращения к общим файлам идут через `../`:
реестр `../executive-support/kb/index.md` в тестах бота, выгрузка канала
`../hr-report-ask-3-4-aug-2026.md` в тестах телеметрии.

## Флоу бота: git + DD в один контекст

Ключевая идея — **инвентарь из DD, смысл из git**, они не пересекаются:

| Что | Источник |
|---|---|
| Имена полей, типы, описания полей, DDL | DD, онлайн |
| Гранулярность, ключи, правила джойна, тип среза, запреты, формулы метрик | `kb/` в git |

Список полей в git не дублируется: он устаревает молча, и агент начинает уверенно
врать. Не хватает описания поля — просим владельца дописать **в DD**, а не заводим
своё. Правило целиком — `executive-support/kb/process/metadata-sources.md`.

### Как устроено в n8n: два воркфлоу

**Ниже — первая конструкция, tool-loop.** Она провалилась по токенам (242 618 на
один вопрос) и заменена конвейером: актуальная схема бота — в разделе
«Подключение к Time». Раздел оставлен потому, что `Support Bot DD.json` ещё
живёт отдельным флоу и служит источником узлов для сборщика ядра, а решения
по самому `DD Lookup` действуют без изменений — он вызывается и из конвейера.

```
Support Bot DD.json  (старое, tool-loop)
chat trigger → Get a file (kb/index.md) → decode base64 → AI Agent
                                                            ├── T-Bank LLM proxy
                                                            ├── read_kb_article   (GitLab)
                                                            ├── list_kb_folder    (GitLab)
                                                            └── dd_lookup         (toolWorkflow → DD Lookup по id)

DD Lookup.json   ← схема ниже устарела; актуальная — в «DD Lookup сегодня»
When called by agent (urn, search) → Route by object type
   ├─ :table: → dd_entity_card → dd_columns → Pick columns → Need column cards ─┬─ да  → dd_column_cards ─┬→ Shape table meta
   │                                                                            └─ нет ─────────────────────┘
   └─ иначе   → dd_report_card → Shape report meta
```

**Схема выше — первой версии `DD Lookup`.** С тех пор `entityFields` перестал
отдавать `summary` и `attributes`, из-за чего `dd_column_cards` разделился
на два узла, у таблицы появился отдельный запрос атрибутов, у отчёта —
витрины-источники. Актуальная схема:

```
DD Lookup.json  (сегодня)
When called by agent (urn, search) → Route by object type
   ├─ :table: → dd_entity_card → dd_entity_attrs → dd_columns → Pick columns
   │            → Need column cards ─нет──────────────────────────────────┐
   │                              └─да→ dd_column_summary → dd_column_attrs
   │                                                      → Shape table meta
   └─ иначе   → dd_report_markdown → dd_report_attrs → dd_report_links
                → dd_report_sources → Shape report meta
```

**Значений полей здесь БОЛЬШЕ НЕТ, и вход `values` тоже убран** — проверка
переехала за автора, см. «Проверка значений стоит после автора». Каталог
снова отвечает ровно на один вопрос: что за поля есть у объекта.

Ветвление здесь по-прежнему запрещено: три входа у `Shape table meta` —
это сходящиеся ветви IF плюс ветка значений, они взаимоисключающие.

`dd_columns` даёт только имена полей, поэтому за описаниями идёт второй запрос —
`dd_column_cards`, по карточке каждой отобранной колонки. `Pick columns` выбирает
цели по фильтру и режет их до 12; при пустом `search` карточки не запрашиваются
вовсе, и `Need column cards` уводит поток сразу в шейпер.

Реестр `kb/index.md` целиком вклеен в системный промпт, и в нём есть колонка
`dd_urn`. Агент по строке реестра получает сразу и путь к статье, и ключ объекта
в DD; по нескольким строкам собирается контекст на несколько таблиц.

**Порядок импорта важен.** `dd_lookup` ссылается на `DD Lookup` по статическому id,
которого до первого импорта не существует:

1. Импортировать `DD Lookup.json`, скопировать id из адресной строки n8n.
2. `DD_SUBFLOW_ID=<id> python3 build_dd_flow.py && python3 patch_prompt.py`
3. Импортировать `Support Bot DD.json`.

Без шага 2 в инструменте остаётся плейсхолдер и вызов падает на «workflow not
found». Это осознанно громкая ошибка: тихо неверная работа хуже.

Шаги 1–2 уже выполнены: id `DD Lookup` — `7tgrNcbmZGuW2AON`, он записан
значением по умолчанию в `build_dd_flow.py`, и пересборка больше не требует
переменной окружения. Заново они нужны только если воркфлоу пересоздали.

Решения, которые важно не потерять при доработке:

- **Ветка DD — отдельный воркфлоу, а не self-call.** `={{ $workflow.id }}`
  в `toolWorkflow` давал `Missing node to start execution`: инструмент
  завершался за 42 мс, ни один запрос в DD не уходил, а агент отвечал по текстам
  статей, будучи уверен, что видел инвентарь. Ошибка тихая и потому дорогая.
- **Один инструмент `dd_lookup`, а не три.** Роутинг внутри `DD Lookup` по
  подстроке `:table:` в URN. Агенту меньше поводов промахнуться, шейпинг —
  в одном месте.
- **Два шага вместо обязательного `search`.** Пустой `search` отдаёт список имён
  полей: 211 имён через запятую — 3.1 КБ, дешевле, чем кажется. Обратный порядок
  (сразу требовать фильтр) создавал курицу-яйцо: агент угадывал имя поля, чтобы
  узнать имена полей, и в первом прогоне сделал пять вызовов с выдуманными
  `search` подряд.
  **В конвейере это правило не воспроизводится:** двухшаговость держалась на
  итерациях агента, которых там нет. Вызов один, а от угадывания защищает
  следующий пункт — промах фильтра возвращает инвентарь.
- **Промах фильтра возвращает инвентарь.** Не «0 полей», а «такого поля нет, вот
  полный список» — иначе агент идёт на второй круг угадывания.
- **Шейпинг обязателен.** Сырой JSON DD по 267 колонкам — сотни КБ в контекст.
  Лимит 60 строк действует только на режим с фильтром, и при обрезании пишется,
  **сколько полей скрыто** — молча резать нельзя.
- **`neverError` + `fullResponse`.** 401 и 404 превращаются в текст для агента
  («истёк Service Account», «неверный URN»), а не в падение инструмента.
- **`followRedirects: false`** на всех трёх HTTP-нодах.

### Форма ответа `/related/columns` — подтверждена живым запросом

Проверено 2026-08-06 на `mdm_employee_structure_d`, `limit=500`:

```json
{ "totalCount": 267,
  "data": [ { "relationId": "…",
              "entity": { "id": "…", "urn": "urn:dd:…:column:emart.…business_dt",
                          "system": "tables.greenplum", "type": "COLUMN",
                          "fqn": "emart.mdm_employee_structure_d.business_dt" } } ] }
```

Два следствия, оба ломали первую версию шейпера:

1. **Сущность вложена в `entity`**, на верхнем уровне лежит связь. `unwrap()`
   доставал элементы, но `fqn` искался на верхнем уровне и не находился —
   инвентарь получался **пустым**, и агент читал это как «полей нет». Распаковку
   делает `nodesOf()`, тесты 0 и 0б в `test_shapers.mjs` держат этот кейс.
2. **`summary` и `attributes` эндпоинт не отдаёт вообще**, хотя `entityFields`
   передан — параметр здесь игнорируется. Описания и типы живут на карточке
   каждой колонки, отсюда и второй запрос `dd_column_cards`.
   `entityFields` в запросе оставлен на случай, если поведение починят.

`totalCount` шейпер сравнивает с числом полученных полей: расходятся — пишет
«получено N из M, список НЕПОЛНЫЙ». `limit` поднят с 300 до 500, потому что при
267 колонках запас был всего 33.

### Форма карточки колонки — подтверждена живым запросом

`GET /entity/{column_urn}?entityFields=displayName&entityFields=summary&entityFields=attributes`
(проверено 2026-08-06 на `business_dt`) отдаёт то, чего нет в списке колонок:

```json
{ "fqn": "emart.mdm_employee_structure_d.business_dt",
  "summary": { "data": "Дата среза" },
  "attributes": {
    "column_type":      { "type": "text",      "data": "date" },
    "keys":             { "type": "text-list", "data": ["PK"] },
    "comment":          { "type": "text",      "data": "business_dt генерируется от даты найма…" },
    "versioning_type":  { "type": "text",      "data": "BSN" },
    "ordinal_position": { "type": "number",    "data": 1 } } }
```

Три вещи, которые здесь легко сделать неправильно:

1. **Значение атрибута лежит в `.data`**, сам атрибут — обёртка `{type, data}`.
   Без распаковки (`attrData()`) тип поля выводился как строка `[object Object]`
   и уходил агенту в таком виде.
2. **Тип данных — только `column_type`.** Свободный поиск ключа по `/type/i`
   первым находил `versioning_type` и выдавал `BSN` за тип данных. Пустой тип
   честнее неверного, поэтому ключи перечислены явно.
3. **`comment` важнее `summary`.** `summary` — это «Дата среза», а в `comment`
   лежит то, из-за чего считают неверно: границы генерации `business_dt`,
   развёртка витрины с 01.01.2021, поведение по уволенным. Шейпер печатает оба.

Цена: один запрос на колонку. Здесь стоял потолок `MAX_CARDS = 12`,
и **2026-08-31 он снят** — см. «Разбор 2026-08-31»: он резал дешёвый путь
(фильтр по имени и так узкий) при том, что дорогой — чтение карточек ВСЕХ
колонок в `by_meaning` — и так шёл без потолка. Остался один предохранитель,
от вырожденного фильтра вроде «e»: совпало больше половины таблицы — карточки
не запрашиваются вовсе, а шейпер печатает инвентарь и говорит, что фильтр
слишком широк. Выражен долей, а не числом полей, потому что вырожденность —
это про долю.

**Поиск по смыслу (`by_meaning`) читает карточки ВСЕХ колонок таблицы, без
потолка.** Раньше здесь стоял `ALL_CARDS_CAP = 60` — сначала как «потолок
стоимости одного вызова», не как порог включения поиска. Живой прогон на
`mdm_employee_structure_d` (289 колонок, hint «декретницы») показал, что
потолок на широкой таблице ломает саму идею: проверялись первые 60 полей
из 289, искомое было среди непроверенных, и ответ «не встретилось» читался
как «такого поля нет», хотя до него просто не долистали — тихий отказ под
видом ответа. Тогда `MAX_CARDS = 12` в режиме `by_name` не тронули: казалось,
что там фильтр уже нашёл совпадения и режется только их количество. Через
пять дней выяснилось, что это неверно, — см. «Разбор 2026-08-31»: описания
не пришли по части найденных полей, и в ТЗ это превратилось в «состав полей
неполный». Потолок снят.
Тест 8г в `test_shapers.mjs` держит инвариант: на таблице шире старого
потолка проверяются все поля, а не первые N.

**И полный список имён полей печатается ТЕПЕРЬ ВСЕГДА**, а не только когда
фильтр промахнулся. Он у шейпера на руках в любом режиме (`rows` строится
из `dd_columns`), стоит ноль запросов и ~3 КБ — а без него автору нечем
проверить, есть ли в витрине поле, которого нет в блоке совпадений. Ровно
на этом 2026-08-31 бот объявил «состав полей неполный, нужен полный
инвентарь», имея 53 совпадения из 289 полей.

Формулировка тоже важна: агент не должен писать «владелец не заполнил описания»,
когда описание не удалось получить — оно может быть заполнено. Правильная
формулировка — «описание поля получить не удалось». Отдельное правило в промпте.

Правки вносятся в `build_dd_flow.py` / `patch_prompt.py` и пересобираются;
JSON руками не правим. После правки Code-нод — `node test_shapers.mjs`.

### `entityFields` на `/entity/{urn}` перестал отдавать summary/attributes — не только у REPORT

2026-08-13 это уже было найдено на отчётах: `GET /entity/{report_urn}?entityFields=…`
отдавал только `id/urn/system/type/fqn`, без `displayName/summary/attributes`,
и починили отдельными запросами к суб-ресурсам (`/markdown`, `/attribute`, `/link`).
Тогда это выглядело как особенность REPORT.

Живой прогон 2026-08-24 показал, что это не особенность типа сущности, а общее
поведение эндпоинта. `GET /entity/{column_urn}?entityFields=displayName&entityFields=summary&entityFields=attributes`
на `business_dt` — **той же колонке**, что 2026-08-06 отдала `summary.data:
"Дата среза"` и полный `attributes` (см. пример выше) — 2026-08-24 отдал только
`id/urn/system/type/fqn`, `content-length: 222` вместо прежних сотен байт
с описанием. Тот же запрос, тот же узел, другой ответ: поведение DD изменилось
между двумя датами, а не наш HTTP-узел сломался.

Раз баг общий, а не специфичный для отчётов, лечится он тем же приёмом
и на карточке колонки, и на карточке таблицы:

- **`dd_entity_card`** теперь бьёт прямо в `/entity/{urn}/summary`. Раньше читал
  `card.displayName`/`card.fqn` для ярлыка объекта — но ни то, ни другое эти
  entityFields больше не отдают, а ярлык и так дублирует `urn` строкой ниже.
  Шейпер печатает `urn` напрямую, `card.displayName`/`card.fqn` в коде больше нет.
- **`dd_column_cards` разделён на `dd_column_summary` + `dd_column_attrs`**,
  цепочкой (сначала summary, потом attrs — не параллельно: у `Shape table meta`
  уже есть входящее соединение с false-ветки `Need column cards`, и параллельный
  вход с обоих новых узлов запустил бы шейпер дважды на одну и ту же порцию
  колонок, n8n не ждёт вторую ветку сам, как это делает Merge). Имени поля
  ни один из двух ответов не несёт — оно берётся из `Pick columns` по индексу:
  оба запроса идут по одному и тому же списку targets, порядок не расходится.
  **Цена поиска по смыслу удвоилась** (один запрос на колонку стал двумя), но
  это разовая цена по запросу пользователя, а не на каждое сообщение в канале.
- **У таблицы, как и у колонки, есть `comment` — отдельно от `summary`.**
  Добавлен четвёртый узел, `dd_entity_attrs` (`GET /entity/{urn}/attribute`),
  цепочкой после `dd_entity_card` и перед `dd_columns` (порядок исполнения,
  данные между ними не зависят друг от друга). В интерфейсе DD это поле
  подписано «Комментарий» — то же самое, что `comment` в атрибутах колонки:
  summary это короткая подпись, а comment часто несёт правило или ограничение,
  из-за которого данные считают неверно. Печатается как `КОММЕНТАРИЙ ИЗ DD`,
  только если отличается от `summary` — совпадающий текст под двумя
  заголовками читался бы как повтор. Тест 00в в `test_shapers.mjs`.

Ключевой урок: живой прогон, подтверждённый в одну дату, не остаётся верным
навсегда — внешний сервис меняется независимо от правок кода. `AGENTS.md`
фиксирует дату проверки не для истории, а как срок годности решения; когда
живой прогон расходится с зафиксированным, доверять зафиксированному нельзя.

**Id записываются в сборщик, а не живут только в переменной окружения.** Пока
они существовали лишь как `DD_SUBFLOW_ID` и `CORE_WORKFLOW_ID`, каждая

существующего (Import from File в уже открытом ядре) id сохраняет — адаптеры
пересобирать не нужно. Импорт ядра **новым** воркфлоу даёт другой id, и тогда
`CORE_WORKFLOW_ID=<новый> python3 build_time_flows.py` плюс переимпорт
адаптеров. По виду флоу разница незаметна: адаптеры продолжат звать старое
ядро, и оно продолжит отвечать — просто без новых полей.

**Ядро и адаптеры переимпортируются вместе.** Входы ядра
(`executeWorkflowTrigger`) — часть контракта: n8n не падает на поле, которого
ядро не объявляет, оно просто не доедет. Залить новый адаптер к старому ядру
значит получить пустые поля формы, неработающее понижение уверенности и по виду
флоу — «всё в порядке». Тест в группе 16 `test_adapters.mjs` держит совпадение
списков на диске, но что залито в n8n, он знать не может.

`patch_prompt.py` из цепочки **выпал**: он правит промпт узла `AI Agent`
в `Support Bot DD.json`, то есть старой конструкции tool-loop, и в ядро этот
промпт не попадает. Промпт бота живёт в `prompts/router.md` и
`prompts/author.md`. Скрипт оставлен, пока жив сам `Support Bot DD.json`,
и предупреждает об этом на каждом прогоне.

### Почему конвейер, а не один агент с инструментами

Живой прогон из лички 2026-08-08 упал на лимите LLM-прокси: **242 618 токенов
на один вопрос**, `quota tpm limit exceeded`. Дело не в жадности агента,
а в устройстве tool-loop: на каждой итерации модель получает заново весь
системный промпт (15,4 КБ), схемы трёх инструментов (3,3 КБ), реестр (8 КБ)
и **всю накопленную историю вызовов**. Рост квадратичный. Только фиксированная
часть — 8 135 токенов на итерацию, при `maxIterations: 6` это 48 811 токенов
ещё до тел статей.

`maxIterations` резал не расход, а **глубину сбора**: лимит упирался раньше,
чем прочитаны мастера домена, и бот начинал систематически отвечать «средняя
уверенность» на вопросы, на которые база отвечает точно. Тихий отказ — ровно
то, от чего защищена вся остальная конструкция.

Стало (посчитано по собранному флоу на 2026-08-27): роутер 2 669 + проекция
реестра 3 532, автор 7 639 + материалы ≈ 10 000, в режиме выгрузки ещё
4 503 за блок правил. **≈ 24 000 токенов на обычный вопрос и ≈ 28 000
на выгрузку**, два вызова модели вместо шести-тринадцати.

Пересчёт на 2026-08-31: промпт автора +12 %, блок выгрузки +19 %, роутер
+15 %, статей в материалах до 12 вместо 8, плюс ~3 КБ имён к каждому
инвентарю. Стало **≈ 26 000 и ≈ 32 000** — при контекстном окне ~1 000 000
это запас тридцатикратный, и снятые лимиты его не расходуют сколько-нибудь
заметно. Ограничение здесь не контекст, а TPM аккаунта (~240 000 в минуту),
и оно про частоту обращений, а не про размер одного. Размер материалов при этом **измеряется** (`materials_len`
в телеметрии): не потому, что близко к пределу, а потому что до сих пор
его не знал никто, и все потолки ставились на глаз.

Первый замер (14 600) устарел: с тех пор промпт автора вырос вдвое, реестр
на треть. Рост объяснимый — каждая правка закрывала свой тихий отказ, —
но он линейный и разовый на вопрос, а не квадратичный по итерациям, и это
и есть то, ради чего конвейер строился.

**ОРИЕНТИР «40 000» БЫЛ ПРИДУМАННЫМ ЧИСЛОМ.** Здесь стояло «перевалит
за 40 000 — резать промпт автора», и это не был ни лимит прокси, ни лимит
контекста: осторожность, записанная как факт, и читавшаяся как факт.

Класс ошибки тот же, что у `MAX_CARDS`, `MAX_ARTICLES` и `MAX_PAIRS`, снятых
2026-08-31: **придуманное число, которое выглядит ограничением и мешает как
ограничение.** Разница лишь в том, что те резали материалы молча, а это
удерживало от правок, которые надо было сделать раньше.

**ЛИМИТА ДВА, И ОНИ ПРО РАЗНОЕ — путать их дорого.** Карточка модели
`tgpt/text.instant.sota` (см. раздел про модель ниже) даёт первый, живой
прогон 2026-08-08 — второй:

| | что это | сколько | чем упирается |
|---|---|---|---|
| Контекстное окно | сколько влезает в ОДИН запрос | **~1 000 000** | длина промпта плюс материалы |
| TPM аккаунта | сколько токенов прокси пропустит ЗА МИНУТУ | **~240 000** | суммой по всем запросам минуты |

При ≈ 26 000 на обычный вопрос и ≈ 32 000 на выгрузку до контекстного окна
**тридцатикратный** запас — по нему резать не придётся никогда, и вопрос
«что вынести из промпта автора» решается не расходом, а тем, помогают
правила или мешают: лишнее правило портит ответ задолго до того, как
упрётся в токены.

А вот **TPM — предел не вопроса, а МИНУТЫ**, и вот он ближе, чем кажется.
Один вопрос это два вызова модели (роутер и автор), в режиме проверки
значений три, с доспросом четыре. При 32 000 на вопрос в минуту помещается
**семь-восемь обращений** — а канал живёт всплесками, и в утренний пик
столько приходит вполне. Упрётся это не в «дорого», а в отказ прокси,
и по виду он неотличим от «бот промолчал»: ровно тот тихий отказ, который
уже был на лимите поста Mattermost.

Отсюда две вещи, которых пока нет и которые стоит завести раньше выхода
в основной канал: **лимит TPM надо запросить под этот аккаунт** (по карточке
это делается в `~gpt-support` с названием модели и аккаунта), и **отказ
прокси обязан быть виден** — сейчас он приедет как пустой ответ ядра,
а должен приезжать строкой джуну наравне с `check_failed`. Мерить расход
уже есть чем: `materials_len` в телеметрии.

Отдельный блок `export.md` вынесен по этой же логике и остаётся вынесенным:
правила выгрузки в вопросе про отчёт не просто стоят токенов — они задают
другой формат ответа, и держать два формата в одном тексте значит получить
их смесь.

Решения, которые важно не потерять:

- **Мастера домена добирает КОД, а не промпт.** Узел `Plan` парсит таблицу
  «Домены» из `index.md` и добавляет мастеров сам. Живой прогон показал, что
  словесные лимиты («до пяти раз») агент не соблюдает — значит, мог пропустить
  и мастера. Теперь это свойство конструкции, а не дисциплины модели. Тесты
  1–3 в `test_pipeline.mjs` держат этот инвариант, и они ломаются при правке
  таблицы «Домены», а не только кода.
- **Промпт разделён на роутер и автора.** Роутеру не нужны правила оформления
  черновика, автору — правила поиска. В tool-loop оба набора платили токенами
  друг за друга в каждой итерации. Поэтому реестр вклеивается **только**
  роутеру, а материалы — только автору.
- **Промпты — в `prompts/*.md`, а не в JSON.** Стали diff-абельными файлами,
  и 12 замен по якорям из `patch_prompt.py` больше не нужны. HTML-комментарии
  в начале файла адресованы тому, кто правит промпт: сборщик их срезает,
  чтобы не платить за них токенами.
- **Реестр уходит в промпт проекцией, а не целиком.** Только `##`-заголовки
  и строки таблиц: 7 971 → 5 364 символа, −33%. Комментарии (1 151 символ)
  и проза между таблицами модели не нужны. Если таблиц в проекции не осталось
  (формат `index.md` изменился), отдаётся полный текст — дороже, но работает,
  а не молча пустой реестр. Узел `Plan` при этом читает поле `full`: разбор
  мастеров не должен зависеть от фильтрации.
- **Чтение статей — обычной GitLab-нодой, ноль токенов.** Раньше каждая статья
  приходила ответом инструмента и потом пересылалась модели в каждой следующей
  итерации. Теперь текст попадает к модели ровно один раз.
- **Ни один выход не ветвится на два узла.** В n8n нет неявного слияния: узел
  за развилкой выполнится по разу на каждую дошедшую ветвь. Развести `Plan`
  сразу в `Any articles` и `Need DD` значило бы два выполнения `Author` — два
  разных ответа на один вопрос и двойной расход. Поэтому ветки выстроены
  в цепочку: статьи → DD → сборка. Проверка в `test_adapters.mjs` следит
  за веером на выходе (сходящиеся ветви IF, наоборот, нормальны).
- **`Collect articles` обязателен.** `Read article` выполняется по разу на путь,
  и после него в `$json` лежит ответ GitLab API, а не план. IF `Need DD` читает
  `$json.dd_urn` — без свёртки условие молча не сработает ни разу, и метаданные
  полей не запросятся никогда: бот будет отвечать по статьям, считая, что видел
  инвентарь. Тест 11 держит это.
- **Двухшаговый DD в конвейере не нужен.** Промах фильтра в `DD Lookup` и так
  возвращает полный инвентарь — это его документированное поведение. Одного
  вызова достаточно: попал фильтр — придут описания, не попал — придёт список
  полей, и автор честно скажет, что такого поля нет.
- **Объектов DD может быть несколько, до четырёх.** Роутер возвращает
  `dd: [{urn, hint}]`, `Split DD` разворачивает список, `Call DD Lookup`
  выполняется по разу на объект, `Build materials` собирает через `.all()`.
  Главный кейс — вопрос про отчёт: нужны и сам отчёт (есть ли готовое решение),
  и витрина под ним (из чего считается); одного объекта не хватает. Промпт
  автора велит сначала предложить готовый отчёт, а витрину — как способ
  посчитать то же самое.
  Четыре решения внутри, каждое закрывает тихую ошибку:
  **пара `{urn, hint}` едет вместе** — общий фильтр на два разных объекта
  промахнётся хотя бы по одному; **каждый блок метаданных подписан своим URN** —
  два инвентаря без подписи это приглашение приписать поле не той витрине;
  **`.all()`, а не `.first()`** — раньше второй объект пропадал молча;
  **дубли URN и не-URN отбрасываются** в `Plan` — иначе лишние запросы и 404.
  Скалярная форма `{dd_urn, field_hint}` тоже принимается: модель может сбиться
  на прежний формат, и терять из-за этого метаданные целиком нельзя — пустой
  инвентарь читается как «полей нет». Тесты 8, 8б–8д в `test_pipeline.mjs`.
- **Пробелы называются, а не замалчиваются.** `Build materials` отличает
  «статьи нет в базе» от «статью не удалось прочитать», а при неудаче DD прямо
  запрещает автору формулировку «владелец не заполнил описания» — это
  ограничение выгрузки, а не пробел владельца. Обрезка по лимиту (8 статей)
  тоже перечисляется по именам. Тесты 6, 7, 9.

Прежние решения, остающиеся в силе:

- **Ядро отдельно, а не три триггера в одном флоу.** Два триггера n8n допускает,
  но текст агента ссылался на `$('When chat message received')`, которого
  в выполнении от Time-триггера нет. Главное не в этом: тест в чате должен
  проверять ровно то, что работает в канале, и при общем ядре это свойство
  конструкции, а не дисциплины. Копия промпта в трёх флоу разъезжается молча —
  так же, как список полей, скопированный из DD в статью.
- **Ядро возвращает структуру, а не текст.** Адресаты блоков разные: черновик
  читает коллега, `ИСТОЧНИКИ` с путями `kb/` — джун, `ЧЕГО НЕ ХВАТИЛО` — идёт
  в приоритизацию базы. Отправить в личку всё целиком значит нарушить то же
  правило, что запрещает служебное в черновике.
- **Слушаем и пишем разные каналы** — иначе цикл. В личке канал один и тот же,
  поэтому фильтр `props.from_bot` там не удобство, а условие работоспособности.
- **Ошибка разбора не роняет флоу и не молчит.** Формат сломан — уходит сырой
  текст плюс пометка `parse_error`. Пустой ответ выглядел бы как «бот не знает».
- **Лог живёт в канале джуна, отдельного канала нет.** Тестовый канал и так
  видит только джун, а служебный блок под черновиком и есть лог. Разборы из
  лички дублируются туда же: иначе самые живые вопросы в приоритизацию
  не попадут.

**Личка РАБОТАЕТ — проверено живым прогоном 2026-08-27.** `mattermostTrigger`
события DM при пустом `postedFilters` отдаёт, ответ в личку доходит. Прежняя
запись «не проверено, возможно потребуется WebSocket-сервис как
`Proxy Problem Bot`» снята: обходной механизм не нужен.

**Фильтр триггера лички задать МОЖНО — «Is Direct Message», и он обязателен.**
Здесь стояло «фильтр по каналам для лички задать нельзя: у DM-канала
техническое имя из двух `user_id`». Про имя канала это верно, а вывод был
неверный: у ноды есть операция «Is Direct Message» — фильтр не по имени,
а по типу канала.

Цена ошибки оказалась не теоретической. Пустой `postedFilters` нода
не принимает и при активации падает с «All filters are empty» — то есть
адаптер лички без фильтра просто НЕ ВКЛЮЧАЕТСЯ, и его выставляли руками
после каждого импорта. Ручная правка в интерфейсе живёт ровно до следующего
импорта, поэтому натыкались на это каждый раз заново: тот же класс, что
выключенная руками нода `Collect articles` и разъехавшийся Service Account,
только повторявшийся.

Теперь фильтр подставляет сборщик (`DM_POSTED_FILTER`). **Имя значения
`isDirectMessage` живым узлом не подтверждено:** нода `mattermostTrigger` v2
с `postedFilters` — сборка этого инстанса, в апстриме n8n её нет, и перечень
значений посмотреть негде; имя выведено из подписи в интерфейсе по обычному
для n8n правилу camelCase. Проверяется глазами при импорте — в поле Operation
должно стоять «Is Direct Message», а не пусто. Не совпало — скопировать
настроенную ноду из n8n в `bot/dm_trigger_filter.json`, сборщик читает её
и переопределяет догадку целиком (механизм `load_dm_filter()` заведён под
это давно и до 2026-08-31 стоял незаполненным).

Промах здесь безопасен, и это важно понимать: отсев лички целиком держится
на `Guard DM` (`channel_type === 'D'`), а фильтр триггера лишь режет лишние
срабатывания. Неверное имя даёт больше вызовов, а не неверные ответы, —
тогда как пустой фильтр давал неработающий адаптер.

**`DM_ALLOWLIST` в сборщике пуст, и теперь это не теоретический риск.**
Решение — отвечать только команде HR-аналитики, но список username'ов
не вписан. Пока он пуст, бот отвечает в личке **любому сотруднику компании**,
выдавая имена полей витрин и метаданные каталога. До 2026-08-27 это было
неприятно, но недоказуемо: не было известно, доходят ли до бота события DM
вообще. Теперь известно, что доходят. Сборщик предупреждает на каждом прогоне.

**Разбор формы проверен на одном варианте.** Живой пример — тема «Вопрос по
отчетам» с полями «Выбери домен», «Укажи ссылку на отчет», «Напиши свой вопрос».
Формы остальных тем (у выгрузки свои поля) видны только по обработанной таблице
`hr-report-ask-3-4-aug-2026.md`, а не по сырым постам, поэтому разбор сделан
общим: метка — строка, кончающаяся двоеточием. Нераспознанное не теряется, оно
попадает в `question_text`, и худший случай — уверенность не понизится там,
где могла бы. Что разобралось, видно в данных ноды `Guard channel`:
`form_parsed`, `topic_kind`, `form_domain`.

## Телеметрия канала: обвязка процесса поддержки

Отдельная конструкция, не часть бота. Считает обращения, время реакции и
решения, разрез по типам, качество ответов бота. Собирается
`build_telemetry_flows.py`, проверяется `node test_telemetry.mjs`.

**Почему отдельно от бота.** У телеметрии другой жизненный цикл, другие
триггеры (push-события, крон, вебхук кнопок) и другая цена отказа. Падение
записи в таблицу не должно ронять ответ коллеге, а падение бота не должно
означать, что обращение не посчитано. Граница: **бот пишет только то, что
знает один он (`confidence_key`, `gaps`, версия промпта); всё, что видно
в канале, собирает коллектор.**

```
Telemetry Ingest      executeWorkflowTrigger { event, data, post }
                      → Normalize → Write event (upsert по event_id)
                      ← ЕДИНСТВЕННАЯ точка записи: сменить хранилище =
                        правка одного узла, вызывающие о нём не знают

Telemetry Collector    Time Trigger [posted, reaction_added, reaction_removed]
                       → Guard channel (кодом) → Our channel
                         ├ реакция → Get post → Merge reaction ─┐
                         └ posted ────────────────────────────→ Ingest

Telemetry Backfill     ручной → GET /channels/{id}/posts → Explode → Ingest
                       ← посты и metadata.reactions одним запросом

Telemetry Flush        Cron 1 ч → Watermark (Trino: MAX(ingested_at))
                       → Read watermark (кодом) → Read new events (Data Tables)
                       → Build batch (чанки, MERGE) → Any new rows
                         ├ да  → Write batch (Trino, по запросу на чанк)
                         └ нет → ∅   заливать нечего

Feedback Webhook       Webhook ← кнопка под ответом бота → Ingest (не собран)
Support Bot Core       +1 узел: Ingest (bot_answered, домены)     (не собран)
```

Хранилище сейчас — **n8n Data Tables**, таблица `support_event`. Схема:
`python3 build_telemetry_flows.py --print-schema` (колонки заводятся руками
в UI, тип потом не меняется). Типы Data Tables — только
`string / number / boolean / date`, поэтому `payload` уезжает строкой JSON:
дробить его на колонки нельзя, у разных типов событий разные поля, и таблица
ехала бы на каждом новом типе. Наверх вынесено только то, по чему группируется
витрина: `kind` и `domains`.

**Запись — `upsert` по `event_id`, а не `insert`.** Крон-сверка и повторный
прогон backfill перечитают те же посты; без совпадения по ключу в витрине
появятся дубли, и «обращений за неделю» вырастет без причины.

**Имена параметров узла `Write event` выведены из документации, а не
подтверждены живым узлом.** Документация Data Tables описывает поля интерфейса
(«Must Match», «Conditions», «Mapping Column Mode»), а не ключи JSON. Условие
upsert собрано как `filters.conditions[].keyName/condition/keyValue`,
маппинг — `columns.mappingMode: autoMapInputData`. При импорте эту одну ноду
надо открыть и посмотреть, что n8n прочитал условие по `event_id`, а не
показал пустое поле. Если имена другие — правка в `build_telemetry_flows.py`,
функция `build_ingest()`.

**Вызов `Ingest` намеренно БЕЗ `workflowInputs`.** Триггер объявлен
`passthrough`, потому что события Time — вложенные объекты (`data.reaction`,
`post.props`), а типизированные входы рассчитаны на скаляры, как `urn`/`search`
в `DD Lookup`. Пустой `{"mappingMode": "defineBelow", "value": {}}` хуже
отсутствия: он объявляет «маппинг задан, полей ноль» — в `Ingest` уехал бы
пустой элемент, нормализатор записал бы `unsupported_event`, и флоу остался бы
зелёным при мусоре в таблице. Тест 24.

**`Backfill` ходит в API с credential «Time Bully».** Анонимный запрос вернул
бы 401 без постов, а `Explode posts` прочитал бы это как `backfill_empty` —
«за период ничего не было». `followRedirects: false` по той же причине, что на
нодах DD: редирект на страницу логина иначе приходит как 200 с HTML. Тест 25.

**DLH Trino — постоянное хранение, но писать в него построчно нельзя.** Три
причины, каждая ломает по-своему: каждый `INSERT` в Iceberg/Hive рождает файл
и версию метаданных, за месяц это десятки тысяч мелких файлов — и деградирует
**чтение**, то есть будущий дашборд; `POST /v1/statement` не отдаёт результат
сразу, а требует ходить по `nextUri`, в HTTP-ноде это рукописный цикл; и
главное — при недоступности DLH событие push-триггера теряется навсегда.
Data Tables закрывают всё три и служат буфером: пишем по одному, сольём
пачками. Лимит всех Data Tables инстанса — 200 MiB
(`N8N_DATA_TABLES_MAX_SIZE_BYTES`); при ~156 обращениях в месяц и ~6 событиях
на обращение это порядка 1 МБ в год, запас большой.

### `Telemetry Flush`: перелив в DLH раз в час

Нода — `CUSTOM.trino` с credential «DWH (Trino DLH) account 128», тип и
credential подтверждены экспортом воркфлоу `DLH Examples`
(id `GMKFVejvauDT3k9h`). Таблица `dl.usr_cross_data.support_telemetry` создана
руками; DDL всё равно живёт в сборщике — `python3 build_telemetry_flows.py
--print-ddl`, генерится **из `SCHEMA`**. Состав колонок в запросе обязан
совпадать с таблицей, и разъезжаются они молча: лишняя колонка в `SCHEMA` даёт
ошибку Trino (громко), **не хватающая — тихо не залитые данные**.

Четыре решения, каждое закрывает тихую ошибку:

- **`MERGE INTO … ON t.event_id = s.event_id`, а не `INSERT`.** `Ingest` пишет
  в Data Tables upsert'ом и **всегда** ставит `ingested_at: Date.now()`.
  Значит повторный backfill или крон-сверка обновляют существующую строку,
  у неё появляется новый `ingested_at`, она снова проходит фильтр watermark —
  и при `INSERT` уезжает в Iceberg **второй** строкой. В Data Tables запись
  была идемпотентной, в DLH перестала бы: «обращений за неделю» выросло бы
  без причины, и увидеть это можно только сравнив две витрины.
  Запасной путь есть — `DLH_WRITE_MODE=insert` (если у аккаунта нет прав на
  MERGE), но тогда дедуп по `event_id` **обязан** делать пересчёт витрины:
  `ROW_NUMBER() OVER (PARTITION BY event_id ORDER BY ingested_at DESC)`.
  Режим задаёт и форму запроса, и условие фильтра: `gte` при merge
  (перезалив краевой строки идемпотентен, зато строка с тем же миллисекундным
  `ingested_at` из упавшего чанка не потеряется), `gt` при insert — иначе
  краевая строка дублировалась бы каждый час. Тест 33 держит согласованность
  двух нод, которую в n8n не держит ничто.
- **Батч режется на чанки** (200 строк / 500 000 символов SQL), по одному
  запросу на чанк. `returnAll` плюс один `INSERT` со всеми строками упирается
  в `query.max-length` Trino (по умолчанию 1 000 000 символов), а засев
  истории — это ~1000 событий с `payload` по 0.5–2 КБ, то есть SQL в единицы
  МБ. Отказ при этом накрывает **весь** батч, а не хвост: после backfill
  первый же прогон не залил бы ничего. Чанки идут **по возрастанию
  `ingested_at`**, поэтому падение на середине оставляет в DLH консистентный
  префикс — watermark следующего прогона встаёт ровно на границу залитого.
  При произвольном порядке провал в середине оставил бы дыру, которую
  watermark перешагнул бы молча. Строка длиннее лимита целиком уезжает своим
  чанком: молча выбросить её нельзя, событие пропало бы навсегда. Тест 34.
- **Watermark — запросом `MAX(ingested_at)` к самой таблице**, а не отдельным
  курсором: хранить его значило бы городить ещё одну табличку ради одного
  числа и ловить рассинхрон с Trino при сбое на полпути. Разбор ответа — своим
  узлом `Read watermark`, и **нераспознанная форма роняет прогон**. Форма
  ответа `CUSTOM.trino` живым прогоном не подтверждена, а подставленный 0 —
  это перезалив всей истории каждый час (merge) или дубли всей истории
  (insert); пустое значение — тихо не доезжающая до DLH телеметрия,
  неотличимая по виду флоу от «новых событий не было». Тест 35.
- **Дубли `event_id` схлопываются в узле и называются числом.** В Data Tables
  ключ уникален по upsert'у, но имена параметров условия в `Write event`
  живым узлом не подтверждены: если условие не сработало, в таблице лежат
  дубли, и для MERGE это ошибка Trino «несколько строк источника на одну
  строку цели» — падение всего прогона из-за пары строк. Схлопываем, оставляя
  последнюю запись, но `duplicates_collapsed` в данных ноды — единственный
  сигнал о неработающем upsert'е, поэтому молчать нельзя. Строки без
  `event_id` в батч не идут (все склеились бы в одну) и тоже считаются.

**Что осталось проверить живым прогоном**, всё три — после первого импорта:

1. **Имена полей ноды `CUSTOM.trino`** (`query` / `timeout` / `timeZone`).
   Три попытки скопировать заполненную ноду дали `parameters: {}` — похоже,
   она не сериализует свои поля обычным механизмом n8n. Названия взяты по
   подписям в UI. Открыть `Watermark` и `Write batch`: если Query/Timeout/Time
   Zone пустые — ключи угаданы неверно, править `build_flush()`.
2. **Условие `gte` в фильтре Data Table** по `ingested_at` — первое сравнение
   в проекте (везде был `eq`).
3. **Права на MERGE** в `usr_cross_data` и формат таблицы: row-level update
   в Iceberg требует format v2. Отказ здесь громкий; лечится либо `ALTER TABLE
   … SET PROPERTIES format_version = 2`, либо переходом на `DLH_WRITE_MODE=insert`
   с дедупом в витрине.

### Доменная разбивка — из роутера бота, а не из отдельной LLM

Роутер ядра **уже** определяет домен по таблице «Домены» реестра, а узел `Plan`
добирает мастеров домена. Это готовая кластеризация обращений: шесть доменов
(`headcount-structure`, `legal`, `movement`, `allocation`, `attendance`,
`education`), сопоставленных со словами заказчика по колонке «о чём вопросы».
Отдельная LLM для телеметрии платила бы вторым вызовом модели за то, что ядро
уже посчитало.

Домены **не доезжали** до выхода ядра — `Parse answer` их не отдавал. Добавлены
`domains`, `articles_read`, `dd_count`, `router_error`; проверка — тест 20
в `test_adapters.mjs`.

Две границы, которые важно держать:

- **Домены — факт работы бота** (что он искал), а не оценка обращения.
  Пустой список значит «роутер домен не определил» и читается именно так:
  сигнал о пробеле в реестре. Подставлять заглушку нельзя — пробел перестанет
  быть виден.
- **Разрез по темам и разрез по доменам — разные вещи.** `kind` из префикса
  формы отвечает «что просили» (выгрузка / вопрос по отчёту), домен —
  «про какие данные». Первый есть у 100% обращений, второй только у тех,
  где бот отработал. Складывать нельзя, и в витрине это две независимые
  группировки.

Тонкость: `kind` живёт только на `request_created`. У реакции темы нет, и
выдумывать её из треда значило бы запрос к API на каждое событие — пересчёт
витрины берёт `kind` с корневого события треда. Тест 18.

### Push плюс редкий крон, а не одно из двух

`mattermostTrigger` v2 отдаёт `reaction_added` и `reaction_removed` — WebSocket-сервис
не нужен. Push даёт точные таймстемпы, а крон-сверка (раз в сутки) догоняет
потерянное на перезапуске n8n. Пропущенное событие теряется навсегда,
пропущенное окно опроса догоняется следующим проходом; идемпотентность
по `event_id` делает повторный проход бесплатным. Тем же механизмом
засевается история за июль–август.

### Модель данных: append-only лог плюс пересчёт витрины

`support_event` никогда не апдейтится: `event_id`, `thread_id`, `event_ts`,
`ingested_at`, `event_type`, `actor`, `source`, `payload`. Четыре источника
пишут про одно обращение в разное время — апдейтить одну строку из четырёх
мест значит ловить гонки и молча терять данные.

`support_request` — витрина, **целиком пересчитывается** из лога. Тогда
снятие реакции разбирается само, а неверная логика метрики чинится
ретроспективно, без переписывания истории. Ключ склейки — `root_id` треда.

Живёт в `telemetry/support_request.sql` — три самостоятельных запроса:

| | |
|---|---|
| `CREATE OR REPLACE VIEW dl.usr_cross_data.support_request` | одна строка = одно обращение |
| диагностика | что витрина **отбросила**: треды без корня, неизвестные типы событий, нераспознанные темы, пустые прогоны backfill, лаг записи |
| метрики | p50/p85 по `kind`: reaction / lead / cycle time, доля закрытых нерешёнными, калибровка уверенности |

**Вью, а не таблица.** Пересчёт из лога — определение витрины, а не способ
её обновления: при вью «пересчёт» происходит сам на каждом запросе, и
рассинхрона между логом и витриной не существует. Строк тут тысячи в год,
поэтому материализовать нечего. `CREATE TABLE AS` понадобится только если
дашборд начнёт упираться в время запроса — и тогда это отдельное решение
с крон-пересчётом, а не молчаливая замена.

Решения внутри витрины, каждое закрывает тихую ошибку:

- **Обращение — только тред с `request_created`.** Триггер `posted` пишет
  и реплики, и посты чужих тредов; считать обращением каждый тред значит
  завысить счёт в разы. Но отсев **назван числом** (`threads_without_root`
  в диагностике): без него остановившийся коллектор и поломанный разбор темы
  дают ту же картину, что «обращений стало меньше».
- **`event_ts = 0` превращается в NULL до всякой арифметики.** Нормализатор
  пишет 0, когда времени в событии не было, и в DLH это 1970-01-01 —
  reaction time уехал бы в минус 56 лет и потянул бы за собой медиану.
- **Правила снятия реакций разведены.** `taken_at` — первое добавление
  `:loading:` за историю треда, `taken_removed` витрина не смотрит вовсе;
  закрывающую реакцию снятие **переоткрывает**. При едином правиле «снятие
  сбрасывает» reaction time обнулился бы у всех закрытых обращений.
  При совпадении миллисекунды у пары «поставили / сняли» тай-брейк считает
  обращение **открытым**: незакрытое видно дежурному, ложно закрытое — нет.
- **Дедуп по `event_id` оставлен, хотя при `merge` избыточен.** Он нужен
  ровно в режиме `insert`, и стоит одну оконную функцию — а цена его
  отсутствия при переключении режима это молча выросшие счётчики.
- **Домысленный тип реакции помечен** (`reaction_types_inferred`): если
  `mattermostTrigger` не отдал имя события, снятие приехало как добавление,
  и снятое «взято в работу» останется в метриках навсегда. Знать, каким
  строкам верить, важнее, чем иметь ровную колонку.
- **Тест 36 в `test_telemetry.mjs` сверяет витрину со сборщиками.** Он
  собирает все типы событий из `build_telemetry_flows.py` (включая
  динамические — из словаря `EMOJI`) и требует, чтобы каждый был либо
  использован в SQL, либо назван в блоке «события, которые витрина не
  использует» с причиной. Он же проверяет имена полей `payload` **по двум**
  сборщикам: `confidence_claimed`/`confidence_key` приходят из ядра бота,
  то есть из `bot/build_time_flows.py`. Новый тип события или переименованное
  поле ломают тест, а не тихо превращаются в пустую колонку дашборда.

**Синтаксис SQL живым прогоном не проверен** — Trino доступен только из n8n.
Первый запуск — руками, и начинать стоит с диагностики: она читает те же
CTE, но ничего не создаёт.

Два пробела, найденные при сборке витрины:

- **`draft_useful` и `answer_helpful` сейчас нечем развести.** Оба приезжают
  одним событием `bot_feedback`, а `channel_id` в payload вебхука не пишется.
  Пока кнопки стоят только под черновиком, это оценка джуна — и витрина так её
  и называет. Когда кнопки появятся в канале обращений, `channel_id` в payload
  **обязателен**: иначе две разные метрики склеятся молча.
- **Настоящий автор обращения в логе не разобран.** Корневой пост публикует
  intake-воркфлоу, поэтому `actor` — это он; человек с вопросом есть только
  в шапке формы («от пользователя @X»), и нормализатор её не парсит. Поле
  поэтому называется `posted_by`, а не `author`: неверная подпись хуже
  отсутствующей колонки. Разбор шапки уже есть в guard'е бота — при
  надобности переносится оттуда.

### Решения, которые важно не потерять

- **Тема обращения — из префикса `Cross Data | <Тема>`.** Проставлена
  человеком в форме intake-воркфлоу: самый надёжный источник разреза из трёх
  возможных (форма / реакция / LLM), и он уже есть. Ни четвёртой реакции-метки,
  ни LLM-классификатора не нужно. `kind_source = 'intake'`.
  Порядок проверки префиксов — **от длинных к коротким**: «Вопрос команде
  DWH HR» это префикс своей же уточнённой версии с ` | `, и наивный обход
  списка отдал бы обеим один `kind`. Сортировка в коде, а не дисциплина при
  правке списка. Тесты 2 и 3.
- **Неизвестная тема называется, а не проглатывается.** `kind='unknown'`
  плюс сырой префикс в `payload`: форму расширят новой темой, и телеметрия
  должна это показать. Тест 4.
- **Обращения к DWH HR пишутся с `ours=false`.** Считать отдельно можно,
  задним числом добрать пропущенное — нельзя. Тест 5.
- **Реакция не знает про тред.** В событии есть `post_id` и нет `root_id`,
  а ставят её на любое сообщение внутри треда. Без догоняющего
  `GET /posts/{id}` одно обращение размажется на несколько записей, и
  в витрине это выглядит как «обращений стало больше». Обязательный узел,
  не оптимизация. Тест 6.
- **Тело реакции приходит JSON-строкой,** а не объектом. Без разбора
  `emoji_name` был бы `undefined`, и все реакции молча стали бы неизвестными:
  дежурный размечает, а метрики пустые. Тест 7.
- **Правила снятия у эмодзи РАЗНЫЕ.** Дежурный снимает `:loading:`, когда
  ставит закрывающую реакцию, — при едином правиле «снятие сбрасывает»
  reaction time обнулился бы у **всех** закрытых обращений. Поэтому
  `:loading:` = первое добавление за историю треда, снятие не сбрасывает;
  закрывающие реакции снятие переоткрывает (там это исправление ошибки).
  Тест 9.
- **`postedFilters` не действует на реакции.** Фильтр по каналам в ноде
  привязан к событию `posted`; подписавшись на реакции, получите их из всех
  каналов, где состоит бот. `Guard` по `channel_id` обязателен, и id канала
  нужен заранее — по имени нода реакции не отфильтрует.
- **Реакции бота отсеиваются.** Бот ставит реакции уверенности в тот же
  канал: считать их за «дежурный отреагировал» = получить медиану в секунды
  и не заметить проблему. `BOT_USER_IDS` в сборщике, тест 12.
- **Связку с трекером ставит машина.** Intake-воркфлоу постит в тред ответ
  со ссылкой на заведённую задачу — оттуда и берётся ключ. Регулярка по
  ключу, который человек забыл написать, не нужна; заведение задачи по
  реакции из n8n тоже отменяется. Тест 10.
- **Реплика в треде ≠ обращение.** Триггер `posted` срабатывает на каждое
  сообщение; считать их обращениями значит завысить счёт в разы. Тест 11.
- **Выход нормализатора никогда не пустой.** Пустой читался бы как «событий
  не было», тогда как это всегда следствие фильтра. Тесты 12 и 16.

### Метрики: определения важнее названий

- **Reaction time** = `taken_at − created_at` (по `:loading:`). Самая понятная
  людям и быстрее всех реагирующая на изменения.
- **Lead time** = `closed_at − created_at`. Что чувствует заказчик. Включает
  ожидание в очереди.
- **Cycle time** = из changelog задачи трекера. Чем управляет команда.
  Очередь не включает.

Lead и cycle расходятся ровно на длину очереди, и эта разница обычно и есть
предмет разговора — мерить только одно значит её потерять. Брать **p50 и
p85**: среднее по правому хвосту врёт всегда, а p85 — это те самые пара
выгрузок в неделю, из-за которых на команду смотрят криво.

Разделение `:done_checkmark:` / `:im_red_cross:` даёт бесплатную метрику
**доли закрытых нерешёнными** — честнее, чем «закрыто N обращений».

**Калибровка — самая ценная метрика:** доля случаев, где бот сказал «высокая
уверенность», а черновик переписали. Врущий `confidence` опаснее низкого
покрытия. Мерить есть чем с первого дня, и мерить нужно **по паре полей**:
`confidence_claimed` — что сказала модель, `confidence_key` — что осталось
после понижения кодом. По одному полю не видно ни того, что модель
систематически завышает, ни того, насколько часто её приходится поправлять;
частота понижений — сама по себе метрика качества промпта автора.

**Кнопки нажимают единицы,** поэтому считать ненажатие за «плохо» —
гарантированно неверная метрика. Нужен прокси-сигнал на 100% обращений: тред
закрылся после ответа бота без правок — вероятно, помогло; черновик переписали
целиком — не помогло. Оба вычисляются из лога бесплатно.

`draft_useful` и `answer_helpful` — **разные поля**: черновик уходит джуну
в `~stonis_hakcs_2`, а не автору вопроса, поэтому кнопка там меряет
полезность для джуна, а не помог ли ответ автору. Складывать нельзя.

### Кнопки под ответом бота

Механизм — `props.attachments[].actions[]` с `integration: {url, context}`,
URL ведёт на вебхук n8n. Три места, где спотыкается:

- **Стандартная нода `mattermost` v1 вряд ли умеет `actions`.** Такой пост
  отправляется HTTP-нодой на `POST /api/v4/posts` с полным телом — подгонять
  ноду не надо.
- **Текстовая обратная связь — через диалог,** не «напишите в тред». Кнопка
  отдаёт `trigger_id`, по нему `POST /api/v4/actions/dialogs/open`. `trigger_id`
  живёт секунды, поэтому вебхук открывает диалог **первым же действием**, до
  записи в лог.
- **В `context` кладётся версия промпта и `confidence_key`** — иначе через
  месяц не разобрать, на какую версию бота ругались. Ответ вебхука заменяет
  кнопки на «записано»: это же защита от повторных нажатий.

### Порядок установки

Четыре шага, все из-за статических id — та же причина, что у `DD Lookup`.
Всё из папки `telemetry/`:

1. `node make_table_csv.mjs` → импортировать `support_event.csv` в Data Tables
   (или завести колонки руками: `python3 build_telemetry_flows.py --print-schema`)
2. `python3 build_telemetry_flows.py` → импортировать `Telemetry Ingest.json`,
   скопировать id
3. `INGEST_WORKFLOW_ID=<id> python3 build_telemetry_flows.py`
4. Импортировать `Telemetry Collector.json` и `Telemetry Backfill.json`
5. Для перелива в DLH: сверить таблицу Trino с `python3
   build_telemetry_flows.py --print-ddl` (создаётся руками), импортировать
   `Telemetry Flush.json` и **открыть ноды `Watermark` и `Write batch`** —
   пустые Query/Timeout/Time Zone значат, что имена полей `CUSTOM.trino`
   угаданы неверно. Первый прогон — вручную, а не по крону: батч сразу
   заберёт всю накопленную историю, и смотреть на него надо глазами.

**Про CSV.** Файл несёт 3 строки-примера, и это не декорация: n8n определяет
тип колонки **сэмплированием данных**, а тип потом неизменяем. CSV из одного
заголовка сделал бы `string` во всех колонках, включая `event_ts` и
`ingested_at` — и сравнения по времени в витрине пришлось бы делать над
строками. Поэтому в примерах у числовых колонок стоят числа.

Импорт CSV создаёт таблицу **и заливает данные** одним действием, так что
примеры станут настоящими строками лога. Они помечены: `event_type =
schema_sample`, `event_id` с префиксом `sample:`. Удалить после импорта —
пересчёт витрины их всё равно отбросит (нет `request_created` с реальным
`thread_id`), но мусор в логе оставлять незачем.

Файл **без BOM** намеренно. С ним первая колонка читается как `﻿event_id`,
а `Ingest` делает upsert ровно по `event_id`: ключ идемпотентности молча
перестал бы совпадать, и каждое событие писалось бы новой строкой. Тест 26.

При импорте **сверить типы, которые предложит n8n**, с выводом
`make_table_csv.mjs`: `event_ts` и `ingested_at` — `number`, остальные
`string`. Ошибка в типе исправляется только пересозданием таблицы.

Без шага 3 в коллекторе остаётся плейсхолдер и вызов падает на «workflow not
found». Это осознанно громкая ошибка: тихо не записанное событие push-триггер
не повторит.

### Статусы задач: `Collector Tracker`

Дежурный нажимает «завести задачу» → бот отвечает в тред сообщением со
ссылкой. Оттуда коллектор канала берёт ключ (`task_linked`), а
`Collector Tracker` опрашивает по нему T-Tracker раз в 15 минут.

**Спейс не нужен.** Опрашиваются ровно те ключи, что пришли из тредов, через
TQL `taskKey IN ("CROSS-1", …)`. Это же снимает вопрос «в каком спейсе будут
задачи»: коллектор узнаёт о задаче из канала, а не ищет её по проекту.

**В T-Tracker НЕТ истории переходов.** Проверено 2026-08-10:
`/tasks/{key}/history`, `/changelog` и Jira-совместимый слой отвечают 404.
Доступны только `create_at`, `finish_at` и `status_update_at` — время
**последнего** перехода, одно значение. Следствия:

- `create_at` и `finish_at` точны всегда → время от заведения задачи до
  готовности выгрузки считается надёжно, независимо от частоты крона;
- промежуточные статусы видны только те, что коллектор **застал**. Переход,
  случившийся и смененный между опросами, теряется. При интервале 15 минут
  и задачах на дни это шум, но события помечены `snapshot: true` — чтобы
  приблизительность не выдавали за точность;
- `event_ts` берётся из `status_update_at`, а **не** из момента опроса, иначе
  все времена поехали бы на величину интервала. Тест 29.

Решения, каждое закрывает тихую ошибку:

- **Ключ берётся из ССЫЛКИ, а не из любого похожего текста.** «HR-2» в вопросе
  или имя таблицы `MDM-1` дали бы связь с несуществующей задачей — и cycle
  time потерялся бы там, где он есть. Голый ключ принимается только от бота:
  он пишет по шаблону. Тест 27.
- **Закрытые задачи не опрашиваются.** Статус не изменится, а список иначе
  растёт бесконечно и упирается в лимит запроса.
- **Задачи из jira3 пропускаются** (`tracker: 'jira'` в payload). Коллектор
  умеет только T-Tracker; запрос по чужому ключу вернул бы пустоту, которую
  легко прочитать как «задача исчезла». Задачи за июль–август остаются
  историей — их статусы, если понадобятся, берутся из changelog jira3, где
  он есть.
- **Пустой список — не пустой запрос.** TQL с `IN ()` вернул бы ошибку либо
  все 68 тысяч задач трекера. Тест 28.
- **Опрос поиском, а не точечным GET.** `GET /tasks/key/{key}` отдаёт 403 на
  задачу из недоступного спейса и роняет прогон целиком; поиск возвращает
  только доступное, а расхождение списков ловится в `Diff`.
- **Событие только на ИЗМЕНЕНИЕ статуса.** Иначе каждый прогон крона добавлял
  бы строку на задачу — сотни записей в день без новой информации.
- **Невернувшаяся задача называется.** Нет доступа к спейсу или задачу
  удалили — пишется событие с `error`. Молчание выглядело бы как «статус
  не менялся», и cycle time тихо замер бы.
- **Финальность по `finish_at`, а не по названию статуса.** В T-Tracker
  76 статусов на инстанс (`Done`, `Closed`, `Completed`, `Released`,
  `В работе`, `Cancel`, …), и какие из них использует воркфлоу выгрузок —
  заранее не известно. `finish_at` трекер заполняет сам по статусу
  с `aux.type = finish`. Список названий оставлен только подсказкой.

### Врезка в личку: один узел на два адаптера, разные источники

Ответы из лички в лог не попадали вовсе — узел `Ingest` стоял только
в адаптере канала. Калибровка при этом считалась только по каналу, а в личке
спрашивают иначе: формы нет, человек пишет свободным текстом, и промахи
роутера видны там лучше всего. Врезка сделана в `Adapter DM` третьей ветвью
от ядра, рядом с ответом человеку и копией в канал джуна.

Четыре решения, каждое закрывает свою тихую ошибку:

- **Узел ОДИН на два адаптера, а не копия.** Поля `payload` витрина читает
  по именам, и вторая копия разъехалась бы с ней молча — ровно как разъезжались
  credential'ы и списки тем. Различаются адаптеры только именем guard'а
  и значением `source`, оба подставляет сборщик (`answer_event_js`).
  Тест 46 в `test_adapters.mjs` сверяет тексты узлов и состав payload.
- **`source` разделяет канал и личку, и это не украшение.** У обращения
  из лички нет ни формы, ни реакций дежурного, ни задачи в трекере: время
  реакции, время решения и доля закрытых по нему не считаются вовсе. Смешать
  их с канальными значило бы разбавить каждую метрику процесса строками,
  у которых этих метрик нет.
- **Счётчик отсева не должен расти от нормальной работы.** У обращения
  из лички нет `request_created` — intake-воркфлоу его не публикует, — и без
  исключения каждый ответ в личку увеличивал бы `threads_without_root`.
  Этот счётчик заведён ловить остановившийся коллектор и поломанный разбор
  темы; нормальная работа лички выглядела бы в нём как поломка канала,
  и смысл счётчика пропал бы целиком. Личка исключена и **названа своим
  числом** (`dm_answers`), а не просто вычтена.
- **Ответы из лички читаются, иначе врезка пишет в никуда.** Витрина
  `support_request` построена на `request_created`, и строк лички в ней нет
  и быть не может. Поэтому калибровка вынесена отдельным запросом поверх
  `bot_answered` с разрезом по источнику — и разрез берётся из
  `payload.channel_kind`, а не из служебной колонки `source`: колонку ставит
  нормализатор и может переопределить, а payload пишет сам адаптер.

Проверки: группа 46 в `test_adapters.mjs` (структура, прогон узла, отсутствие
схождения ветвей), группа 42 в `test_telemetry.mjs` (нормализатор, счётчик
отсева, наличие запроса и разреза).

### Узел телеметрии в ядре бота — отдельным шагом

Ответ бота сейчас уходит в `~stonis_hakcs_2`, а не в канал обращений: бот ещё
не выведен в `~hr-report-ask` полноценно. Врезка `Ingest` в ядро от этого
не зависит — `bot_answered` пишется по `thread_id` исходного обращения, и
где напечатан черновик, для лога неважно.

Порядок такой: сначала коллектор и Data Tables на живом канале (обращения,
реакции, время реакции и решения — всё это уже считается без бота), потом
врезка в ядро. Причина не в сложности, а в отладке: коллектор трогает данные
канала, врезка трогает работающий бот, и ломать их одним прогоном незачем.
Когда бот выйдет в канал, `draft_useful` (кнопка джуна) и `answer_helpful`
(кнопка автора вопроса) станут разными полями — они и сейчас разные.

### Фикс `Guard channel`: бот отвечал не на то

Найдено при разборе телеметрии. В `Guard channel` не было условия на префикс
темы, а триггер `posted` срабатывает на каждую реплику — бот писал черновик
на любое сообщение в канале, включая обсуждение внутри треда и обращения
к чужой команде DWH HR.

Хуже было условие `from_bot != true`: если intake-воркфлоу постит обращение
от имени бота или через вебхук, оно отбрасывалось — бот **не отвечал на
реальные обращения**, зато отвечал на переписку вокруг них, то есть работал
наоборот. По виду канала это незаметно: черновики появляются.

Теперь в канале: префикс `Cross Data |` + только корневые (`root_id == ''`),
а `from_bot` **убран** — эхо там невозможно по конструкции (слушаем
`hr-report-ask`, пишем `stonis_hakcs_2`). В личке `from_bot` остаётся
обязательным: там бот слушает и пишет один канал. Флаг `bot_echo` в `guard()`.

### Guard переехал в код: условия IF молча пропускали всё

Живой прогон 2026-08-10 показал, что бот **всё равно** отвечает на каждое
сообщение канала — включая реплики в тредах и обращения к DWH HR. При том,
что оба условия предыдущего фикса в собранном адаптере на диске были.

У такого отказа две возможные причины, и **по виду флоу они неразличимы**:

1. в n8n залита версия адаптера до фикса — условий там нет вовсе;
2. условия есть, но `post` пришёл не объектом, а **JSON-строкой** в `data.post`
   (ровно так Mattermost отдаёт событие, и нормализатор телеметрии это уже
   разбирает через `asObj()`). Тогда `$json.post.root_id` — `undefined`,
   `?? ''` даёт пустую строку, и условие «только корневые» **проходит для
   каждой реплики**. Фильтр на месте, выглядит рабочим, пропускает всё.

Второе — тихий отказ в чистом виде, и он же объясняет, почему прежние проверки
`gs.includes('root_id')` были зелёными на нерабочей конструкции: подстрока
в параметрах есть, поведения она не гарантирует.

Поэтому нормализация формы и решение об отсеве переехали из условий IF
в Code-ноду `Guard channel` (`GUARD_JS` в сборщике). Она распаковывает пост
один раз, возвращает элемент **всегда** и пишет решение в два поля: `pass`
и `reason` — «реплика в треде», «не наша тема: …», «системное сообщение», —
а ворота `Our request` (IF по `pass`) уводят отсев в пустую ветку. Причина
видна в данных ноды, гадать по каналу больше не нужно.

Что изменилось по существу:

- **Тема проверяется префиксом, а не списком тем формы.** Список сокращается
  и пополняется (в телеметрии он живёт в `TOPICS`), и бот не должен переставать
  отвечать на новую тему из-за того, что её забыли вписать в сборщик.
  Распознанная тема уезжает в поле `topic`. `Вопрос команде DWH HR` отсекается
  тем же условием — так же, как в телеметрии у этих тем `ours = false`.
- **Первая строка чистится от markdown** (`**Cross Data | …**`): intake-воркфлоу
  может обрамлять тему жирным, и тогда сообщение начинается со звёздочек.
- **`root_id == id` считается корнем.** Mattermost у корневого поста иногда
  проставляет `root_id` равным его же `id`; строгое «пусто» отбрасывало бы
  настоящие обращения.
- **Вопрос в ядро идёт из `$json.question`**, а не `$json.post.message` — guard
  уже распаковал пост, каким бы он ни пришёл.
- **Сломанный JSON не роняет ноду**: пустой пост — это отсев с причиной,
  а не исключение и не пропуск дальше.
- **`Guard DM` — та же нода** с другими флагами (`require_dm`, `bot_echo`,
  `allowlist`), чтобы разбор формы события не раздваивался.

Проверки — прогоном кода, а не поиском подстроки: тесты 21–23 и 25 в
`test_adapters.mjs` гоняют guard на реальных событиях, включая **обе** формы
payload (пост объектом и пост JSON-строкой). Тест 22 — тот самый кейс, на
котором прежний фильтр был зелёным и не работал.

Эта же нода теперь разбирает поля intake-формы — см. «Разбор intake-формы»
ниже. Отсев при этом не изменился: разбор только добавляет поля к выводу,
и `pass`/`reason` считаются ровно как раньше.

**Первое, что нужно сделать при таком симптоме, — переимпортировать адаптер.**
Файл на диске может быть уже исправлен: `git`-истории у `bot/` нет, и разойтись
с тем, что залито в n8n, он может молча.

### Лимит поста Mattermost: 4000 символов

Живой прогон 2026-08-10, уже с исправленным guard'ом: до ядра дошло ровно одно
обращение, ответ собрался — и `Post draft` упал с «Bad request - please check
your parameters». В ответе сервера: «Ваше сообщение слишком длинное. Допустимая
длина ограничена 4000 символами».

Цена отказа здесь высокая и незаметная: падает **последний** узел. Ядро уже
отработало, токены уплачены, черновик готов — и не доехал никуда. В канале это
выглядит как «бот промолчал», то есть неотличимо от «ответа в базе нет».

Текст поэтому не обрезается, а **разбивается** на несколько постов (`mmSplit`
в `MM_SPLIT_JS`, общий для канала, лички и лога лички):

- **3900, а не 4000** — запас на маркер `(1/2)` и на markdown, который мы
  добавляем сами. Упереться в лимит повторно значит снова уронить последний
  узел уже после того, как ответ собран.
- **Режем по границе строки**, при неудаче — по слову. Разрыв посреди
  markdown-ссылки или таблицы ломает разметку в обеих половинах.
- **Посты нумеруются.** Без `(1/3)` несколько постов подряд читаются как
  несколько разных ответов на одно обращение.
- **Не больше четырёх постов.** Больше — это не длинный ответ, а сбой, и
  спамить канал джуна нельзя. Хвост обрезается, и обрезка **называет, сколько
  символов потеряно**: молчаливый огрызок — тот же тихий отказ.
- Обрезка осталась только аварийной. Черновик для джуна — рабочий материал,
  и потерять его хвост значит заставить человека переспрашивать бота.

Нода `mattermost` отправляет по посту на входной элемент, поэтому сборщики
сообщений возвращают несколько элементов, а не один. Проверки — тест 24
в `test_adapters.mjs`: лимит соблюдён, содержание не потеряно, обрезка
называет потерю.

### Разбор intake-формы: три сигнала, которые ставил человек

Обращение приходит не текстом, а заполненной формой:

```
Cross Data | Вопрос по отчетам от пользователя @Anna Sokolova
Выбери домен:
Стоимость и расходы на персонал
Укажи ссылку на отчет:
https://proteus.tcsbank.ru/superset/dashboard/budget-corporate-events/?…
Напиши свой вопрос:
привет! подскажите, долились ли бюджеты на сотрудников летом…
```

Бот эти поля игнорировал целиком, хотя они **надёжнее любого вывода модели**:
их проставил человек. Теперь `Guard channel` их разбирает и отдаёт
`topic_kind`, `form_author`, `form_domain`, `report_url`, `question_text`,
`form_context` — и по ним кодом вычисляются и промах роутера, и пробел базы,
без второго вызова модели.

- **Разбор общий, а не по списку известных полей.** У каждой темы формы свои
  поля (у выгрузки — бизнес-задача, состав данных, чувствительность), и список
  в сборщике разъехался бы с формой молча. Метка — короткая строка, кончающаяся
  двоеточием; значение — всё до следующей метки. Нераспознанные метки не
  выбрасываются, а остаются в `question_text`.
- **В ядро уходит ПОЛНЫЙ пост, а не `question_text`.** Поля формы для автора
  содержательны, экономия от урезания нулевая, а риск потерять условие
  задачи — реальный. Отдельные поля едут рядом, для кода.
- **Автор — из шапки формы, а не из `sender_name`.** Постит intake-воркфлоу,
  и `sender_name` это он, а не человек с вопросом.
- **`\b` в JS определён по ASCII.** Первая версия отрезала хвост «от
  пользователя @X» регуляркой `/\bот\s+пользователя/` — она не совпадает
  с кириллицей **никогда**, и в тему уезжала вся шапка целиком. Проверка
  по подстроке была бы зелёной, поймал только прогон.
- **Обе формы payload.** Пост приходит и объектом, и JSON-строкой в `data.post`
  (ровно на этом прежний IF-фильтр молча пропускал всё). Разбор формы обязан
  работать одинаково: иначе поля приедут пустыми, правило про непокрытые отчёты
  не сработает, и по виду флоу это неразличимо. Тест 25 гоняет оба варианта.

### Уверенность считается кодом, а не берётся на слово

Живой прогон 2026-08-11. Вопрос: «долились ли бюджеты на сотрудников летом» со
ссылкой на дашборд `budget-corporate-events`. Ответ бота: «в витрине
`mdm_employee_structure_d` нет ни одного поля про бюджеты», **уверенность
высокая**, источники — три статьи про численность.

Разбор показал не плохую формулировку, а **тихий отказ**. Отчёта в базе нет
вовсе (`kb/reports/` пуста, строк типа `report` в реестре ноль). Роутер не
вернул ни одной статьи, но назвал домен `headcount-structure` — и `Plan` добрал
трёх мастеров этого домена, **как и обязан**. Автор получил полноценные
материалы не по теме вопроса и уверенно ответил по ним. То есть инвариант
«мастера читаются первыми и всегда» сработал, а оснований под ответом не было
ни одного.

При этом уверенность до этой правки **никто не считал**: `Parse answer` брал
слово модели и переводил его в ключ, а в `prompts/author.md` не было ни одного
критерия, что такое «высокая», — только правила, когда её понижать.

Теперь понижают **факты**, и это свойство конструкции, а не дисциплины модели —
ровно по той же причине, по которой мастеров добирает код:

| условие | до чего понижается |
|---|---|
| материалов не было вовсе | `нет ответа` |
| спрашивали про отчёт, отчёта в материалах нет, и роутер не подобрал ни одной статьи | `нет ответа` |
| то же, но статью роутер подобрал | `средняя` |
| всё прочитанное — мастера домена по умолчанию | `средняя` |
| `router_error` или `parse_error` | `средняя` |
| метаданные запрашивались и не дошли | `средняя` |
| реестр ссылается на файл, которого нет | `средняя` |

- **Повышения нет по конструкции.** Код не читал материалы и не знает,
  отвечают ли они на вопрос, — это остаётся за моделью.
- **Два уровня у правила про отчёт, а не один.** Понижать до «нет ответа»
  черновик, где ответ реально собран из подобранной статьи, значит отучить
  джуна читать черновики — тот же тихий отказ, только в другую сторону.
- **`unknown` не двигается вообще.** Это «модель отклонилась от формата», а не
  «средняя уверенность»: рядом печатается `parse_error`, и подменять этот
  сигнал понижением значит спрятать его за нормально выглядящим словом.
- **`confidence_claimed` сохраняется навсегда.** Калибровка считается по **паре**
  «заявлено / действует»: без заявленного не увидеть, что модель систематически
  завышает, без действующего — что её понижал код. Поле `confidence_key`
  осталось тем же, только теперь исправленным, поэтому телеметрия и личка
  получают верную оценку без правок.
- **Проверка домена формы — поиском по тексту таблицы «Домены», без списка
  соответствий.** Список «домен формы → домен реестра» живёт в двух местах
  (форма и сборщик) и разъезжается молча. Здесь достаточно факта: слова
  заказчика не встречаются в колонке «о чём вопросы». Промах этой проверки
  безопасен — она только называет задачу для базы и уверенность не трогает.

Дополнительно правило закрыто с двух других сторон: `prompts/author.md` получил
градации уверенности и правило «отсутствие данных в витрине, о которой не
спрашивали, ответом не является», а `prompts/router.md` — запрет угадывать
домен по одному общему слову и подставлять витрину вместо отчёта. Пустой домен
означает, что мастера не добираются вовсе, — то есть первопричина закрывается
в роутере, а понижение в коде остаётся страховкой.

### Самообслуживание: два разных гейта и чистка текста от шаблона формы

Часть выгрузок коллега делает сам — отчётом-трансформером «HR Executive —
Детальные списки». Кандидата находит **код** по таблице «Самостоятельные
выгрузки» в `kb/index.md`: совпадение ключевого слова — сигнал «предложить
отчёт», а не гарантия, что нужные атрибуты там есть (инвентарь полей отчёта
бот не видит и сверять его не должен).

Живой прогон из чата 2026-08-17 прошёл мимо отчёта на обращении, которое было
ровно про него: нужны логины сотрудников юнита по ссылке на my.tbank.ru —
дежурный на такой же вопрос ответил именно «Детальными списками». Разбор дал
две независимые причины, обе тихие.

**Первая: поиск отчёта стоял под темой формы, а в чате её нет.** `Adapter
Chat` передаёт `topic_kind` пустой строкой, и весь блок самообслуживания
в `Plan` не запускался вовсе. При этом `Build materials` режим выгрузки
**восстанавливал** по плейбуку среди прочитанного, и на выходе ядра стояло
`is_export: true` — по выходу отказ неотличим от нормальной работы.
Асимметрия «у режима фолбэк есть, у поиска отчёта нет» и была причиной.

Теперь тема восстанавливается из шапки обращения (`Cross Data | …`) — в чат
пост вставляют целиком. Но гейтов **два, и это не одно и то же**:

| | чем включается | что стоит на кону |
|---|---|---|
| режим выгрузки (`is_export`) | только тема — своя или из шапки | две статьи, правила в промпте автора, требование блока ТЗ |
| подсказка про самообслуживание | тема **или** слово «выгруз» в тексте | один объект в DD Lookup и блок в материалах |

Признак по всему тексту нельзя отдавать режиму: «необходимо завести запрос
на выгрузку» стоит в половине обращений с темой «Мне только спросить», и режим
включался бы там целиком. А подсказке — можно и нужно: в личке формы нет
вовсе, человек пишет «нужна выгрузка логинов моей команды», и не предложить
ему готовый отчёт значит завести задачу на аналитика там, где он справился бы
сам. `isAccess` запасного признака по тексту не получает вообще — слово
«доступ» стоит в подписи поля самой формы выгрузки.

**Вторая: совпадало служебное.** Единственным совпавшим словом было «фио»,
и не из запроса, а из варианта выпадающего списка чувствительности:
«Персональные данные сотрудников (неполное ФИО, логин, раб. почта, возраст,
master ID и др. внутренние ID)». Вариант одинаков во всех обращениях про ПДн,
то есть отчёт предлагался бы по шаблону формы в каждом втором. Ложное
совпадение хуже промаха: предложение, которое появляется всегда, перестают
читать.

Поэтому матчинг идёт по тому, что написал **человек**: из текста
выбрасываются шапка, любая строка, кончающаяся двоеточием, и всё в круглых
скобках. Скобки здесь главное, и это **не** то же самое, что «оставить
значения полей»: «фио» пришло именно из значения, а не из подписи. Правило
про двоеточие агрессивнее, чем `LABEL_RE` в guard'е (60 символов): guard
обязан не потерять значение, здесь надо не оставить подпись, а подписи формы
длинные — «Перечисли логины сотрудников, кому необходимо дать доступ
к выгрузке:» это 69 символов и содержит «логин», то есть совпадало бы
в каждой выгрузке. Цена правил: суть, написанная только в скобках, не
совпадёт — это промах, а не ошибка.

Ключевые слова при этом живут в `kb/index.md`, а чистка текста — в сборщике
бота, то есть в разных репозиториях. Чтобы они не разъезжались, контракт
описан прозой над самой таблицей: слова из служебного текста формы писать
туда бессмысленно.

На том же обращении после правки совпадает `логин`, `юнит`,
`my.tbank.ru/structure` — по какому слову отчёт попал в материалы, видно
в поле `self_service[].matched`: раньше «отчёт предложен» и «отчёт предложен
по слову из подписи поля» по выходу ядра не отличались никак.

Проверки — группа 22 в `test_pipeline.mjs`: то самое обращение целиком,
в двух формах входа (чат без темы и канал с темой — результат обязан
совпадать), плюс обращение, где своих слов из списка нет, а шаблонные есть.

### Что видит джун: ссылка вместо копии обращения и готовая задача для базы

Раньше сообщение в `~stonis_hakcs_2` печатало `'> ' + question`, то есть **весь
пост формы целиком** — рядом со ссылкой на тред. Чистое дублирование, и именно
оно разгоняло посты к лимиту 4000 символов, на котором падал `Post draft`.

Теперь вместо цитаты — шапка `**Тема** · @автор · [открыть тред]`, а под
черновиком три служебные строки и блок задач:

```
**Уверенность:** нет ответа ← бот заявил высокую
**Почему:** спрашивали про отчёт, отчёта в базе нет, а статьи под вопрос
            роутер не подобрал — читались только мастера домена
**Основание:** статей: 3 (только мастера домена, совпадения в реестре нет) ·
            метаданные: emart.mdm_employee_structure_d ·
            домен из формы: «Стоимость и расходы на персонал» →
            бот искал в: headcount-structure

**Задача для базы**
— нет статьи об отчёте budget-corporate-events → kb/reports/: указать,
  на какой витрине построен и кто владелец
— домен формы «Стоимость и расходы на персонал» не встречается в таблице
  «Домены» kb/index.md
— в реестре нет строки под этот вопрос: читались только мастера домена
```

- **`Основание` — это и есть ответ на «непонятно, как считается уверенность».**
  Видно было только слово, а не то, что за ним стоит.
- **Строка `←` печатается только при понижении.** В обычном случае это шум,
  при понижении — самое важное, что есть в сообщении.
- **Блок задач собран КОДОМ из фактов**, а не просьбой к модели. Блок
  `ЧЕГО НЕ ХВАТИЛО` от автора остаётся рядом: он хорошо называет отсутствующие
  сущности прозой, но пропускает то, чего сам не видел, — например что реестр
  ссылается на несуществующий файл.
- **В логе лички цитата ОСТАЁТСЯ**, в отличие от канала: ссылки на сообщение
  из лички нет, и без цитаты в приоритизацию попадёт «был вопрос» без вопроса.
  Но она обрезается до 300 символов, и обрезка называет потерю.
- **Стык «входы ядра ↔ что передают адаптеры» проверяется тестом.** n8n не
  падает на поле, которого нет в объявленных входах, — оно просто не доедет:
  поля формы приедут пустыми, уверенность не понизится, и по виду флоу это
  неотличимо от «всё в порядке». Поэтому после правки ядра адаптеры
  **обязательно** переимпортировать.

Проверки: тесты 25–27 в `test_adapters.mjs` (разбор формы в обеих формах
payload, понижение обоих уровней, задачи для базы, отсутствие цитаты
в канале), тесты 15–16 в `test_pipeline.mjs` (`router_articles` отдельно от
итога, факты про отчёт в материалах).

### Разбор фидбека аналитика 2026-08-26/27: четыре отказа, невидимых по логу

Аналитик поддержки оценил 49 живых обращений за 14–26 августа: полезными
черновик признан **дважды**, отрицательно — 42 раза. Разбор показал, что
формулировки почти ни при чём: в 24 случаях из 49 бот отвечал, **не видя
ни одного имени поля**, а ещё в части — уверенно отрицал существование
полей, которые в витрине есть. Ниже — что нашлось и что с этим сделано.
Общее у всех четырёх: по виду флоу и по логу они неотличимы от нормальной
работы, поэтому каждый прожил недели.

**1. Ветка каталога не выполнялась ни разу.** В n8n руками выключили ноду
`Collect articles`. Выключенная нода в n8n не пропадает — она **пропускает
данные насквозь**, поэтому в `Need DD` вместо плана приезжал ответ GitLab
по статье. Условие `$json.dd_count > 0` читало `undefined`, поток уходил
в ложную ветку, и `Call DD Lookup` не выполнялся. Условие `files.length > 0`
выполняется практически всегда (у выгрузок код сам добирает плейбук
и `rc-structure-choice`, при определённом домене — мастеров), так что
работающего пути просто не оставалось.

Маскировали отказ три слоя, и каждый работал как задумано: `dd_count`
в телеметрии — это **план** роутера, а не факт получения; понижение
уверенности срабатывало, но модель и так заявляла `medium`, поэтому
`confidence_capped` оставался `false`; а `try/catch` вокруг
`$('Call DD Lookup')`, написанный для честного «вопрос был не про поля»,
молча проглатывал «объекты запланированы, а узел не выполнился».

Сделано: `ddNodeRan` в `Build materials` разводит эти два случая,
`dd_never_ran` — отдельный флаг, `dd_received` — факт рядом с планом,
оба уезжают в телеметрию. Понижение при `dd_never_ran` — до **«нет ответа»**,
а не до средней: средняя читается как рабочий черновик. «Задача для базы»
в таком случае прямо говорит, что это поломка бота, и называет ноду.
Тест 9б в `test_pipeline.mjs`; тест 9 при этом пришлось починить — он
симулировал «каталог не ответил» через **неисполнившийся узел**, то есть
проверял ровно тот случай, который в проде и сломался, и был зелёным.

**2. Уверенное отрицание поля, которого не искали.** На вопрос «какое поле
хранит логин и есть ли рабочая почта» бот ответил, что рабочей почты
в витрине нет, сославшись на 289 полей. Поле `wrk_email_address_txt`
с описанием «Рабочая почта» там есть.

Причин две, и обе конструктивные. Роутер отдаёт **один hint на объект**,
а дедуп в `Plan` шёл по URN и выбрасывал вторую пару с той же витриной —
то есть «логин» и «почта» в одном вопросе были несовместимы by design,
и почту не искали вовсе. Вторая: полный список имён печатается только
в ветке «ничего не совпало», а здесь «логин» совпал; единственное, что бот
видел про остальные 288 полей, — строку «проверены 289 из 289», которая
относится к **фильтру**. Он прочитал её как «я видел все поля».

Цена высокая и незаметная: в режиме выгрузки на отрицании строится раздел
«Чего не будет», и заказчик узнаёт о пропавшем атрибуте после сдачи файла.
(Раздела с 2026-08-31 нет, но цена ошибки та же: поле, объявленное
несуществующим, просто исчезает из состава файла.)

Сделано: дедуп в `Plan` **склеивает** иглы вместо выбрасывания (объект один,
запрос один, фильтр — список до четырёх слов); `needlesOf()`/`matchesAny()`
в `COMMON_JS` сравнивают по списку игл и режут русские слова до основы
(`почты` → `почт`, иначе подстрока не совпадёт со склонением); блок
совпадений теперь **обязан** говорить, что показаны только совпавшие поля
и судить по нему об отсутствии другого понятия нельзя. В `prompts/author.md`
добавлен блок «отсутствие поля — это утверждение о факте», в
`prompts/router.md` — правило перечислять понятия через запятую. Тест 8д
в `test_shapers.mjs`. Живой прогон после правки: находятся и 8 login-полей,
и `wrk_email_address_txt`.

**3. Service Account разъехался между сборщиком и n8n.** В живых `DD Lookup`
и `Support Bot Core` стоял «…Service Account Support», сборщик выдавал
«…account 2»: credential тянулся из `Support Bot.json` — снимка первой
конструкции, который давно не трогали, и через него доезжал до ядра
(`GITLAB_CRED` берётся из ноды `Get a file` собранного `Support Bot DD`).
То есть один устаревший id в забытом файле разъезжался сразу по трём
воркфлоу, и первый же импорт уронил бы **и** каталог, **и** чтение статей
из GitLab по 401 — без единой правки кода.

Сделано: `DP_CRED` в `build_dd_flow.py` — единственное место, и нормализация
проставляет его **любой** ноде с `devplatformApi`, включая унаследованные
из исходника. Тест 32 в `test_adapters.mjs` проверяет не конкретный id,
а согласованность: во всех воркфлоу он один, и ядро читает GitLab тем же
аккаунтом, каким `DD Lookup` ходит в каталог.

**4. Причина средней уверенности была захардкожена.** В `DM_MSG_JS` на любую
среднюю печаталось «определение ещё не подтверждено» — формулировка правила
про `status: draft`. Ни одна прочитанная статья черновиком не была. Настоящая
причина при этом посчитана и лежит рядом, в `confidence_capped_reason`.
Придуманное объяснение хуже отсутствующего: его читают и перестают верить
всей строке, ради которой уверенность и считается. Сделано: понизил код —
печатается настоящая причина; заявила средней сама модель — говорим только
то, что знаем, без выдуманного повода. Блок `gaps` в личку не уходит: он про
пробелы базы и адресован джуну. Тест 33 в `test_adapters.mjs`.

**Общий урок, который дороже четырёх частных.** Три отказа из четырёх —
это **ручная правка в интерфейсе n8n**, разошедшаяся со сборщиком, либо
проверка, симулирующая не тот случай. Ни один не виден по виду флоу, и ни
один не ловится чтением кода на диске: диск был прав во всех четырёх.
Отсюда правило: при расследовании «бот отвечает странно» **первым делом
экспортировать воркфлоу из n8n и сравнить с диском**, а не перечитывать
сборщик. И второе: `prompt_version` — хеш только промптов, и отказ во флоу
он не видит в принципе; отсечку в логе он даёт лишь тогда, когда правились
именно промпты.

**Что фидбек аналитика говорит про базу знаний** — отдельно от поломок выше,
и это не обесценивается их починкой:

| Чего не хватило | Обращений из 49 | Состояние |
|---|---|---|
| Название отчёта по ссылке и его владелец | 11 | ждёт прогона `DD Recon` |
| Эксперт по теме (человек или канал) | 13 | **закрыто:** таблица «Маршруты» |
| Готовый отчёт вместо ручной выгрузки | 8 | частично: «Самостоятельные выгрузки» |
| Обязательное согласование ИБ при передаче вне контура | 4 | **закрыто:** правило по полю формы |
| «Такого у нас нет вовсе» (ЮЛ, госслужащие, размер одежды, корп. телефон) | 5 | `kb/process/no-such-data.md` не заведён |

Первые две строки — половина канала, и обе закрываются справочниками,
а не статьями. Оценки по выгрузкам при этом **нерепрезентативны**: 24 из 42
отрицательных бот получил без единого имени поля, то есть это был отказ
инфраструктуры, а не пробел базы. Переоценивать их надо по новому трафику.
А вот про отчёты не изменится ничего: `kb/reports/` пуста независимо от DD.

**Решение по реестру отчётов: владельцы берутся из DD, а не дублируются
в git.** Владелец — типичный инвентарь, он меняется без нашего ведома, и
скопированный в git протухнет молча (то же правило, что для состава полей,
`kb/process/metadata-sources.md`). Но связи между ключом ссылки Proteus
(`/dashboard/23466/`, `/dashboard/p/el8AZBZX5Zv/`,
`/dashboard/employee_ambassadorship/`) и ключом объекта в DD у нас нет,
поэтому в git остаётся **мост, и только мост**: `ключ ссылки | dd_urn`,
без названия и владельца. Он не протухает — меняется то, что лежит по URN.
`reportSlug()` в `build_time_flows.py` уже разбирает все три формы ссылки.
До стройки — разведка DD (`/related`, `/attribute`, `/markdown`, `/link`
на `urn:dd:reports:reports:report:1728`; `entityFields` не пробовать, он
с 2026-08-24 не отдаёт ни `summary`, ни `attributes`) и **сверка с эталоном**:
фидбек даёт готовые пары «отчёт → кого тегает аналитик» на 11 отчётах, и
по трём из них видно, тот ли человек приезжает из DD или технический
владелец ноутбука.

### Согласование ИБ — детерминированным правилом, а не просьбой к модели

Единственное поле формы, у которого цена ошибки — не «черновик получился хуже»,
а **файл с персональными данными, ушедший наружу без согласования**. В фидбеке
аналитика такой ответ стоял в 5 обращениях из 22 выгрузок, и в 4 из них
правильным ответом было «сначала заявка в `~sec_analytics_ask`». Правило было
отдано модели словами — и она его пропускала, ровно так же, как пропускала
лимит итераций и мастеров домена. Теперь признак считает код, по всей цепочке:

| где | что делает |
|---|---|
| `Guard channel` | разбирает ответ человека → `external_transfer`: `yes` / `no` / `''` |
| вход ядра | `external_transfer` объявлен наравне с остальными полями формы |
| `Build materials` | `ib_required` и **обязательный блок** в материалах автора |
| `prompts/export.md` | требование отдельной строкой под составом файла, без смягчений |
| `Parse answer` | `ib_stated` / `ib_missing` — дошло ли требование до черновика |
| сообщение джуну | строка `🔒` **первой**, раньше основания и источников |
| телеметрия | `external_transfer`, `ib_required`, `ib_missing` |

Решения внутри, каждое закрывает тихую ошибку:

- **Три состояния, а не булево.** «Не разобрано» и «остаётся внутри» — разные
  вещи, и подставлять второе вместо первого значит молча снять требование ИБ.
  Пустой признак при распознанной теме выгрузки печатается в материалы
  отдельной заметкой: форму переформулируют, разбор промахнётся, и молчание
  здесь неотличимо от «согласование не нужно».
- **Разбор по строкам, а не по `sections`.** Подпись поля — «Выгрузка нужна для
  использования исключительно внутри группы компаний:» — это 71 символ, а
  `LABEL_RE` в guard'е ограничен 60: в `sections` она не попадает вовсе и молча
  приклеивается значением к предыдущему полю. Поднимать лимит нельзя — длинный
  вопрос, кончающийся двоеточием, начал бы резать `question_text`.
- **Полярность выводится из подписи, а не угадывается по ответу.** Сейчас форма
  спрашивает «нужна исключительно внутри группы компаний», и «нет» там значит
  передачу наружу. Переформулируют в «данные передаются за пределы контура» —
  и то же «нет» будет значить ровно обратное. Подпись, из которой полярность
  не читается, даёт «не разобрано», а не догадку.
- **Уверенность эта проверка НЕ трогает** — как `draft_leaks` и
  `draft_too_long`. Основание под ответом от неё не зависит, а понижение
  испортило бы калибровку. Джун видит её первой строкой разбора: всё остальное
  в служебном блоке говорит, насколько черновику верить, а эта строка — что его
  нельзя отправлять как есть.
- **В личке и в чате заметки о неразобранном признаке нет.** Формы там нет
  вовсе, режим выгрузки восстанавливается по плейбуку среди прочитанного —
  и строка печаталась бы на каждой второй выгрузке. Строка, которая горит
  всегда, перестаёт читаться: ровно так «ФИО» из шаблона формы обесценило
  самообслуживание.

Проверки: группа 23 в `test_pipeline.mjs` (блок в материалах, тишина внутри
контура, промах разбора назван), группы 34–35 в `test_adapters.mjs` (разбор
в обеих формах payload, обе полярности, порядок строк в треде).

**Третий случай `\w` и `\b` по кириллице — и первый, который прошёл мимо
тестов.** Проверка `ib_stated` искала четыре формулировки, и две из них были
**мёртвым кодом**: `информационн\w*\s+безопасност` не совпадает с
«информационной безопасностью» **никогда** — в JS `\w` это `[A-Za-z0-9_]`,
после «информационн» стоит «о», для `\w*` она не подходит, а `\s+` её не
принимает. Держалась проверка на одной аббревиатуре «ИБ», то есть верный
черновик, где всё написано словами, получал ложную тревогу — то самое, чего
эта проверка задумана избегать.

Прошло это мимо тестов потому, что оба соседних случая прикрывали промах
**другими** альтернативами: один писал `~sec_analytics_ask`, второй —
«согласования ИБ». Формулировка без аббревиатуры и без имени канала
не проверялась вовсе. Теперь проверяется, в двух падежах.

Отсюда правило для этого проекта: **кириллический хвост слова пишется классом
`[а-яё]`, а `\w` и `\b` рядом с кириллицей не ставятся вообще.** Это уже третий
случай — `\bот\s+пользовател` в разборе шапки, `групп\w*\s+компан` в подписи
поля, теперь `информационн\w*`. Все три тихие, все три выглядели рабочими,
и ни один не ловится чтением кода: регулярка читается как верная.

### `DD Recon` — разведка каталога под реестр отчётов

Мост «ключ ссылки Proteus → `dd_urn`» строить нечем: **ни одной пары** у нас
нет, а руками их не добыть. Код матчинга в `Plan` по пустой таблице — это
код, который не работает и выглядит рабочим. Поэтому пары добываются машинно,
отдельным одноразовым воркфлоу (`build_dd_recon.py` → `DD Recon.json`).

Фазы, оставшиеся в прогоне после разбора его же результатов:

| | что спрашивает |
|---|---|
| **A** | Где у отчёта лежит владелец. Пять запросов по `urn:dd:reports:reports:report:1728`: `/related`, `/summary`, `/attribute`, `/markdown`, `/link` |
| **C**, **E** | Форма `POST /search/query`: тело запроса и что приходит в ответ |
| **D** | Три пробы Trino: видит ли аккаунт HR-витрины, кардинальность `emp_specialization_desc` и **чем отказ по недоступной таблице отличается от пустого результата** |

**Фазы B и F удалены**, причины записаны в шапке `build_dd_recon.py`.
B строила мост со стороны витрин — ни одна связь таблицы не отдала `REPORT`,
собралось ноль пар. F перечисляла отчёты каталога — и это оказалось
бессмысленно по существу: в DD лежат отчёты **всех команд компании**, их
десятки тысяч, и наших среди них не найти перечислением. Правильный метод —
поиск **по названию**, по одному запросу на отчёт, а список названий даёт
аналитик: он и есть первичный источник. Оставлять код, который не работает,
но выглядит рабочим, нельзя — это ровно то, из-за чего заведён сам `DD Recon`.

Решения:

- **Мост идёт со стороны витрин, а не поиском по названиям.** У таблицы есть
  подтверждённый живым запросом ключ связи `notes` — «ноутбуки и отчёты,
  читающие таблицу», и форма ответа `/related/{key}` известна. Тело
  `POST /search/query` (`SearchRequest`) на момент сборки не подтверждено
  ничем, и строить на нём единственный источник пар значило бы получить
  пустой результат, неотличимый от «отчётов в каталоге нет».
  **Это опасение оправдалось наполовину:** мост со стороны витрин не собрался
  вовсе (ни одна связь таблицы не отдаёт `REPORT`), а поиск как раз
  заработал — но узнать это удалось только пробами, потому что сервер
  на неверное тело отвечает 200. Схема пришла позже, из спецификации
  OpenAPI (файл `openapi` в корне), и записана в разделе «Поиск сущностей».
- **Проба поиска стоит в цепочке ради ответа сервера.** Ответит 400 — прогон
  не сломается, а текст ошибки обычно и называет ожидаемые поля. Это и есть
  дешёвый способ узнать форму тела.
- **`entityFields` не используется вовсе.** С 2026-08-24 он не отдаёт ни
  `summary`, ни `attributes` — ни у отчётов, ни у колонок.
- **URN витрин берутся из реестра, credential — из собранного `DD Lookup`.**
  Ни список, ни Service Account в сборщике не дублируются: скопированная копия
  разъезжается молча — то самое, из-за чего 2026-08-27 один устаревший id
  в забытом файле уронил бы разом каталог и чтение статей.
- **Ключи из фидбека — эталон, а не источник.** Они нужны ровно для одного:
  посчитать покрытие моста, сколько из 10 нашлось машинно. Сам мост строится
  из ответа каталога.
- **Code-ноды проверены прогоном** (`test_recon.mjs`): распаковка
  `entity` из ответа `/related` и удержание пары «объект ↔ его ответ» индексом.
  Оба промаха дают не ошибку, а **пустой результат** — на первом из них уже
  один раз молча получился пустой инвентарь колонок.

Воркфлоу ничего не вызывает по id и ничего не решает в проде: ручной триггер,
только GET плюс одна проба POST. Сделает своё дело — удаляется.

**Прогон выполнен 2026-08-27**, разбор — в разделе «Прогон разведки» ниже.
Таблицы «Отчёты Proteus» в `kb/index.md` по-прежнему нет: мост строится
из списка отчётов аналитика поиском по названию, а не перечислением каталога,
и до появления списка матчинг в `Plan` писать не по чему.

### Фаза D: значения полей — только из данных, и только через Trino

Перечня уникальных значений поля **в каталоге нет** — подтверждено владельцем
задачи, `samples` проверять незачем. А без значений бот не закрывает типовой
случай: заказчик говорит «BI-аналитики», фильтровать надо по
`emp_specialization_desc`, и какое там значение — «Бизнес-аналитик BI»,
«Аналитик BI» или иное — из каталога не видно. Живой прогон 2026-08-27 на этом
и остановился: поле бот назвал верно, значение — нет.

Так к двум уровням добавляется третий, по тому же признаку:

| | откуда | почему |
|---|---|---|
| имена и типы полей | DD | меняются без нашего ведома |
| **значения поля** | **короткий стабильный список — git, динамический — данные** | 13 значений `active_type_nm` лежат в `rc-field-synonyms`; специализации перечислять там нельзя по той же причине, по которой не перечисляем поля |
| гранулярность, джойны, запреты, формулы | git | в каталоге этого нет и не будет |

Фаза D отвечает на три вопроса, и все три — блокеры для стройки:

1. **Видит ли аккаунт 128 HR-витрины.** Он заведён под `dl.usr_cross_data`,
   а витрины лежат в `prod_v_emart`, и каталог Trino для них неизвестен.
   `SHOW CATALOGS` даёт список, если префикс окажется неверным.
2. **Кардинальность поля** — от неё зависит, нужен ли потолок и какой.
3. **Как выглядит отказ по недоступной таблице.** Это главное. Часть витрин
   до Trino не доехала, и «витрины здесь нет» обязано отличаться от «таких
   значений нет»: слитые в один диагноз, они отправят чинить не то — ровно
   как `ddFailed` и `ddMissing` до 2026-08-27. Поэтому третья проба —
   **намеренный промах** по несуществующей таблице: без него форму отказа
   взять неоткуда, а угаданный в коде разбор не сработает ни разу и будет
   выглядеть рабочим.

Решения, принятые заранее и не подлежащие пересмотру при стройке:

- **Значение выбирает АВТОР, а не код.** Список реальных значений уезжает
  в материалы, автор называет очевидное или оставляет вопрос заказчику.
  Автоподстановка «наиболее подходящего» — это `ilike '%аналитик%'`, который
  поймает и «Бизнес-аналитик BI», и «Системный аналитик»: запрос выполнится
  и вернёт неверные цифры молча. Тот же класс, что `рид` внутри «гибрид»,
  только цена выше.
- **Витрина не в Trino — это названное ограничение, а не молчание.** Код
  печатает заметкой: поле рекомендовано по описанию из каталога, конкретного
  значения мы не знаем. Просить эту оговорку у модели нельзя — такие она
  роняет первыми, как роняла требование согласования ИБ.
- **Канонический срез в запросе обязателен** (`last_day_flg = 1`): без него
  `select distinct` по витрине «сотрудник × день» — скан всей истории.
- **По ПДн значения не тянутся вовсе.** `distinct` по `full_nm` или
  `contact_main_phone_no` — это персональные данные в контексте модели,
  и нужен явный список полей, по которым можно.
- **Нода и credential Trino берутся из собранного `Telemetry Flush`**, а не
  дублируются в сборщике разведки: аккаунт и имена полей `CUSTOM.trino`
  подтверждены живым прогоном 2026-08-17, и вторая копия разъехалась бы молча.

Code-нода фазы разобрана прогоном (`test_recon.mjs`, группа 5): отказ, пустой
результат и невыполнившийся узел дают три разных строки, а не одну.

**Прогон 2026-08-27 — все три блокера сняты.**

| | |
|---|---|
| Сервер | `https://trino.dlh.t-infra.ru`, каталог по умолчанию `dl` |
| Витрина видна | `prod_v_emart.mdm_employee_structure_d` читается; префикс каталога писать не нужно — Trino резолвит её в `dl.prod_v_emart.…` сам |
| Значения | пришли: `Первая линия поддержки клиентов` — 13 484, ПДн среди них нет |
| Отказ по несуществующей таблице | **отличим**: `Table '…' does not exist`, то есть ошибка, а не пустой результат |

Последнее — главное: диагностика «витрины нет в Trino» строится на тексте
отказа, и явный список доступных витрин заводить не нужно. Копии, которая
протухала бы молча, не будет.

**Кардинальность прогоном НЕ измерена, и это важно не перепутать.** Узел вернул
800 строк при `LIMIT 200` — потому что пробы стояли цепочкой, а `SHOW CATALOGS`
отдал 4 строки, и следующий узел выполнился по разу на каждую. Цифра выглядит
правдоподобно и читается как «800 специализаций», хотя это 200 × 4. Починено
`executeOnce: true` на всех трёх пробах, и шейпер теперь прямо предупреждает,
что число строк упирается в `LIMIT` и кардинальностью не является.

Для конструкции это ничего не меняет: значений **не меньше 200**, то есть
полный список в материалы не отдать. Значит фильтр по слову заказчика
(`ilike '%слово%'`) — не оптимизация, а условие работоспособности.

### Прогон разведки: владелец нашёлся, мост — нет

Остальные три ноды того же прогона.

**Владелец в каталоге ЕСТЬ, а разведка отрапортовала, что его не видно.**
В `/attribute` отчёта лежат `report_developer`, `data_team`, `developers_team`,
`support_channel` — ни одно под регексп поиска владельца не подходило, и
`owner_hits` вышел пустым при том, что ответ владельца содержал. Тихий отказ
ровно того класса, от которого защищено всё остальное: искали по угаданному
списку слов и приняли промах списка за факт. Список расширен.

Следствие для реестра отчётов: **владельца в git дублировать не нужно**, он
берётся из карточки — как и предполагалось. Плюс `support_channel` отвечает
на вопрос «куда писать», которого мы даже не задавали.

**`/link` отдаёт ключ ссылки Proteus.** На `report:1728` —
`{"reports": {"url": ".../superset/dashboard/hr-executive-detail-employee"}}`.
То есть механизм моста «URN → ключ ссылки» подтверждён; неизвестно только,
как перечислить сами URN отчётов.

**Мост через связь `notes` не собрать — и лимит тут ни при чём.** 0 пар
из 1782, все проверенные — ноутбуки Helicopter. Причина конструктивная:
`notes` по построению отдаёт сущности типа `NOTE`, а дашборды Proteus это
тип `REPORT`. Совет «поднять `MAX_NOTES` и прогнать ещё раз», который печатал
шейпер, отправлял бы чинить не то — исправлено.

**Поиск отвечает 200 и молча игнорирует неизвестные поля.** Тело
`{"query": …, "limit": 20}` вернуло колонки чужих схем, то есть выдачу
по умолчанию. Расчёт на то, что 400 назовёт ожидаемые поля, не оправдался:
ошибки нет вовсе, и форму тела из ответа не узнать.

Отсюда **фаза E** — пять проб, отвечающих ровно на то, чего не хватило:

| | |
|---|---|
| `Table related` | ключи связей У ТАБЛИЦЫ и типы сущностей за ними. До сих пор брались из документации, и `notes` оттуда же. Ищем связь, отдающую `REPORT` |
| `Report sources` | `source_tables` отчёта — «на какой витрине построен», вторая половина вопроса, ради которого затевался мост |
| `Search base` / `Search text` / `Search searchText` | одно и то же тело с разными именами поля. Рабочее опознаётся тем, что выдача **отличается** от базовой без текста — по-другому его не отличить, раз сервер о неизвестных полях молчит |

### Эксперт по теме: самый большой пробел закрывается справочником

Есть доменные области, в которых экспертизы дежурного не хватает, и по флоу
зовётся тот, у кого она есть. В фидбеке аналитика за 14–26 августа так
решались **13 обращений из 49** — больше, чем у отчётов (11). Ответа в базе
на них нет и быть не может, а бот отвечал по витринам, потому что домен
формально определялся — тихий отказ ровно того класса, из-за которого
мастеров домена добирает код.

**Это НЕ переадресация и не «обращение не к нам», и формулировка «это ведёт
не CrossData» из кода, промптов и базы убрана целиком.** Часть экспертов
в таблице — сотрудники CrossData: обращение остаётся нашим, просто в этой
теме разбирается не дежурный. Часть адресатов действительно в других
командах, но отдельного признака для них нет — действие одно и то же,
а неверная формулировка звучала бы как отказ в помощи там, где мы помогаем,
то есть портила бы ровно те обращения, ради которых справочник и заведён.

Устроено как самообслуживание: таблица `## Маршруты` в `kb/index.md`, матчинг
кодом в `Plan`, блок в материалах автора, строка джуну в треде.

| | |
|---|---|
| `kb/index.md`, `## Маршруты` | `маршрут \| ключевые слова \| кому \| где \| проверено` |
| `Plan` | матч по очищенному тексту → `routes`, `routes_dropped` |
| `Build materials` | блок `ПОЗВАТЬ ЭКСПЕРТА ПО ТЕМЕ` |
| `prompts/author.md` | назвать эксперта обязан, но ответ им не заменять; «это не к нам» запрещено |
| сообщение джуну | строка `🧭` с экспертом, словом-совпадением и датой |
| телеметрия | `routes` — id'шниками, разрез «по каким темам звали эксперта» |
| `validate_kb.py` | `check_routes()`: дубли, пустые слова, пустой адресат, формат даты |

Решения, каждое закрывает тихую ошибку:

- **Гейта нет, в отличие от самообслуживания.** У отчётов-трансформеров гейт
  защищает от расхода: совпадение добавляет объект в `DD Lookup`, до
  тринадцати HTTP-запросов. Маршрут не стоит ничего — только строка
  в материалах, — а тема у него любая: «кто ведёт квоты» приходит и вопросом,
  и выгрузкой, и в личку, где формы нет вовсе.
- **Защита от ложного совпадения — не гейт, а сам список слов, и он выверен
  по выгрузке канала.** Маршрут срабатывает на 3 % строк (7 из 204), каждое
  срабатывание по адресу. Это и есть нужный порядок: строка, которая
  появляется в каждом втором ответе, перестаёт читаться.
  Проверка обязательна, потому что **совпадение идёт подстрокой** и на глаз
  этого не видно. По ней выброшены слова, которые кажутся очевидными:
  `рид` внутри «гибрид» и «юридический» — четыре ложных из четырёх; `оклад`
  внутри «доклад»; `фот` внутри «фото»; `найм` — это домен `movement`
  и наш ответ, а не подбор; `юрлиц` — «с разбивкой по юрлицам» наш вопрос
  про данные; `преми` совпало на C&B-отчёте, где верным адресатом был другой
  человек, а **неверное имя хуже отсутствующего**. Правило записано прозой
  над самой таблицей — она в другом репозитории, и разъезжаться контракту
  с кодом нечем только так.
- **Эксперт не заменяет ответ, и порядок в блоке обратный привычному.**
  Сначала сказано «не заменяет», и только потом названо имя: автор читает
  материалы сверху вниз, и увидев имя первым, напишет «идите к такому-то»
  даже там, где база отвечает. В фидбеке 8 обращений закрывались и ответом,
  и экспертом одновременно.
- **Человек и канал разводятся кодом, а не догадкой автора.** Человека зовут
  в тред обращения, в канал задаётся сам вопрос. Перепутать значит либо
  оставить коллегу ждать ответа в чужом канале, либо тегнуть человека там,
  где отвечает дежурная смена.
- **Уверенность эта проверка не трогает ни в одну сторону.** Эксперт — не
  пробел базы и не основание под ответом, а дополнительный факт.
- **Дата подтверждения обязательна и печатается ДЖУНУ, а не в черновик.**
  Маршрут — утверждение про человека, и оно протухает молча. Владельца отчёта
  мы для этого и не дублируем в git, а берём онлайн из DD; здесь взять
  неоткуда — объекта «кто ведёт квоты» в каталоге нет. Единственная защита —
  видимая дата, и валидатор её требует: строка без даты выглядит такой же
  рабочей, как свежая. В черновик дата не идёт: «напишите Иванову (маршрут
  проверен 26 августа)» — это служебное в черновике, запрещённое отдельным
  правилом.
- **Попадание адресата в черновик код НЕ проверяет.** Соблазн велик — рядом
  стоят три проверки, которые именно это и делают, — но померить нечем:
  в реестре «Kirill Seliverstov», а модель напишет «Кирилл Селиверстов»,
  «@k.seliverstov» или «Кириллу». Поиск подстроки дал бы ложную тревогу
  на верном черновике, то есть ровно то, чем едва не обернулась проверка
  согласования ИБ, — только там формулировок было три, а здесь их столько же,
  сколько падежей. Строка, которая горит на верном ответе, обесценивает
  и себя, и соседние: смотреть перестают на весь блок. Поэтому маршрут просто
  печатается джуну — независимо от того, воспользовался им автор или нет.
- **В телеметрию едут id, а не имена.** Имя в реестре меняется, id нет,
  и разрез «по каким темам звали эксперта» должен пережить смену человека.
- **Двух строк в таблице нет намеренно.** Согласование ИБ разбирается
  детерминированно по полю формы, и вторая копия требования в таблице
  разъехалась бы молча — причём именно та, у которой цена ошибки максимальна.
  «Встречи и календарь»: маршрут в фидбеке есть, имени нет, а строка без
  адресата ничего не решает — джун всё равно идёт спрашивать, кто это.

- **Строка признаётся маршрутом ПО ФОРМЕ, а не по тому, что лежит в секции:**
  пять колонок и дата в последней. В той же секции реестра живёт
  пояснительная таблица «какие слова выброшены и почему» — двухколоночная,
  и без проверки формы её строки разбирались бы маршрутами: `найм` стал бы id,
  а объяснение — списком ключевых слов, то есть маршрут срабатывал бы ровно
  на том слове, которое из списка выброшено. Прозу над таблицей правят чаще,
  чем код, и разъезжается это молча. Строка без даты не срабатывает вовсе:
  валидатор ругается на неё громко и до коммита, а парсер обязан не пустить
  в черновик маршрут, про который неизвестно, когда его подтверждали, —
  промолчать тут дешевле, чем тихо назвать уволившегося человека.

**Побочно закрыты две вещи, обе про границы таблиц.**

`rows('## Самостоятельные выгрузки', null)` читал до конца файла, и строки
новой таблицы разобрались бы как отчёты: id взялся бы из колонки `маршрут`,
`byTitle` дал бы фолбэк на сам id, и бот предлагал бы «самостоятельную
выгрузку» под названием «payroll». Граница поставлена, тест 24 держит её
прогоном — при снятой границе он краснеет.

И **проекция реестра больше не платит за таблицы, по которым решает код.**
`## Самостоятельные выгрузки` и `## Маршруты` роутеру не нужны: матч делает
`Plan`. Хуже расхода то, что модель, увидев их, может подставить id маршрута
в `plan.articles` как путь к статье. Отбрасываются **по заголовку**, а не
по номеру секции: порядок разделов может поменяться, смысл заголовка — нет.
Неизвестный заголовок остаётся — реестр растёт, и новая таблица должна
доезжать до роутера по умолчанию, а не пропадать молча.

`kb/process/routing.md` **перестал быть рыбой**: `status: active`, ни одного
плейсхолдера `‹…›`, раздел называется «Когда зовём эксперта», а не «если это
не к нам». Имена в него не переехали — он ссылается на таблицу
реестра, потому что копия имён разъехалась бы с ней молча. Порядок доступа
к отчёту (матрица прав → AD-группа → спец. роль на оргпортале → ставит
руководитель или HRBP → доступ на следующий день) записан из разбора
обращений. Таблица систем заполнена тем, что проверяемо, а колонка владельца
осталась пустой намеренно: владелец — инвентарь, он берётся из каталога.

### Разбор живых ответов 2026-08-27 (вечер): три отказа после включения маршрутов

Первые ответы бота уже с новой базой знаний. Формулировки к делу почти
не относятся — все три отказа про то, на чём построен ответ.

**1. Бот отрицал поле, глядя на метаданные, которых не получал.** Обращение
из инфобеза про телефоны подрядчиков. В служебном блоке стояло
`метаданные: 1728` — из каталога пришёл ровно ОДИН объект, отчёт. Инвентарь
витрины `mdm_employee_structure_d` не запрашивался вообще. При этом в ТЗ:
«в метаданных витрины `mdm_employee_structure_d` нет поля с мобильным
телефоном». Утверждение о факте, которого бот не видел; поле в каталоге есть
(`contact_main_phone_no`, «Личный основной номер телефона»).

Отчёт попал в план кодом (таблица самообслуживания), а витрину должен был
назвать роутер — и не назвал. Класс тот же, что фикс № 2 от 26/27 августа,
но вариант новый: там промахивался фильтр по уже полученному инвентарю,
здесь объект **не запрашивали вовсе**. Прежние понижения этот случай
не ловили: `dd_never_ran` про неисполнившуюся ноду, а тут нода отработала,
просто по другому объекту.

Починено в двух местах, и это ровно то же разделение, что у мастеров домена:

- **Инвентарь прочитанных витрин добирает КОД.** `Plan` строит карту
  «путь статьи → витрина» из реестра и добавляет `dd_urn` каждой витрины,
  чья статья уехала автору. Свойство конструкции, а не дисциплины роутера.
- **`hint` при доборе пустой намеренно.** Без фильтра приходит полный список
  имён полей одним запросом (289 имён ≈ 3 КБ), а не тринадцать запросов
  за описаниями. Дёшево и, главное, ПОЛНО — вопрос стоял «есть ли такое поле
  вообще». Угадывать фильтр за роутера значило бы то самое угадывание, от
  которого защищает документированное «промах фильтра возвращает инвентарь».
  Если роутер этот URN уже назвал со своим `hint`, он сохраняется: фильтр
  даёт ещё и описания.
- **Гейт: только выгрузка и просьба помочь с запросом.** Там состав полей —
  то, из чего собирается ответ: ТЗ перечисляет поля поимённо, `select` их
  пишет. На вопрос «что такое текучесть» отвечает статья, и полный список
  был бы 3 КБ шума и расхода на КАЖДОМ обращении.
- **Остаток называется.** Потолок `MAX_DD`, отказ запроса, неисполнившийся
  узел — витрина всё ещё может остаться без инвентаря. `Build materials`
  печатает такие витрины отдельной заметкой и прямо запрещает формулировки
  «в витрине нет поля X»; `Parse answer` понижает уверенность до средней —
  **только в режиме выгрузки**. На обычном вопросе понижать нельзя: статья
  отвечает и без инвентаря, а понижение сделало бы «среднюю» значением
  по умолчанию и обесценило сигнал, ради которого уверенность и считается.

**2. Режим выгрузки включался на просьбе написать запрос.** «Можешь
подсказать, как написать select, чтобы выгрузить сотрудника, его
управленческий юнит и его юнит из функциональной структуры?» — и бот выдал
три уточняющих вопроса, согласование состава полей и ТЗ. SQL не написал:
в режиме выгрузки он прямо запрещён. То есть на просьбу написать запрос
ответил «давайте сначала согласуем, что выгружаем».

Развилка здесь в том, ОТКУДА взялся режим: тема из формы — **факт**, её
проставил человек; восстановление по плейбуку среди прочитанного —
**догадка**, нужная в личке и чате, где формы нет. Признак «просят помочь
с запросом» (`select`, `sql`, `join`, «как написать», «как посчитать»,
«какой джойн») перебивает догадку и не трогает факт: заявка на файл со
словом «select» в тексте режим не теряет.

Слово «выгруз» признак намеренно не отменяет: «как написать select, чтобы
выгрузить» — это ровно тот случай, ради которого правило и заведено.

**3. `kb/process/sql-conventions.md` не доезжал до бота НИ РАЗУ.** Строк
`kb/process/` в реестре нет — роутер такие файлы не выбирает никогда, — а код
добирал по путям только плейбук выгрузки и маршрутизацию. То есть на вопрос
про запрос у автора не было ни одной статьи о том, как этот запрос положено
писать. Теперь добирается тем же признаком, что и всё остальное.

Отказ этот невидим со всех сторон сразу: файл лежит в базе, статус `active`,
ссылки на него из статей живые (`rc-field-synonyms` на него ссылается),
валидатор молчит — он сканирует только четыре папки сущностей. Поэтому
у регламентов появилось поле фронтматтера **`reached_by`**: `code` — путь
вписан в сборщик и добирается признаком обращения, `human` — файл только
для людей и для агента, правящего базу. `check_process()` в `validate_kb.py`
ругается на файл без этого поля. Проверить, что `code` не соврал, валидатор
не может — сборщик в другом репозитории, — но необъявленный файл он поймает,
а это ровно тот момент, когда ошибку ещё дёшево исправить.

**Что осталось невылеченным и почему.** В том же прогоне бот спросил «нужны
строки по сотрудникам или сводные цифры?» на обращении, где это написано.
Правило «не переспрашивай то, что заказчик уже написал» стоит в
`prompts/export.md` первым и с пометкой «главнее остальных» — и не сработало.
Кодом это померить нечем: «ответ на вопрос уже есть в обращении» —
суждение о смысле, и любая подстрочная проверка станет ложной тревогой
на верном черновике, то есть тем же, чем едва не обернулась проверка
согласования ИБ. Пока это единственный пункт разбора без решения
в конструкции.

**Про состав полей отчёта-трансформера** правило переписано: раньше промпт
запрещал утверждать, какие поля есть в отчёте («ни блок, ни ты этого
не проверяли»), и писалось оно, когда полей мы не видели. Владелец описывает
отчёт в каталоге сам, и там бывает перечислено, что доступно в фильтрах
и в выборе колонок. Теперь правило симметрично: перечислено — назови
и скажи, что есть; не перечислено — скажи, что состав из каталога не виден.
Догадка запрещена в обе стороны. **Живым прогоном не подтверждено**: несут
ли markdown-блоки отчёта список полей, из кода не видно, DD доступен только
из n8n.


**Продолжение того же дня: ещё два отказа, оба крупнее предыдущих.**

**4. Каталог вызывался ПАЧКОЙ, и разбирался только первый объект.** Живой
прогон: запрошено три объекта, пришёл один (`dd_received: 1`), а «Задача для
базы» советовала проверить URN в реестре и срок жизни Service Account — то
есть чинить не то.

У `executeWorkflow` значение по умолчанию — «Run once with all items», и `mode`
у ноды `Call DD Lookup` не задавался вовсе. Внутри `DD Lookup` все три шейпера
читают вход через `$('When called by agent').first().json`: при вызове пачкой
субворкфлоу разбирает **первый** объект и молча возвращает один `dd_meta`
на сколько угодно запрошенных.

Отказ прожил всё время существования конвейера и не виден ниоткуда: с одним
объектом в плане он не проявляется вовсе, а Code-ноды тестируются на подставном
`.all()` и до режима вызова не достают. `AGENTS.md` при этом утверждал, что
«`Call DD Lookup` выполняется по разу на объект» — это было решением, а не
фактом, и в собранном флоу оно не выполнялось. Теперь `mode: "each"`, и
тест 38 в `test_adapters.mjs` держит связь: пока шейперы читают вход через
`.first()`, режим обязан быть поштучным.

Заодно разведены два диагноза, которые сливались в один список: `ddFailed` —
каталог ответил, но метаданных не дал (чинится URN или Service Account);
`ddMissing` — объект **не доехал** до вызова (чинится режим ноды в n8n).
Слитые вместе, они отправляли чинить не то.

**5. Пустой план роутера читался как «в базе нет ответа».** Вопрос «где взять
инфу о количестве биай аналитиков в стриме дата 15 грейда в юните human
capital origination»: роутер вернул пустые `domains` и `articles`, мастера
поэтому не добрались, материалов не было вовсе — и код честно понизил до
«нет ответа». А ответ в базе есть: это обычная численность с фильтрами,
и считается она по мастер-витрине сотрудников.

Пустой план — это отказ **роутера**, а не пробел базы, и выдавать одно
за другое нельзя. Починено с двух сторон:

- **Данными.** Слова заказчика в таблице «Домены» дополнены по выгрузке
  канала: `грейд` (18 обращений), `специализация` (16), `юнит` (11),
  `должность` (9), `табельный номер` (7), `стрим` (5) — ни одного из них
  в описании доменов не было, а `ГПХ`, `подрядчики`, `аутсорсинг` добавлены
  в `legal`. Слова взяты из живого трафика и посчитаны по нему, а не
  придуманы.
- **Конструкцией.** Роутер не назвал НИ домена, НИ статьи — код добирает
  витрину по умолчанию. Догонять дыры роутера словами это гонка без конца,
  страховка нужна одна.

Решения внутри:

- **Витрина по умолчанию выводится ИЗ РЕЕСТРА** — сущность, назначенная
  мастером в наибольшем числе доменов. Своя константа в сборщике была бы
  четвёртым местом, где живёт одно знание. Тест 27 пришпиливает вывод
  к `t-emp-structure`: реестр изменится так, что умолчание переедет, — тест
  покраснеет, и решение примет человек.
- **Условие узкое:** только когда пусто И то, И другое. Одного домена
  достаточно, чтобы мастера добрались сами.
- **Подмена названа автору прямым текстом** — «под вопрос не подбиралось
  ничего, эта витрина добрана по умолчанию; не отвечает — так и скажи,
  и не пересказывай её вместо ответа». Без этого автор получает полноценную
  статью и отвечает по ней уверенно: ровно отказ 2026-08-11, только там
  мастера хотя бы соответствовали названному домену.
- **Уверенность понижается до средней**, а не до «нет ответа»: материалы
  есть и могут оказаться по теме, но основания «роутер нашёл это под вопрос»
  нет ни на грош.
- **`router_empty` уезжает в телеметрию.** Доля пустых планов — метрика
  качества роутера, и мерить её надо с первого дня: задним числом «роутер
  промахнулся» и «в базе нет ответа» по логу неразличимы.


**6. Черновик назвал эксперта, которого код не подбирал.** На том же вопросе
про BI-аналитиков бот написал «Подключу в тред @Artur Mermovich». Ни одно
ключевое слово маршрута на этом тексте не срабатывает: про деньги там нет
ничего, `стрим` и `грейд` — поля ультраширокой витрины, `юнит` — управленческая
структура, и весь ответ собирается из одной витрины. Прогон текущего сборщика
на точном тексте вопроса даёт `routes: []` — то есть на диске этого поведения
нет, и живой флоу или база на инстансе разошлись с диском (то самое правило:
при странном ответе первым делом экспортировать воркфлоу и сравнить).

Причина, впрочем, вторична: правило промпта «эксперта ОБЯЗАН назвать» читалось
в отрыве от условия «когда блок есть в материалах», и на пустых материалах
модель дописала правдоподобное имя. Неверное имя в треде видит **заказчик**,
и цена такой ошибки выше, чем у неполного ответа.

Закрыто с двух сторон:

- **Промпт получил явный отрицательный случай.** Блока нет — называть чьё-либо
  имя запрещено вовсе: ни подключить в тред, ни «спросите у такого-то»,
  ни @-упоминание. Правило «обязан назвать» действует только при наличии
  блока, и это сказано прямо, а не подразумевается.
- **Код мерит и называет.** `Plan` отдаёт `route_names` — ВСЕ адресаты таблицы,
  не только совпавшие; `Parse answer` ищет в черновике имя из таблицы, которое
  под этот вопрос не подбиралось, и джун видит строку `🚩` первой, раньше
  маршрута и основания. Уверенность проверка не трогает — как `draft_leaks`
  и `ib_missing`: основание под ответом от этого не меняется.

Проверка узкая **намеренно**: ищутся только имена из таблицы маршрутов.
Придуманное с нуля имя она не поймает — померить это нечем, — зато у неё нет
ложных тревог, а общий поиск `@` по черновику их дал бы (в шапке intake-формы
автор обращения тоже написан через `@`). Тот же выбор, что с проверкой
попадания адресата в черновик: лучше точная проверка узкого случая, чем
широкая, на которую перестанут смотреть.

**Заодно про базу.** `юнит` не был алиасом ни у одной сущности, хотя
`rc-find-unit-level` — это ровно «как найти уровень и ключ подразделения».
Добавлено в реестр и во фронтматтер: вопрос «в юните X» теперь ведёт
к рецепту, а не в пустоту.


### Проверка значений стоит ПОСЛЕ автора, а не до него

Правило разделения источников имеет третий уровень. Оно то же самое:
**берём там, где живёт, а не там, где удобно переписать.**

| | откуда | почему |
|---|---|---|
| имена, типы, описания полей | каталог DD | меняются без нашего ведома |
| **значения полей** | **сами данные, через Trino** | перечня уникальных значений в каталоге нет вовсе — подтверждено владельцем задачи |
| гранулярность, джойны, запреты, формулы | git | в каталоге этого нет и не будет |

Живой прогон 2026-08-27 остановился ровно здесь: поле бот назвал верно
(`emp_specialization_desc`), а какое в нём значение — «Бизнес-аналитик BI»,
«Аналитик BI» или иное — сказать не смог. Заказчику от такого ответа толку
нет: фильтр он написать не может.

**Две первые конструкции стояли ДО автора и обе провалились по одной
причине.** Сначала слова заказчика раскладывались по полям перебором —
каждое слово в каждое поле; в запрос уехало `legal_unit_nm LIKE '%аналит%'`
и `LIKE '%15%'`. Потом раскладку отдали отдельному вызову модели внутри
`DD Lookup` — и он раз за разом отправлял искать «юнит» в ЮРИДИЧЕСКОЙ
структуре вместо управленческой.

Причина у обоих одна, и она не в качестве раскладки: **у узла внутри
каталога есть имена и описания полей, но НЕТ СТАТЬИ.** Выбор между
`mapped_management_unit_nm` и `legal_unit_nm` делается по правилу из
`rc-structure-choice`, а по описанию поля эти два одинаково похожи на
«юнит». Автор в это же самое время выбирал верно — у него статья, рецепт
и инвентарь разом. Знание было, просто не в том месте.

Поэтому проверка переехала туда, где контекст уже собран:

```
Parse answer → Build check SQL → Need check ─нет→ Final answer
                       └да→ Check values → Check result
                            → Revise draft (LLM) → Parse revised → Final answer
```

Код собирает пары «поле = значение», идёт в данные, автор переписывает
черновик с реальными значениями.
**Проходов ровно два, и это видно по схеме флоу, а не по счётчику итераций.**

### Решение «проверять ли» принимает КОД, а не автор

Первым гейтом был блок `ПРОВЕРИТЬ ЗНАЧЕНИЯ`: нет блока — нет проверки.
Живой прогон 2026-08-28 показал цену. Бот выдал готовый SQL с фильтром
`emp_specialization_desc = '…'`, **сам написал в «Чего не хватило», что
точное значение не проверено и нужен `select distinct»**, — и блок
не поставил. В логе осталось `check_reason: «автор не просил проверять
значения»`: узел зелёный, ветка честно пропущена, и по виду прогона
отказ неотличим от нормы.

Модель знала, что проверить надо, и всё равно не попросила. Это четвёртый
случай того же класса — мастера домена, лимит итераций, согласование ИБ, —
и лечится он так же: переносом решения в код, а не усилением формулировки.

Границу это НЕ двигает. Выбор поля по-прежнему за автором: только у него
статья и рецепт, и он уже сделал этот выбор, написав фильтр в черновике.
Код не выбирает поле — он не даёт сделанному выбору остаться непроверенным.

| | откуда берётся |
|---|---|
| **какое поле** | автор: фильтр в черновике либо блок `ПРОВЕРИТЬ ЗНАЧЕНИЯ` |
| **проверять ли** | код: есть строковый литерал в фильтре — проверяем |
| **как запрашивать** | код: срез, потолки, запрет на ПДн |

Решения внутри:

- **Источник пар — САМ ЧЕРНОВИК.** Строковый литерал в условии это
  утверждение о данных: заказчик скопирует запрос и получит ноль строк,
  если значение записано иначе. Блок автора остаётся вторым каналом —
  им просят проверить то, чего в черновике ещё нет.
- **Числа не берём.** Ошибаются на справочниках, которые ведутся словами,
  а `grade = 13` стоил бы лишнего скана витрины на каждом обращении.
- **Список `IN` разбирается целиком.** Проверить первое значение и
  промолчать про остальные значит назвать проверенным то, что не проверяли.
- **Пара из двух источников не удваивает запрос** — дедуп по «поле+значение».
- **Причина пустой проверки больше не сваливает вину на автора.**
  «В черновике нет фильтров по значению» и «пары были и не прошли отбор» —
  разные вещи, и вторая перечисляет, что именно отсеялось и почему.
- **Неподтверждённое значение понижает уверенность до средней.** Проверка
  запускается ровно там, где ответ утверждает что-то о данных; если запрос
  отказал или строк не вернул, «высокая» относится к значению, которого
  никто не видел. До «нет ответа» не понижаем: поле названо верно, статья
  прочитана, не подтверждено одно звено.
- **Автору прямо запрещена оговорка «уточните через `select distinct`».**
  Фильтр из его черновика проверяется, и такая оговорка либо окажется
  неверной, либо продублирует строку, которую печатает код.

**Точное совпадение не подменяется похожим — и это отдельное решение.**
Живой прогон 2026-08-28: заказчик спросил продуктовых аналитиков, в поле
есть и «Продуктовый аналитик» (685 строк), и «Продуктовый аналитик (DA)»
(806). Обе строки `matched`, сортировка шла по частоте — и вариант с (DA)
встал ВЫШЕ точного совпадения. Автор взял первую строку и подставил
в фильтр не то, что сам же написал в первом проходе: **проверка заменила
верное значение на неверное**, то есть сработала хуже, чем её отсутствие.

Причины конструктивные, и их три:

- **Частота — плохой признак правоты.** У длинного варианта людей может
  быть больше просто потому, что это отдельная многочисленная роль.
  Теперь в запросе есть признак `exact_hit` (сравнение с целой фразой),
  и `ORDER BY exact_hit DESC, matched DESC, cnt DESC` ставит дословное
  совпадение первым независимо от количества строк.
- **В блоке для автора три уровня, а не два.** Точное совпадение — это
  не «одно из совпавших», а подтверждённый данными выбор, который автор
  уже сделал. Похожие значения печатаются под явным «В ФИЛЬТР НЕ СТАВЬ,
  но НАЗОВИ коллеге»: «(DA)», возможно, тоже нужен, и решает это
  заказчик, а не бот. Молча подставить похожее вместо точного — значит
  подменить проверенное непроверенным.
- **Правка сохраняла устаревшую оговорку.** Промпт второго прохода велел
  «всё остальное оставь как было», и фраза «точное написание нужно
  подтвердить через `select distinct`» пережила проверку, которая ровно
  это и подтвердила. Теперь вычистить её — отдельное правило правки.

`check_exact` уезжает в телеметрию отдельно от `check_rows`: «данные
ответили» и «ответ был тот самый» — разные вещи, а доля дословных
подтверждений показывает, насколько автор угадывает написание с первого
раза. Тест 38 в `test_pipeline.mjs` держит весь кейс целиком.

**Черновик — это markdown, а не чистый SQL.** Живой прогон 2026-08-28,
второй за день: автор не стал ставить значения в запрос, а вынес их
списком в текст — `` - `emp_specialization_desc` = 'GO разработчик' `` —
то есть сделал ровно то, что от него требуется. Проверка всё равно
не запустилась: имя поля обёрнуто в обратные кавычки, а регулярка
допускала между именем и оператором только скобку и пробелы. В логе
осталось «в черновике нет фильтров по значению» — по логу это выглядит
как «проверять было нечего».

Разметка теперь снимается ДО разбора, а не описывается в регулярке:
список того, чем модель может обрамить имя поля, открыт, и гнаться за ним
регуляркой значит проигрывать заново каждый раз. Кавычки у значения тоже
принимаются любые — одинарные, двойные, ёлочки: пропустить пару из-за
кавычки значит не проверить значение, названное прямым текстом.

**Подчёркивание при этом НЕ снимается, и это не мелочь.** Оно и разметка
курсива, и часть каждого имени поля: общая чистка `[`*_~]` превратила
`emp_specialization_desc` в три слова, в отбор ушло `desc`, и причина
стала «нет в инвентаре». То есть чистка разметки съела ровно то, ради
чего разбор и делается. Поймано прогоном, а не чтением: регулярка
читается как верная. Тест 39 в `test_pipeline.mjs`.

**Доспрос: автор уже знает, чего не хватило — надо просто спросить.**
Пары код достаёт из свободного текста, и промах разбора был тихим дважды.
Но ответ всё это время лежал рядом: в «Чего не хватило» автор прямым
текстом пишет, какие значения не проверены — «точное написание „GO
разработчик“ и „Краснодар“ в данных неизвестно». Выбрасывать это
и догадываться по разметке расточительно.

Поэтому там, где разбор промахнулся, а автор признался, задаётся ОДИН
узкий вопрос: назови пары «поле = значение». Не «перепиши ответ» —
только пары; ответ разбирается кодом и уходит во второй экземпляр
сборщика, дальше путь общий с обычной проверкой.

- **Доспрос РОВНО ОДИН, и это свойство графа, а не счётчика.** Обратной
  связи из `Need check after ask` в первый сборщик нет по конструкции:
  цикл «пока не найдёт» вернул бы счётчик итераций, от которого ушли
  вместе с tool-loop. Два прохода видны по схеме флоу, три — уже нет.
  Тест в группе 40 проверяет именно отсутствие обратного ребра.
- **Гейт узкий.** Без признания автора доспрос не запускается вовсе,
  и при найденных парах тоже: лишний вызов модели на каждом ответе,
  где значений и не было, не нужен.
- **Сборщик ставится ДВАЖДЫ одним текстом** — как `Parse answer`
  и `Parse revised`. Пары берутся из входа, черновик всегда у
  `Parse answer`: он один на оба прохода, и вторая копия кода
  разъехалась бы молча.
- **«Спросили и не назвал» — отдельный диагноз.** После доспроса это уже
  не поломка разбора, а «бот посмотрел второй раз и проверять не нашёл
  чего», и джуну говорится именно это: значения всё равно неподтверждённые,
  но чинить надо промпт автора, а не разбор. `check_retried` в телеметрии
  разделяет эти два случая.

**Промах разбора пар объявляет себя сам.** Пары код достаёт из свободного
текста модели, и каждый промах до сих пор был ТИХИМ: сначала гейтом был
блок автора («автор не просил проверять значения»), потом имя поля
в обратных кавычках («в черновике нет фильтров по значению»). Оба раза
в логе стояла честная причина, и оба раза она читалась как «проверять было
нечего» — отличить одно от другого можно было только открыв прогон в n8n.

Гнаться регуляркой за очередной формой разметки — проигрышная гонка:
список того, чем модель может обрамить пару, открыт. Поэтому ловится само
ПРОТИВОРЕЧИЕ: автор в «Чего не хватило» пишет, что написание значения
неизвестно, а `check_asked` при этом ноль. Значит разбор промахнулся —
и это поломка бота, а не пробел базы, что джуну и сказано прямым текстом
вместе с причиной, которую записал код. `check_missed` и `check_reason`
уезжают в телеметрию: разбивка по причине и есть список того, что чинить.

**Устаревшая оговорка мерится кодом.** Запрет писать «уточните через
`select distinct`» стоит в промпте автора и всё равно роняется — тот же
прогон дал эту фразу трижды в одном ответе. Условие узкое намеренно:
оговорка считается устаревшей ТОЛЬКО когда проверка реально подтвердила
значения. Не проверяли или проверка отказала — совет коллеге уточнить
самому остаётся верным, и джуна тревожить незачем. `draft_stale_caveat`
уезжает в телеметрию: доля не падает — значит правило надо усиливать
не формулировкой.

Проверки: группы 34–35 в `test_pipeline.mjs` (тот самый живой кейс целиком,
формы `=` / `IN` / `lower(…) LIKE`, оба фильтра ПДн), группа 51
в `test_adapters.mjs` (понижение и его причины).

Решения, каждое закрывает тихую ошибку:

- **SQL пишет КОД, а не модель.** Канонический срез `last_day_flg = 1`,
  запрет тянуть ПДн и потолки строк — свойства кода; если запрос начнёт
  писать модель, они перестанут быть гарантиями и станут пожеланиями.
  Тот же довод, по которому мастеров домена добирает код, а не промпт.
  Граница: **ЧТО проверять — решает автор, КАК запрашивать — код.**
- **Имя поля сверяется с инвентарём.** Придуманное имя — это либо ошибка
  Trino, либо, хуже, обращение к полю, которое мы намеренно исключили как
  персональное. Ответ модели здесь данные, а не команда.
  Но **подчёркивания в имени НЕ требуется**: `grade` — настоящее поле
  и самое частое слово в живом трафике (18 обращений), а по правилу
  «идентификатор обязан содержать `_`» оно молча объявлялось бы выдуманным,
  и отсев отправлял бы джуна править реестр, где всё верно. Направление
  послабления выбрано по цене промаха: лишнее имя стоит одной ошибки Trino,
  которая приезжает в `check_failed` и прямо запрещает автору что-либо
  утверждать; пропущенное имя тихо выключает проверку целиком.
- **Второй проход — ПРАВКА, а не новый ответ.** Ему не нужны материалы
  целиком: только вопрос, свой же черновик и то, что вернули данные. Полный
  второй вызов автора стоил бы ещё ~18k токенов, правка стоит ~5k.
- **Пять исходов звучат по-разному**, потому что чинятся в разных местах:
  значения нашлись; не совпало ничего; запрос отказал; строк нет; узел
  не выполнялся. Слитые в один диагноз, они отправляют чинить не то — ровно
  как `ddFailed` и `ddMissing` до 2026-08-27.
- **ЗАПРОС НА ПОЛЕ, а не один `UNION` на все.** `UNION` покупал «один
  HTTP-вызов» дорого: типы всех полей сводились к общему через `CAST`,
  потолок на поле требовал оконной функции, а отказ одного поля ронял
  выдачу по всем остальным. Соседние узлы того же флоу и так выполняются
  по разу на КОЛОНКУ — четыре запроса к Trino на этом фоне не стоят ничего.
  Запрос стал плоским: `GROUP BY` по полю, признак `matched` в `SELECT`,
  `ORDER BY matched DESC` — и **потолок строк не может выбросить искомое**,
  потому что совпавшее поднято сортировкой.
- **ФИЛЬТР ПО СЛОВАМ НЕ В `WHERE`, а признаком над группировкой.** Здесь
  была ошибка в расчёте стоимости: `GROUP BY` и так идёт по всему срезу,
  а фильтр режет только ВЫДАЧУ. То есть словарь значений поля стоит ровно
  столько же, сколько отфильтрованный список, — а платили за это тем, что
  промах слов давал ноль строк и ответ «таких значений нет» при живых данных.
- **СПРАВОЧНИКИ ВЕДУТСЯ ПО-АНГЛИЙСКИ, А СПРАШИВАЮТ ПО-РУССКИ.** Стрим
  в витрине называется `Data`, заказчик говорит «Дата» — кириллица
  с латиницей не совпадает никогда, и стемминг тут не поможет. Поэтому
  **потолок словаря зависит от исхода**: при совпадениях словарь это фон
  и шести значений хватает, без совпадений словарь И ЕСТЬ ответ, и резать
  его значит спрятать искомое — печатается до 60. Автору прямо сказано
  искать в перечне по смыслу, а не по буквам.
- **В TRINO НЕТ `ILIKE`.** Живой прогон 2026-08-28 ответил «mismatched
  input `ILIKE`»: это оператор Postgres и Greenplum. Регистронезависимость
  делается через `lower()` на колонке. Тест 47 в `test_adapters.mjs`
  сканирует весь собираемый SQL на синтаксис Postgres и сам проверен
  на той регулярке, что сломалась.
- **Слово режется до основы РОВНО ОДИН РАЗ.** Стемминг не идемпотентен:
  «аналитик» → «аналит» → «анал», четыре буквы, которые совпадут с чем
  угодно. Слова хранятся сырыми, основа считается при сборке SQL.
  Фраза при этом ищется и целиком, и по словам: точное совпадение ценнее
  приблизительного, а альтернативы в OR ничего не теряют.
- **ПДн не тянутся никогда, и фильтров два** — список имён и признак
  `sensitivity` из карточки колонки: признак в каталоге может быть
  не проставлен, а поле всё равно персональное.
  **До 2026-08-28 здесь не было НИ ОДНОГО, хотя этот абзац обещал оба.**
  Пока пары приходили только из блока автора, дыру прикрывала дисциплина
  модели, то есть ничего; после переноса решения в код запрос
  `select distinct full_nm …` собрался бы САМ, без чьего-либо решения.
  Записанная гарантия, которой нет в коде, хуже отсутствующей: на неё
  ссылаются вместо того, чтобы её проверить.
- **`_nm` — это название чего-то, а не имя человека.** В списке ПДн стояло
  голое `nm`, и под фильтр попадало КАЖДОЕ поле с этим суффиксом — то есть
  ровно те, ради которых ветка и заведена. Персональным считается поле
  про ЧЕЛОВЕКА: контакты, документы, дата рождения, логин, адрес.
- **Пустой результат НЕ должен ронять прогон.** n8n останавливает выполнение,
  когда нода вернула ноль элементов, — а ноль строк здесь нормальный исход.
  Живой прогон 2026-08-28 («No output data returned») показал цену: шейпер
  не выполнился вовсе, и бот остался без инвентаря при полностью
  отработавшем каталоге. То есть ветка значений, задуманная как дополнение,
  **отбирала основной ответ**, и по виду прогона это выглядело успехом.
  Лечится `alwaysOutputData: true`. Теперь тот же флаг стоит на `Check values`,
  и цена ошибки там выше: автор уже отработал и токены уплачены.
- **Таймаут интерактивный, а не батчевый.** Нода и credential Trino берутся
  из собранного `Telemetry Flush` — аккаунт и имена полей `CUSTOM.trino`
  подтверждены живым прогоном 2026-08-17, и вторая копия разъехалась бы
  молча. А вот ЗНАЧЕНИЕ таймаута оттуда не годится: у крон-перелива
  в запасе четверть часа, здесь человек ждёт ответа в чате, и зависший
  запрос выглядел бы как «бот промолчал». Наследуется ключ, а не число.
- **Общий финал обязателен.** Сабворкфлоу возвращает вызывающему данные
  ПОСЛЕДНЕГО выполненного узла. Без узла `Final answer` на ветке «проверять
  нечего» адаптер получил бы служебный элемент `Need check` вместо
  разобранного ответа — и в канал уехал бы пустой черновик при зелёном
  прогоне. Тест 48 в `test_adapters.mjs` держит единственность терминального
  узла.
- **Джун видит строку `🔢`, и она печатается ТОЛЬКО когда проверка была.** Без неё подтверждённое данными значение и придуманное
  выглядят в треде одинаково, а разница между ними — это разница между
  верной цифрой и молча неверной. Строка, которая горит на каждом
  обращении, перестаёт читаться: ровно так «ФИО» из шаблона формы
  обесценила подсказку про самообслуживание.
- **Роутер значения БОЛЬШЕ НЕ ВЫДЕЛЯЕТ.** Поле `values`, счётчик
  `values_asked` и блок правил в `prompts/router.md` удалены целиком.
  Оставлять их «на всякий случай» значило бы держать код, который
  не работает и выглядит рабочим, — и платить за него токенами на каждом
  вопросе. Тест 28 в `test_pipeline.mjs` держит отсутствие пути.

Проверки — группы 32–33 в `test_pipeline.mjs` (сборка запроса и пять
исходов), 48–50 в `test_adapters.mjs` (проводка, общий финал, строка джуну).


### Активная численность — умолчание любого запроса по сотрудникам

Витрина сотрудников хранит и уволенных. Запрос без фильтра активности
выполнится, вернёт правдоподобное число и будет **молча завышен**: ошибка
не падает, не выглядит странно и заказчиком не замечается никогда — просто
людей больше, чем есть. Поэтому правило звучит как умолчание: если человек
прямо не просит всех, включая уволенных, фильтр обязателен.

Обратное так же важно: там, где спрашивают про увольнения, отток, текучесть,
приём или динамику за период, фильтр НЕВЕРЕН — он выбрасывает ровно тех,
про кого вопрос.

Закрыто с трёх сторон, и это тот же порядок, что у мастеров домена:

| | |
|---|---|
| `Plan` | добирает `m-active-headcount` на просьбе про запрос и на выгрузке — по id из реестра |
| `prompts/author.md` | правило умолчания и обратный случай |
| `Parse answer` | `draft_no_active_filter` — мерит, поставлен ли фильтр |
| сообщение джуну | строка `🚩` с условием целиком |
| телеметрия | доля запросов без фильтра |

Решения внутри:

- **Формула НЕ дублируется в сборщике** — ни кодом, ни комментарием.
  Правила расчёта живут в git, и вторая копия разъезжается молча. Код
  отвечает за то, чтобы статья доехала, и за то, чтобы измерить результат.
- **Единственная копия — в проверочном запросе**, потому что там SQL пишет
  код. И она **сверяется со статьёй тестом**: обе стороны лежат на диске,
  формула вынимается из блока ```sql``` статьи и сравнивается с условием
  в узле. Изменится формула в базе — покраснеет тест, а не прод. Тот же
  приём, что двусторонняя сверка `reached_by`.
- **Проверочный запрос тоже смотрит на активных.** Словарь значений
  собирается по тем же строкам, по которым заказчик будет считать: иначе
  значение, встречающееся только у уволенных, приедет автору как живое,
  и фильтр из черновика вернёт заказчику ноль строк.
- **Применяется, только если оба флага есть в инвентаре.** У другой витрины
  их может не быть вовсе, и запрос упал бы на несуществующем поле.
- **Оба условия обязательны, одного мало.** Проверка требует именно двух:
  половина правила по виду черновика неотличима от целого.
- **Уверенность проверка НЕ трогает** — как `draft_leaks` и `ib_missing`.
  Escape по словам («уволилось», «отток», «текучесть», «найм», «динамика»,
  «включая») сделан в сторону молчания, и всё же он про смысл, а не про
  факт: понижение на верном черновике испортило бы калибровку, ради которой
  уверенность и считается. Джун видит строку и решает сам.
- **Код НЕ дописывает фильтр в черновик.** Править текст модели кодом
  нельзя — в канал уехало бы то, чего никто не писал.

### Чувствительность поля: признак есть в каталоге, спрашивать не надо

Бот отвечал «неоткуда узнать, чувствительные это данные или нет», имея
признак прямо в карточке колонки. Атрибут называется `sensitivity`
(подтверждено владельцем задачи 2026-08-27): **заполнен — поле закрыто,
нужен доступ и согласование.** Значение называет AD-группу, групп много,
но решение от группы не зависит — она говорит только, куда идти.

Три состояния разведены намеренно, и это не педантизм:

| | что значит | что говорить заказчику |
|---|---|---|
| признак заполнен | поле закрыто | нужен доступ и согласование, группа названа |
| признак пуст | по данным каталога поле не чувствительное | можно, но запрет на ПДн действует независимо от каталога |
| признака нет в ответе | карточки не запрашивались или не пришли | ни что открыто, ни что закрыто сказать нельзя |

Слитые вместе, они дают самый дорогой из возможных ответов — уверенное
«согласование не нужно» на чувствительном поле. Поэтому блок печатается
сводкой («ЧУВСТВИТЕЛЬНЫХ ПОЛЕЙ N из M»), а не только строками у полей:
для запроса на выгрузку это готовый раздел сообщения заказчику.

Отдельное правило в `prompts/author.md` запрещает формулировку «неоткуда
узнать, чувствительные это данные»: при наличии блока она неверна, а без
блока верным ответом является «признак не пришёл», а не отсутствие знания.

### Срез по полям — не метрика, и определения ему не нужно

Живой прогон 2026-08-27 (вечер), после починки инвентаря. Вопрос: «где взять
инфу о количестве BI-аналитиков в стриме „Дата“, 15 грейд, юнит Human Capital
Origination». Бот ответил правильно и полно: назвал `mdm_employee_structure_d`,
поля `grade`, `emp_stream_desc`, `lvl{N}_mapped_management_unit_nm`, привёл
двухшаговый запрос по рецепту `rc-find-unit-level`. И поставил **среднюю**
уверенность, а в «Чего не хватило» написал, что нет отдельной статьи
с определением метрики «количество BI-аналитиков».

Понижения кодом при этом не было — строки «Почему» в разборе нет,
`confidence_capped: false`. Среднюю заявила сама модель, и подтолкнул её
к этому промпт: в градациях стояло «средняя — нужного определения нет,
но есть соседнее», а статьи с определением такого счёта не существует.

**Требование такой статьи ломает основной принцип проекта.** Инвентарь
берётся из каталога именно затем, чтобы не описывать его в git
(`kb/process/metadata-sources.md`); комбинаций фильтров бесконечно много,
и завести определение на каждую значит переписать каталог в базу. Бот,
который на каждый срез просит новую статью, ставит перед базой невыполнимую
задачу и портит себе калибровку: средняя уверенность становится значением
по умолчанию на всех вопросах, ответ на которые собирается из полей.

В `prompts/author.md` записано разделение:

| | |
|---|---|
| **срез** — отбор строк по значениям известных полей и подсчёт | определения не нужно, ответ полный, уверенность высокая |
| **показатель с нетривиальной логикой** — числитель и знаменатель, дата расчёта, кого исключать, поведение на границах периода | нужна статья, и её отсутствие это настоящий пробел |

Оттуда же три следствия:

- **Инвентарь каталога плюс правила среза из статьи витрины — это ПОЛНОЕ
  основание**, а не половина. Сказано прямо, потому что из прежней формулировки
  это не читалось.
- **Многошаговый рецепт не делает основание частичным.** `rc-find-unit-level`
  сам по себе двухшаговый: сначала уровень и ключ юнита, потом выгрузка.
  Параметр, который заполняется на первом шаге, — это рецепт из базы, а не
  пробел в нём.
- **В «Чего не хватило» запрещены записи вида «нет статьи с определением
  <комбинация фильтров>».** Настоящий пробел здесь один: значение фильтра,
  которого не видно в метаданных, — и писать надо про значение поля,
  а не про недостающую статью.

Кодом это не померить: «нужно ли этому показателю определение» — суждение
о смысле, и любая подстрочная проверка станет ложной тревогой на верном
черновике. Второй пункт разбора без решения в конструкции, рядом с «не
переспрашивай написанное».

### Расхождение имени поля: правило сработало, ошибка была в данных

Живой прогон 2026-08-28, вопрос про BI-аналитиков 15 грейда. Инвентарь
пришёл (`метаданные: emart.mdm_employee_structure_d`), домен определился,
роутер нашёл две статьи плюс мастера — то, что чинилось 27-го, работает.
А уверенность встала средней, и в «Чего не хватило» бот написал:
«расхождение в описании поля грейда между статьёй (`grade_nm`)
и метаданными каталога (`grade`)».

**Конструкция отработала верно, неверными были данные.** Правило «в составе
и именах полей прав каталог, в правилах расчёта права статья; молча выбирать
нельзя — назови расхождение и снизь уверенность» сделало ровно то, для чего
написано: назвало оба имени, указало обе стороны и не стало гадать. Чинить
надо было базу, и по сообщению бота видно, что именно.

Цена при этом была высокой и незаметной: `grade_nm` стоял в четырёх файлах,
а грейд — самое частое слово в живом трафике (18 обращений). То есть каждый
вопрос про грейд получал среднюю уверенность из-за одной лишней буквы,
и понять это по логу было нельзя — `confidence_capped` там `false`, средняя
пришла от модели.

**Автоматической проверки на этот класс не завели, и намеренно.** Сверить
имена полей из статьи с каталогом код мог бы только на ПОЛНОМ инвентаре
и только для той таблицы, которой статья посвящена, — а статьи называют
и поля соседних витрин (правила джойна), и сами витрины. Проверка вида
«поля нет в инвентаре» загоралась бы на `attendance_dt`, `change_dt`,
`employee_profession_dk` и прочем верном содержимом, то есть на верной
статье. Строка, которая горит всегда, обесценивает и себя, и соседние —
ровно по этой причине в проекте нет и проверки попадания эксперта
в черновик. Внутрибазовая сверка «одно поле в двух написаниях» тоже
не годится: на `employee_profession` / `employee_profession_dk` она даёт
ложное совпадение, а это верная пара «таблица и её ключ».

Что осталось защитой: правило в промпте автора, которое эту ошибку
и поймало, и статус каталога как источника имён, записанный теперь в самой
статье витрины.

### Ревизия связей 2026-08-27: четыре контракта, которые держались на честном слове

Отдельно от правок по существу — сплошная проверка того, что части проекта
не противоречат друг другу. Найденное ниже не проявлялось ни в одном живом
прогоне и не ловилось ни одним тестом: всё четыре — контракты между двумя
местами, которые разъезжаются молча.

- **Границы секций реестра были вписаны в сборщик парами имён**
  (`rows('## Сущности', '## Самостоятельные выгрузки')`). Вставка нового
  раздела между ними или смена порядка — и чужие строки разбираются как свои,
  формат колонок другой, на выходе неверные данные. Реестр правят чаще, чем
  сборщик, и живёт он в другом репозитории. Граница теперь — **следующий
  заголовок `## `, какой бы он ни был**; тест 24 в `test_pipeline.mjs`
  вставляет в реестр посторонний раздел и требует, чтобы он не подмешался
  ни в сущности, ни в самообслуживание, ни в маршруты.
- **`fill()` проверял один плейсхолдер из четырёх.** Ассерт стоял на
  `{{REGISTRY}}`, а `{{MATERIALS}}`, `{{MODE_RULES}}` и `{{FORM}}` не
  проверялись вовсе: опечатка в имени слота уехала бы к модели буквальным
  текстом `{{MATERIALS}}`, и промпт при этом выглядел бы рабочим, а половина
  контекста до модели не доезжала. Проверка стала общей по регулярке.
- **`reached_by: code` нечем было сверить со сборщиком.** `validate_kb.py`
  требует поле, но проверить, что путь действительно вписан в сборщик,
  не может — сборщик в другом репозитории. При этом оба каталога лежат рядом
  на диске, и тест 29 в `test_pipeline.mjs` сверяет обе стороны: файл
  со статусом `code`, которого нет в сборщике, не доезжает до бота **ни разу**
  (так месяцами не доезжал `sql-conventions.md`), а путь в сборщике без файла
  в базе даёт «статью не удалось прочитать».
- **`\w` и `\b` рядом с кириллицей больше не ловятся глазами.** Тест 43
  в `test_adapters.mjs` сканирует Code-ноды **всех** собранных флоу, включая
  телеметрию, и сам детектор проверен на трёх регулярках, которые жили
  в проде и выглядели рабочими: `информационн\w*`, `\bот\s+пользовател`,
  `групп\w*\s+компан`. Без такой самопроверки зелёный тест не значит ничего —
  сломанный детектор и чистый код по выводу неразличимы.

Пятый случай литерального `\n` вместо перевода строки (на этот раз
в собранном SQL) поймал тест группы 12: **проверка на настоящий перенос
строки теперь стоит рядом с проверкой самого запроса.** Класс известный —
JS внутри неraw-строки Python, — и ловится он только прогоном: по виду JSON
литеральный `\n` неотличим от нормального запроса.

**Шестое — проверка, которая сама теряла проверяемое.** Тест 37 требует,
чтобы каждое поле `Parse answer` было либо в витрине, либо названо
неиспользуемым, и якорь у него стоял строго по началу строки: `^out\.`.
Часть присваиваний живёт внутри блоков `{ … }` и потому с отступа —
`experts_invented` и `draft_own_tools` проскакивали мимо теста молча.
Ровно то же, что уже было с `gs.includes('root_id')`: подстрока в тексте
есть, поведения она не гарантирует. Проверять надо и сам детектор — здесь
это видно по числу найденных полей, и оно печатается.

**И один пробел по существу, найденный тем же проходом.** `get_table_info` —
инструмент аналитика в его собственной среде, коллеге предлагать его нельзя.
Правило есть в промпте автора, но упоминаний в базе знаний шесть, и одно
из них в `kb/process/sql-conventions.md`, которая с 2026-08-27 доезжает
до автора на КАЖДОЙ просьбе помочь с запросом. `draft_leaks` эту дыру
не закрывал: он считается **только** в режиме выгрузки, а просьба помочь
с запросом режим как раз гасит. Теперь код мерит и называет —
`draft_own_tools`, строка `🚩` джуну, список закрытый (одно имя), чтобы
у проверки не было ложных тревог: широкая проверка «любое имя
с подчёркиванием» на ответе с запросом горела бы всегда.

### Сплошное ревью 2026-08-28: двадцать девять находок, ни одной видимой по прогону

Отдельным проходом проверено всё разом — флоу бота, телеметрия, база знаний —
на противоречия между частями. Найденное ниже объединяет одно свойство:
**каждая часть по отдельности работает как задумана и зелена по тестам,
ломается стык.** Ниже только то, что закрыто; полный разбор — в истории git.

**Черновик хвалили и тут же велели вычистить.** `LEAK_RE` ловил
`sec_analytics_ask` как имя поля — устроено оно ровно так же, — и в одном
сообщении джуну стояли две строки подряд: `🔒` «согласование ИБ названо»
и `⚠️` «вычистить `sec_analytics_ask`». Имя канала заказчику как раз нужно,
без него неизвестно, куда подавать заявку. Совпадают эти условия ВСЕГДА,
когда правило ИБ применимо: и `ib_required`, и `draft_leaks` считаются только
при `is_export`. Тот же промах бил по адресатам маршрутов. Адреса
(`~channel`, `@user`) вырезаются перед поиском, как ссылки.

**Калибровка считала ноль.** Ядро пишет `confidence_claimed` английским
ключом (`high`), витрина сравнивала со словом «высокая». Метрика, названная
в этом же документе самой ценной, была пустой и выглядела рабочей: колонка
есть, запрос зелёный, в ней всегда 0. Тест 38 сверяет значения со сборщиком.

**Личка включала режим выгрузки по свободному тексту.** `topic_kind` — это
«что человек выбрал в форме», и `Plan` принимает его как ФАКТ. В личке
`PREFIXES` пуст, формы нет, и туда уезжала вся первая строка: вопрос «нужно
ли заводить запрос на выгрузку, если разово?» включал полный режим (+две
статьи, +4500 токенов, требование ТЗ), а просьбу написать `select` погасить
было нечем — догадкой такой режим не считался. Живой отказ 2026-08-27
в личке оставался невылеченным. Темы теперь нет там, где не было префикса.

**Каталог считал упавшие карточки проверенными.** `checked = details.length`,
а `details` включает и отказавшие запросы, поэтому `checked < totalCols`
не мог стать true никогда. На таблице, где половина карточек отдала 500,
шейпер печатал «проверены 3 из 3», и «не встретилось» читалось как «такого
поля нет». Рядом `cardsFailed` вычислялся и не читался нигде: поле, чьё
описание не пришло, выглядело как поле без описания.

**Владелец отчёта и канал поддержки выбрасывались.** Оба подтверждены
прогоном разведки, оба лежат в `/attribute`, а шейпер печатал команду и два
УГАДАННЫХ ключа (`period`, `status`). По фидбеку аналитика «кто владелец» —
11 обращений из 49, «к кому идти» — ещё 13: ответ на два самых частых
вопроса канала приезжал из каталога и терялся по дороге.

**Основа слова резалась до трёх букв.** `грейд` → `гре`, `стрим` → `стр`,
`оклад` → `окл` — при том что совпадение идёт подстрокой, и `стр` ловит
структуру, стратегию и страну. Слова не случайные: это самые частые в живом
трафике, их для того и дописали в описания доменов. Минимум — четыре буквы.

**Коллектор трекера не видел своих же событий.** Фильтр `source eq "channel"`
пропускал `task_linked` и отсекал `task_status_changed`: закрытые задачи
опрашивались вечно, а `Diff statuses` видел каждый статус изменившимся
и писал бы событие на задачу каждые 15 минут — ровно то, что комментарий
в самой ноде обещает не допускать.

**Ещё четыре тихих в телеметрии.** `event_inferred` терялся в `Merge
reaction` между тем, кто его вычислил, и тем, кто читает, — а реакции идут
только этим путём. Засев истории обрывался на 200 постах без единого
признака. `event_ts = 0` приезжал в DLH как `1970-01-01 03:00` (from_unixtime
отдаёт время в тайм-зоне сессии, а ноды Flush ставят Europe/Moscow), и точное
гашение полуночи мимо него промахивалось. Credential снова разъехался:
в телеметрии остался устаревший «…account 2».

**«Задача для базы» отправляла чинить несуществующее.** Путь, выдуманный
роутером, попадал в `articles_failed` и печатался как «реестр ссылается
на файл, которого нет» — джуна отправляли править строку, которой нет.
Два диагноза разведены.

**Вопрос про отчёт не распознавался вне канала.** `Build materials` брал тему
и ссылку из сырых полей формы, а формы нет ни в чате, ни в личке — правило
«спрашивали про отчёт, а отчёта нет» и понижение за ним не срабатывали ни
разу. Та же асимметрия, что однажды уже нашли на самообслуживании.

**В базе знаний три расхождения.** `m-active-headcount` определял декрет
и прогульщиков через `status_nm`/`employment_type_nm` — поля, которых больше
нигде нет, — со значениями в единственном числе, тогда как перечень
`active_type_nm` хранит их во множественном: неверное имя поля роняет запрос
громко, а неверное написание значения даёт **ноль строк без ошибки**. Три
`FROM` ссылались на каталожную схему вместо `prod_v_`. Плейбук выгрузки,
доезжающий до бота на 43 % обращений, предлагал выбрать между ATS и HCM —
системами, которых в этой базе нет вовсе, остаток шаблонного описания.

**Пятнадцать алиасов не работали ни разу.** Проверка была односторонней:
реестр обязан быть подмножеством фронтматтера, обратное не проверялось —
а роутер видит только проекцию реестра. «Неявки», «квалификация»,
«юрпозиции» жили в статьях и не находились.

Новые проверки, каждая закрывает свой класс: сверка значений уверенности
со сборщиком (тест 38), обрыв засева (39), чтение лога трекером (40),
доезд посчитанного до отчёта (41); в базе — `check_enum_values()`,
`check_sql_schemas()`, `check_process_links()` и двусторонняя сверка алиасов.

**Урок, общий для всех двадцати девяти.** Ни одна находка не видна по прогону
и ни одна не ловится чтением одного файла: все они — контракты между двумя
местами, и оба места по отдельности правы. Отсюда практика: проверять не
«работает ли часть», а «совпадает ли то, что одна часть пишет, с тем, что
другая читает» — именно так устроены тесты 36–41 и обе стороны сверки
`reached_by`.

### Половина `test_shapers.mjs` была декорацией

Найдено при сверке числа проверок с этим документом: файл печатал 41 строку
`ok`, а здесь записано 74. Расхождение оказалось не устареванием цифры.

Группы 0–11 писались как `console.log('имя:', выражение)` — они **печатали**
`true`/`false` и не считались нигде. Счётчик `ddFails` и функция `checkS`
появились позже, вместе с группой 11, и `process.exit` читал только его.
То есть регрессия в шейпере таблицы печатала `false` посреди длинного лога,
файл выходил с кодом 0 и словами «проверки прошли», и по выводу это было
неотличимо от исправного прогона.

Класс ровно тот же, что `gs.includes('root_id')`: проверка, которая читается
как проверка и не гарантирует ничего. Только здесь она ещё и **вытесняла**
настоящую — место занято, писать вторую незачем.

48 таких строк переведены в `checkS`, и **две из них сразу оказались
красными**. Обе в группе 8в, и причина у них общая: фикстура «ни имя,
ни описание не совпали» описывала поля текстом «к зарплате отношения
не имеет» — при поиске по слову «зарплата». Пока стемминга не было,
`зарплата` действительно не совпадало с `зарплате`, и тест был верен.
Стемминг (группа 8е) срезал слово до основы `зарплат`, которая в этой
фразе есть, — и фикстура промаха стала совпадать сама с собой. Проверка
покраснела ровно тогда, когда должна была, просто краснеть было некуда.

Отсюда правило: **проверка, которая не может уронить прогон, не проверка.**
Число проверок в этом документе — не украшение: расхождение с фактическим
выводом здесь оказалось единственным следом отказа, прожившего месяцы.

### Разбор 2026-08-31: две первопричины на три кейса, и снятые лимиты

Четыре живых обращения, из них три — не три разные проблемы, а две
первопричины. Общее у обеих то же, что и у всех прежних находок: часть
по отдельности работает как задумана, ломается стык.

**1. Статья с ответом была запрошена и молча потеряна на опечатке в пути.**
В выгрузке про образовательные программы «Задача для базы» сообщала:
«роутер назвал путь, которого нет в реестре: `kb/field-synonyms.md`».
Настоящий путь — `kb/recipes/field-synonyms.md`, и в этой статье лежала
строка `HQ / Line / Support → emp_specialization_oper_code` — ровно то,
чего не хватило: в ТЗ бот написал «поле не обнаружено». То есть он **сам
понял, чего ему недостаёт, сам это попросил и не получил из-за одной папки**.

Отказ был тихим вдвойне: путь уезжал в `articles_invented`, тот печатался
как «промах роутера, править нечего», и уверенность **не понижал**. По логу
потеря статьи и «такой статьи в базе нет» выглядели одинаково.

Лечится тем же приёмом, что мастера домена и инвентарь витрин, — знание
переезжает из памяти модели в код:

- **Роутер называет `id` сущности, путь подставляет реестр.** Тогда
  выдуманного пути не бывает ПО КОНСТРУКЦИИ. Путь принимается как
  совместимость и резолвится через реестр.
- **Промах в папке восстанавливается по имени файла** — и только при
  ЕДИНСТВЕННОМ кандидате: тихо прочитать не ту статью хуже, чем не прочитать
  никакую. Восстановление называется джуну строкой `🔁` и уезжает
  в телеметрию: доля восстановлений — метрика того, держит ли роутер формат.
- **Невосстановимый путь теперь ПОНИЖАЕТ уверенность до средней.** Статья,
  которую роутер счёл нужной, до автора не доехала, и ответ собран без неё.
- **Словарь синонимов добирается КОДОМ** — на том же гейте, что
  `sql-conventions` и активная численность (выгрузка либо просьба помочь
  с запросом). Резолв путей чинит промах, но не забывчивость: в том же дне
  второй кейс («сколько сотрудников по покраске HQ и BigOps», личка) остался
  без словаря вовсе, потому что роутер его не запросил.

**2. «Не совпало ничего» читалось как приглашение подобрать по смыслу.**
На вопросе про покраску автор пошёл в `lvl3_mapped_management_unit_nm`,
дословно не нашёл ни «HQ», ни «BigOps» — и подставил в фильтр «Финансы»,
«Human Capital», «Технологии, Безопасность, Операции», расписав, какие
из них «классические штабные функции». Запрос выполнился и вернул неверные
цифры молча.

Инструкция стояла буквально, в трёх местах: в блоке `Check result`
(«найди подходящее ПО СМЫСЛУ»), в `REVISE_PROMPT` и в `prompts/author.md`.
Писалась она под **«Дата» → «Data»**: одно понятие, другое написание.
А здесь слово заказчика было значением ДРУГОГО поля, и сопоставлять
по смыслу было не с чем.

Это единственный известный случай, когда проверка значений сработала
**хуже своего отсутствия**: без неё автор сказал бы «не нашёл», а с ней
уверенно подставил не то.

Развели два случая явно, во всех трёх местах:

| | признак | что делать |
|---|---|---|
| другое написание того же понятия | «Дата» → `Data` | назвать точное значение, сказать, что заказчик писал иначе |
| слово из другого поля | «HQ» в поле подразделений | **ничего не подставлять**: поле выбрано неверно, искать в словаре синонимов или спросить |

Плюс явный запрет **раскладывать одно слово заказчика в набор значений**:
«BigOps — это вот эти три подразделения» ниоткуда не взято, а выглядит
как знание.

И измеримая проверка, потому что словесные правила модель роняет
(прецедентов уже пять): **`check_substituted`** — значение из группы
«прочие» (ни точное совпадение, ни похожее), оказавшееся в итоговом
фильтре. Заказчик его не называл ни разу. Строка `🚩` джуну раньше
остальных проверок значений, понижение до средней, отдельная колонка
в витрине. Проверка узкая намеренно, как `experts_invented`: сверяется
только с перечнем, который сами же и показали, — придуманное с нуля
значение она не поймает, зато ложных тревог у неё нет.

**3. Лимиты резали полноту там, где стояли дёшево.** В ТЗ той же выгрузки:
«поле „должность“ не вошло в список из 53 найденных по смыслу полей. Либо
его нет в витрине, либо оно скрыто лимитом». Лимита на 53 не было — 53 это
число СОВПАВШИХ. А полный список имён шейпер не печатал вовсе, если фильтр
хоть что-то нашёл: `inventory()` вызывался только из веток промаха.

При этом инвентарь всё это время лежал у шейпера на руках — `rows` строится
из `dd_columns` в любом режиме. **Печать стоит ноль HTTP-запросов и ~3 КБ
на 289 имён**, а молчание стоило «поля нет в витрине» там, где оно есть.

| лимит | было | стало | почему |
|---|---|---|---|
| полный список имён при совпадениях | не печатался | печатается ВСЕГДА | 0 запросов; по нему и только по нему судят об отсутствии поля |
| `MAX_CARDS` (карточки по фильтру) | 12 | снят | резал дешёвый путь, когда дорогой (`by_meaning` по всем колонкам) и так без потолка. Остался предохранитель от вырожденного фильтра — долей, а не числом |
| `MAX_ARTICLES` | 8 | 16 | 10 добирает код + 6 предел роутера: потолок обязан быть НЕ-связывающим |
| `MAX_ROWS` (словарь значений) | 60 | 300 | у широкого справочника значений больше двухсот, сортировка по частоте — редкое искомое было за срезом |
| `MAX_PAIRS` | 4 | 8 | запрос идёт по запросу на поле, восьмая пара — один вызов, а не восьмикратный скан |
| `MAX_HINTS` | 4 | 8 | иглы склеиваются в один запрос; пропущенная игла = понятие не искали вовсе |
| `MAX_DD` | 4 | 4 | оставлен: ограничение не токенное, а по числу HTTP-запросов — сотни на объект в `by_meaning` |

**Про `MAX_ARTICLES` отдельно, потому что там нашлось своё.** Порядок добора
такой: сначала статьи, добранные КОДОМ (плейбук выгрузки, развилка структуры,
маршрутизация, `sql-conventions`, активная численность, словарь синонимов,
поиск юнита, мастера домена), и только ПОТОМ — то, что роутер подобрал под сам
вопрос. Значит обрезка по потолку срезает **именно подобранное под вопрос**,
а служебное остаётся. Потолок, который срабатывает, работает ровно наоборот
замыслу — поэтому он обязан быть не-связывающим: 10 (худший случай кода) плюс
6 (предел, записанный в промпте роутера) = 16. Тест в группе 6 гоняет худший
честный план и требует, чтобы обрезки на нём не было вовсе.

**Про `MAX_ROWS` — это третий случай одного и того же отказа.** `ALL_CARDS_CAP
= 60` обрывал поиск по смыслу на 289-колоночной витрине; здесь ровно то же
делалось с перечнем ЗНАЧЕНИЙ. Когда не совпало ничего, перечень и есть ответ:
справочники ведутся по-английски, заказчик называет их по-русски, и искомое
находится только глазами по списку. Сортировка идёт по частоте — значит
редкое искомое оказывалось за срезом, и «не встретилось» читалось как «такого
нет». Цена снятия: ~3 000 токенов, и только в случае «не совпало ничего».

**Триста, а не двести, и разница принципиальная.** Про
`emp_specialization_desc` известно ровно одно: значений «НЕ МЕНЬШЕ 200» —
прогон 2026-08-27 упёрся в `LIMIT` и тем самым измерил **сам потолок,
а не кардинальность**. Поставить потолком то самое число, на котором прошлый
замер остановился, значит гарантированно резать хвост у поля, про которое
мы и знаем-то только, что оно длиннее. Триста оставляет запас и делает срез
ВИДИМЫМ: пришло меньше трёхсот — перечень полный; ровно триста — упёрлись,
и это повод померить кардинальность отдельно, а не гадать.

**Потолок живёт в ДВУХ нодах и обязан в них совпадать.** `Build check SQL`
ставит `LIMIT`, `Check result` режет печать. Разъедутся молча: строки придут,
за них заплатят запросом, а автор их не увидит — и «не встретилось» опять
прочитается как «такого нет». Тест в группе 33 вынимает оба числа из
собранного флоу и требует равенства, плюс отдельно — что потолок выше
единственного известного замера.

**И главное про лимиты: их размер теперь измерим.** `materials_len`
считается в `Build materials` и уезжает в телеметрию. До этой правки числа
не было ни в одном поле вывода — то есть все потолки были придуманными,
и каждый раз, когда они мешали, это выяснялось живым отказом.

Седьмым придуманным числом оказался сам ориентир: в этом документе стояло
«перевалит за 40 000 — резать промпт автора», хотя **контекстное окно
модели ~1 000 000**, а 240 000 — это TPM аккаунта, то есть предел МИНУТЫ,
а не вопроса (на нём и упал tool-loop: 242 618 токенов на один вопрос,
`quota tpm limit exceeded`). То есть 40 000 были осторожностью, записанной
как факт, — и удерживали от правок, которые надо было сделать раньше.
При ≈ 26 000 и ≈ 32 000 запас по контексту тридцатикратный, и снятые выше
лимиты его не расходуют сколько-нибудь заметно.

Отсюда правило рядом с прочими: **число, записанное как порог, обязано
называть, откуда оно взято.** Осторожность и измеренный предел выглядят
в тексте одинаково, а стоят по-разному.

**Цена правок в токенах.** Промпт автора вырос на 12 %, блок выгрузки
на 19 %, роутер на 15 %; статей в материалах может быть 12 вместо 8,
и к каждому инвентарю добавились ~3 КБ имён. Стало примерно **26 000
на обычный вопрос и 32 000 на выгрузку** при контекстном окне ~1 000 000 —
запас тридцатикратный, и вопрос «что вынести из промпта автора» решается
не расходом, а тем, помогают правила или мешают: лишнее правило портит ответ
задолго до того, как упрётся в токены. Ближе другой предел — TPM аккаунта,
но он про число обращений в минуту, а не про размер одного.

**4. Увольнения — только `company_fire_flg`, и причина важнее запрета.**
Правило в базе было (`m-turnover` считает `sum(company_fire_flg)`,
в «Категорически нельзя» есть запрет фильтровать потоки по датам), но
причины не было нигде: **`company_fire_dt` проставляется ЗАРАНЕЕ** —
заявление написано, увольнение назначено через две недели, — и такое
увольнение может не состояться. Считая по дате, складываем несвершившиеся
события со свершившимися: запрос не падает, цифра правдоподобна, сверить
не с чем, потому что «правильная» получается тем же запросом.

Записано в `t-emp-structure` («Факт увольнения»), в `m-turnover`,
в плейбук выгрузки (там «уволен» перестал быть вопросом-развилкой)
и в промпт автора. Плюс `draft_fire_by_date` — зеркало
`draft_no_active_filter`: дата увольнения стоит в СРАВНЕНИИ, а флага нет
вовсе. Дата как выводимое значение проверку не тревожит.

**5. Название компании — не фильтр.** «Уволились из Тбанка» — это вся
витрина, а не значение поля. Бот пошёл искать «Тбанк» среди значений
`lvl3_mapped_management_unit_nm` и в «Чего не хватило» предложил проверить
уровни глубже, то есть отправил чинить не то. Шаг −1 в `rc-structure-choice`
(с исключением про юрлицо), правило в промпте автора и `draft_company_filter`
со **закрытым коротким списком** — широкая проверка «значение похоже
на организацию» горела бы на верных черновиках.

**6. ТЗ для аналитика — готовый запрос, а не его описание.** Разделы
`ГРАНУЛЯРНОСТЬ / ФИЛЬТРЫ / ПОЛЯ / ДЖОЙНЫ` перечисляли прозой то, из чего
аналитик потом писал `select` — то есть повторяли перевод, который бот уже
сделал. Теперь два раздела: `ЗАПРОС` (готовый SQL, `prod_v_`-схема, срез
и флаги дословно, развилки заказчика — комментарием `--`) и `ЧТО ПРОВЕРИТЬ
ПЕРЕД ЗАПУСКОМ`. Побочно это **усиливает существующие проверки**: и разбор
пар «поле = значение», и `draft_no_active_filter` читают `tech_spec`,
и по настоящему SQL они работают точнее, чем по списку прозой.

### Карточка модели `tgpt/text.instant.sota`

Записана из карточки LLM-прокси, чтобы решения не принимались по названию.
Семейство и tier здесь значат разное, и по одному только имени модель легко
недооценить.

| | |
|---|---|
| Tier `sota` | максимальное качество в сложных задачах |
| Семейство `text.instant` | модели под простые текстовые задачи с низкой latency |
| Контекстное окно | **~1 000 000 токенов** |
| Возможности | Reasoning, Tool calling |
| Чувствительные данные | **разрешены**: модель развёрнута внутри банковского контура, данные не покидают его пределы |
| Уровень поддержки | Business operational |
| Доступность | по умолчанию, добавлена 20.07.2026 |

Три следствия для конструкции:

- **Контекст перестал быть ограничением вовсе.** ≈ 32 000 на выгрузку против
  миллиона — запас тридцатикратный. Все потолки в этом проекте (`MAX_ARTICLES`,
  `MAX_ROWS`, `MAX_PAIRS`) теперь ограничивают что угодно, кроме контекста:
  число HTTP-запросов, время ответа, внимание автора. Ссылаться на «дорого
  по токенам» при их обсуждении больше нельзя — это будет ровно тот
  придуманный порог, который здесь уже разбирали.
- **Tool calling модель умеет, и мы им не пользуемся — намеренно.** Конвейер
  заменил tool-loop не потому, что инструменты не поддерживались, а потому
  что расход рос квадратично по итерациям. Появление tool calling в карточке
  этот довод не отменяет: он про устройство цикла, а не про возможности
  модели.
- **Работа с чувствительными данными разрешена инфраструктурно.** Это снимает
  ОДИН из двух доводов за фильтр `PII_RE` в проверке значений — тот, что
  «персональные данные уезжают в контекст модели». Второй довод (политика
  обращения с ПДн) карточкой не закрывается, поэтому фильтр оставлен как
  есть: снимать защиту по косвенному признаку — это то же самое, что
  подставлять значение по смыслу.

**TPM запрашивается отдельно.** Лимит токенов в минуту не выдаётся вместе
с моделью: по карточке нужно назвать модель и аккаунт в канале
`~gpt-support`. До выхода в основной канал это стоит сделать — расчёт
в разделе про токены выше.

### Модель LLM переехала в константу — она нигде не была записана

Смена алиаса на `tgpt/text.instant.sota` вскрыла то, чего в проекте
не хватало: **модель не была записана ни в одном сборщике.** Узел
«T-Bank LLM proxy» копировался из `Support Bot.json` — снимка первой
конструкции, который давно не трогали, — и через него алиас
`tgpt/deepseek-v4-flash-fp8` доезжал до всех четырёх узлов ядра. Поменять
модель можно было только руками в интерфейсе n8n, а правка в интерфейсе
живёт ровно до следующего импорта.

Класс известный, третий случай подряд: так же разъезжались Service Account
(2026-08-27) и так же жила выключенная руками нода `Collect articles`.
Лечится тем же приёмом: `LLM_MODEL` и `LLM_CRED` в `build_dd_flow.py`,
нормализация **всех** узлов `CUSTOM.llmProxy`, включая унаследованные
из исходника, и сам исходник тоже приведён к ней. `build_time_flows.py`
читает модель из собранного `Support Bot DD` — как id `DD Lookup`
и `GITLAB_CRED`, одно значение в одном месте, — и **падает**, если её там
нет: пустая модель это не ошибка сборки, а падение первого же вопроса.

Тест 32б в `test_adapters.mjs` проверяет не конкретный алиас, а
согласованность: одна модель и один credential во всех воркфлоу, исходник
наравне с собранным (в прошлый раз устаревшее значение лежало именно
во входе, и тест на выходе оставался зелёным).

**И отдельно — модель уезжает в телеметрию рядом с `prompt_version`.**
Калибровка (заявленная уверенность против действующей) названа в этом
документе самой ценной метрикой, и она **помодельная**: у другой модели
своя манера завышать. `prompt_version` смену модели не ловит вовсе — он
хеш промптов, и 2026-08-31 модель сменилась, а хеш остался прежним. Без
колонки `llm_model` две модели сложились бы в одну цифру, доля завышений
поехала бы, и списать её было бы не на что. Разрез по модели добавлен
и в сам запрос калибровки.

### Запрета на выгрузку у нас нет — есть требование согласовать доступ

Отдельным решением, потому что оно меняет политику, а не формулировку.

Раздел «Чего не будет» утверждал, что данные в файл не попадут: ПДн
«не выгружаются вовсе», просьба о них — «эскалация руководителю группы».
Живой процесс устроен иначе: **за выгрузками в канал приходят как раз те,
у кого доступа пока нет, и согласуют его прямо в треде обращения.**
Получалось прямое противоречие, видимое заказчику: бот говорит «этого
не будет», человек идёт согласовывать и получает ровно то, чего «не будет».

Раздел убран целиком, вместе с самим отказом. Вместо него:

- поле, требующее доступа, **остаётся в составе файла** и помечается 🔒;
- под списком **одна** строка: «по полям с 🔒 понадобится согласование
  доступа». Ни отдельного раздела, ни второго списка полей: сообщение
  читают с телефона, а дублирование только удлиняет его;
- основание — **только признак `sensitivity` из каталога**, три состояния
  по-прежнему разведены (заполнен / пуст / не пришёл), и в спорном случае
  пометка ставится: лишняя стоит одного вопроса, пропущенная — выгрузки
  без согласования;
- название AD-группы в черновик не идёт, его место в ТЗ: заказчику оно
  ничего не объясняет.

Убраны формулировки «персональные данные не выгружаются», «взамен предлагаем
суррогатный ключ», «это эскалация» — из `export.md`, `author.md`
и `kb/process/export-playbook.md`. Суррогатный ключ предлагается там, где
он решает задачу («связать с другой выгрузкой»), а не как замена отказу.
Сами персональные данные в переписке по-прежнему не пишутся: сказать,
что поле существует и требует согласования, можно; назвать ФИО и телефон —
нет. Фильтр `PII_RE` в проверке значений не тронут: он про другое —
не тянуть ПДн в контекст модели.

Единственное, что осталось жёстким, — **согласование ИБ при передаче
за пределы группы компаний**: это требование ИБ, а не шаг процесса,
и смягчать его нельзя.

Измеримая часть: `sens_unmarked` — каталог назвал закрытые поля, а в черновике
нет НИ ОДНОГО замка. Проверка узкая намеренно: сопоставлять конкретное поле
с конкретной строкой состава нельзя — в черновике поля названы
по-человечески («рабочая почта», а не `wrk_email_address_txt`), и такая
сверка давала бы ложные тревоги на верном черновике. Уверенность
не трогает — как `draft_leaks` и `ib_missing`.

**Что осталось на потом:** разные виды замков (по группам доступа) и проверка
по логину, есть ли у человека доступ уже сейчас. Пока — один замок и одна
строка.

### Что общего у всех шести находок

Ни одна не видна по прогону, и ни одна не ловится чтением одного файла.
Но здесь добавился новый класс, которого раньше в этом документе не было:
**правило, которое работает хуже своего отсутствия**. «Найди подходящее
по смыслу» было написано ради полезного случая («Дата» → `Data`) и в другом
случае заставило подставить неверное значение — то есть проверка, заведённая
против тихой ошибки, сама её и произвела. Отсюда практика: у каждого
правила, которое велит модели что-то ВЫБРАТЬ, спрашивать не только «когда
оно помогает», но и «что оно велит делать там, где выбирать не из чего».

## Data Detective 2.0 Public API

Источник метаданных для флоу бота: описания таблиц и колонок, DDL, владельцы, связи
между объектами, метрики использования. Отвечает на вопросы «что лежит в этом поле»,
«кто ещё читает эту таблицу», «какой ноутбук её грузит».

Base URL: `https://dd.t-tech.team/api/v3`

Авторизация — credential n8n «Spirit (Devplatform) Service Account API» (`spiritToken`).
В узле HTTP Request **обязательно** выключить Options → Redirects → Follow Redirects.

### Модель данных

Всё в DD — это `entity` с полями `id`, `urn`, `fqn`, `system`, `type`.
Связи — `relation` с типом: `CONTAINS`, `CAN_ACCESS`, `LOADS`, `USES`, `LINK`,
`INCLUDES` и другие. Всё остальное — описания, атрибуты, код, таблицы, ссылки, теги,
метрики — ресурсы-расширения сущности.

> **Ключевое правило: вложенные объекты не лежат внутри карточки.**
> Колонки таблицы — отдельные сущности, доступные только через Related Entity API.
> Параметр `entityFields` их не вернёт, сколько бы значений в него ни передали.

URN всегда кодируется через `encodeURIComponent`, точки не трогаются:

```
urn:dd:tables:greenplum:table:emart.mdm_employee_structure_d
→ urn%3Add%3Atables%3Agreenplum%3Atable%3Aemart.mdm_employee_structure_d
```

### Базовые эндпоинты

| Что нужно | Запрос |
|---|---|
| Карточка сущности | `GET /entity/{urn}?entityFields=...` |
| Описание | `GET /entity/{urn}/summary` |
| Атрибуты | `GET /entity/{urn}/attribute`, `/attribute/{key}` |
| Markdown-блоки | `GET /entity/{urn}/markdown` |
| Код, DDL, SQL | `GET /entity/{urn}/code` |
| Статичные таблицы | `GET /entity/{urn}/table` |
| Уведомления | `GET /entity/{urn}/notification` |
| Теги | `GET /entity/{urn}/tag` |
| Ссылки | `GET /entity/{urn}/link` |
| DQ-метрики | `GET /entity/{urn}/requirement-dq-metric` |
| История изменений | `GET /entity/{urn}/history` |

`entityFields` — повторяющийся query-параметр. Значения: `displayName`, `attributes`,
`codes`, `tables`, `markdowns`, `notifications`, `requirements`,
`requirementDqMetrics`, `links`, `summary`, `tags`, `oldUrns`.

### Related Entity API — вложенные объекты

Шаг 1, разведка (один раз на новый тип сущности):

```
GET /entity/{urn}/related
```

Возвращает словарь ключей связей с описанием: `relation.type`, `direction`,
`entity.type`, `entity.system`, `limit`.

Шаг 2, рабочий запрос:

```
GET /entity/{urn}/related/{key}
    ?entityFields=displayName&entityFields=summary&entityFields=attributes&limit=300
```

Дополнительные параметры: `relationFields`, `limit`, `search`, `aroundUrn`,
`afterUrn`, `beforeUrn` (курсорная пагинация).

Готового ключа не хватает — `POST /entity/{urn}/related-by-query`, тело
`RelationsConditional` (по спецификации: обязательные `type` и `direction`,
необязательный `entity` — фильтр сущности). Массово — `POST /entity/batch/related` и
`POST /entity/batch/related-by-query`.

### Проверенный кейс: колонки таблицы Greenplum

Ключ связи — `columns` (`CONTAINS`, direction `src_dest`, `entity.type` `COLUMN`,
system `tables.greenplum`, `limit` до 500).

```
GET /entity/{encoded_table_urn}/related/columns
    ?entityFields=displayName&entityFields=summary&entityFields=attributes&limit=500
```

Ответ (проверено 2026-08-06 на `mdm_employee_structure_d`, `totalCount` 267):

```json
{ "totalCount": 267,
  "data": [ { "relationId": "…",
              "entity": { "id": "…", "urn": "…:column:emart.…business_dt",
                          "system": "tables.greenplum", "type": "COLUMN",
                          "fqn": "emart.mdm_employee_structure_d.business_dt" } } ] }
```

Элемент массива — **связь**, сама колонка вложена в `entity`. Имя поля — часть
`fqn` после последней точки.

> **Эндпоинт отдаёт только идентификаторы колонок.** `summary` (описание),
> `attributes` (тип данных) и `displayName` в ответе отсутствуют, хотя
> `entityFields` передан — параметр здесь игнорируется. Так что «состав полей»
> из него получить можно, а «описания полей» — нет.

Описания и типы берутся с карточки колонки — **проверено, работает**:

```
GET /entity/{encoded_column_urn}?entityFields=displayName&entityFields=summary&entityFields=attributes
```

Возвращает `summary.data` (краткое описание), `attributes.column_type.data`
(тип данных), `attributes.comment.data` (развёрнутый комментарий владельца),
`attributes.keys.data` (`PK` и прочие ключи). Значение любого атрибута —
в `.data`, сам атрибут это обёртка `{type, data}`.

Цена — один запрос на колонку, поэтому так тянут точечно по нужным полям,
а не весь состав таблицы. Батч-варианты (`POST /entity/batch/related`,
`/related-by-query`) не проверялись; если они умеют `entityFields`, ими можно
заменить пачку одиночных запросов.

Другие ключи связей у таблицы:

| Ключ | Что даёт |
|---|---|
| `physical_tables` | `CAN_ACCESS` — размер, DDL, партиции |
| `notes` | Ноутбуки и отчёты, читающие таблицу (`USES`, `dest_src`) |
| `data_products` | Продукты данных |
| `data_processes` | ETL-процессы |
| `consumers` | Потребители |
| `terms` | Термины глоссария |
| `samples` | Примеры данных |
| `jira_issues` | Связанные задачи |
| `cuts`, `guillotine` | Срезы и отсечения |

### Отчёты и ноутбуки

Живут в системе `reports.helicopter` (и `reports.helicopter_sens`), `type = NOTE`.

1. Найти URN: `POST /search/query`, тело `SearchRequest`.
2. Карточка:
   `GET /entity/{urn}?entityFields=displayName&entityFields=summary&entityFields=attributes&entityFields=links&entityFields=tags`
3. Связи: сначала `GET /entity/{urn}/related` — увидеть ключи для этого типа.
4. Обратный вопрос «какие ноуты используют таблицу» решается со стороны таблицы,
   ключ `notes`.

### Метрики: usage и impact analysis

> Метрики висят на **логической** сущности (`TABLE`), не на физической.

```
GET /entity/{urn}/metrics-group                                       → список групп
GET /entity/{urn}/metrics-group/{group}                               → содержимое группы
GET /entity/{urn}/metrics-group/{group}/format                        → доступные форматы
GET /entity/{urn}/metrics-group/{group}/format/{format}               → все метрики формата
GET /entity/{urn}/metrics-group/{group}/format/{format}/metric        → список ключей метрик
GET /entity/{urn}/metrics-group/{group}/format/{format}/metric/{metric} → конкретная метрика
```

| Группа | Что внутри |
|---|---|
| `impact_analysis_usage` | Кто обращался к объекту |
| `impact_analysis_etl` | Даг или ноут, владельцы, запуски за 100 дней, время последнего запуска |

Форматы: `BADGE` — одиночное значение, `SERIES` — набор значений или таблица.

```
GET /entity/{urn}/metrics-group/impact_analysis_usage/format/SERIES
```

### Поиск сущностей

`POST /search/query` — тело `SearchRequest`, ответ — массив `SearchCard`.
Используется, когда известно имя объекта, но не известен URN.

Схема подтверждена **спецификацией OpenAPI** (файл `openapi` в корне) и живым
прогоном 2026-08-27:

```json
{ "text": "Активность в GitLab",
  "limit": 20, "offset": 0,
  "filters": { "type": ["REPORT"],
               "systemType": ["reports"],
               "systemName": ["reports"] } }
```

| поле | |
|---|---|
| `text` | строка поиска. **Именно `text`** — перебором это стоило трёх проб |
| `limit` / `offset` | по умолчанию 20 / 0. Пагинация есть, значит список перечисляется целиком |
| `filters` | словарь «ключ → **массив** строк», не скаляр. Ключи: `type`, `systemType`, `systemName` |
| `sessionId` / `requestId` | uuid поисковой сессии, не обязательны |

Значения фильтров выводятся из URN, который устроен как
`urn:dd:<systemType>:<systemName>:<type>:<id>`: дашборд Proteus — это
`reports` / `reports` / `report`, ноутбук — `reports` / `helicopter` / `note`,
витрина — `tables` / `greenplum` / `table`.

`SearchCard` в ответе: `urn`, `fqn`, `system`, `type` (обязательные),
`displayName`, `summary`.

**Поля `searchText` в `/search/query` не существует вовсе.** Оно принадлежит
другой ручке — `POST /search/facets/{facetKey}/filters` (тело
`SearchFacetFiltersRequest`: `searchText`, `facetText`, `limit`, `filters`),
которая отдаёт доступные значения фильтров фасета. Проба с `searchText`
поэтому вернула выдачу по умолчанию, и **сервер об этом не сообщил**:
на неизвестные поля он отвечает 200 и молчит.

### Правила

1. Вложенные списки **не** получаются через `entityFields` — только через
   `/related/{key}`. И наоборот: в ответе `/related/{key}` `entityFields`
   игнорируется — приходят только идентификаторы связанных сущностей,
   вложенные в `entity`. Описания и атрибуты по ним запрашиваются отдельно.
2. Для нового типа сущности сначала `GET /entity/{urn}/related` и
   `GET /entity/{urn}/metrics-group`, потом рабочие запросы. Ключи связей
   не угадываются.
3. URN кодируется через `encodeURIComponent`, точки остаются как есть.
4. Массовые операции — через `/entity/batch/related`, а не циклом по одиночным
   запросам.
5. При большом числе связанных объектов — пагинация через `afterUrn`.
6. `401` — протух Service Account. `404` — неверный URN либо несуществующий ключ
   связи; проверять по ответу `/related`, а не подбором.
7. Альтернатива для больших разовых выгрузок — SQL по репликам в DLH или Greenplum,
   схема `prod_chrono_data_detective` (`entity_dd2_catalog`, `relation_dd2_catalog`,
   `entity_*_dd2_catalog`). Нужна AD-группа
   `greenplum_access_chrono_data_detective`. Лаг репликации — от минут до 24 часов,
   поэтому за свежими метаданными идём в API, а не в реплику.
