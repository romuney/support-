# Состав полей

Гранулярность: одна строка = пара `candidate_sk` × `vacancy_id`, максимально
достигнутая стадия за период.

| # | Поле | Тип | Источник | Комментарий при согласовании |
|---|---|---|---|---|
| 1 | `candidate_sk` | bigint | `dim_candidate` | Суррогатный ключ. Заказчик просил ФИО — не даём, ПДн. Для сверки конкретного человека рекрутер найдёт его в E-Staff по id вакансии и дате отклика |
| 2 | `vacancy_id` | varchar | `dim_vacancy` | Номер вакансии как в E-Staff, чтобы заказчик мог открыть и проверить руками |
| 3 | `vacancy_title` | varchar | `dim_vacancy` | Просили «название должности» — даём название вакансии. Оно не всегда совпадает с должностью в штатном расписании, предупредил в треде |
| 4 | `org_unit_at_publish` | varchar | `dim_org_unit` | **Основная колонка.** Подразделение на дату публикации вакансии. Из-за реорганизации 01.05.2026 текущее значение ломает сравнение кварталов |
| 5 | `org_unit_current` | varchar | `dim_org_unit` | Добавлена справочно по просьбе заказчика: он хотел группировать по нынешней структуре |
| 6 | `hiring_type` | varchar | `dim_vacancy` | `mass` / `professional` / `it`. Заказчик не просил, добавили сами: конверсия каналов в массовом и IT-найме несопоставима, без разреза выводы будут ложными |
| 7 | `application_date` | date | `fct_candidate_stage` | Дата отклика. **Не** поле фильтрации периода — см. п. 2 в README |
| 8 | `source` | varchar | `fct_candidate_stage` | Источник найма со слов рекрутера. Согласован как **основной** для бюджета каналов |
| 9 | `source_utm` | varchar | `fct_candidate_stage` | utm-метка отклика. Справочно. По Q2 расходится с `source` в 18% строк |
| 10 | `max_stage` | varchar | `fct_candidate_stage` | Максимально достигнутая стадия: `applied` → `screening` → `interview` → `offer` → `hired` |
| 11 | `max_stage_date` | date | `fct_candidate_stage` | Дата перехода на максимальную стадию |
| 12 | `is_rejected` | boolean | `fct_candidate_stage` | Добавлено после спора о знаменателе (п. 3 в README). Без него конверсия не считается |
| 13 | `rejection_reason` | varchar | `fct_candidate_stage` | Справочник E-Staff. Заполнен в 71% отказов, остальное — пусто; предупредил, что по причинам отказа полной картины не будет |
| 14 | `offer_date` | date | `fct_candidate_stage` | Дата принятия оффера кандидатом, не дата выставления. Отдельно проговорили в треде |
| 15 | `hire_date` | date | `fct_hire` (1С:ЗУП) | Фактическая дата выхода. Единственное поле не из E-Staff — стык систем, см. проверку 3 в `query.sql` |
| 16 | `is_primary_application` | boolean | вычисляемое | Признак «первый отклик кандидата в периоде». Компромисс по п. 1: даёт заказчику срез по людям без потери строк |

Итого 16 полей. Формат — xlsx, одна вкладка, без сводных.

## Что просили, но не включили и почему

| Просили | Почему не включили |
|---|---|
| ФИО, телефон, почта кандидата | Персональные данные. В репозиторий и в выгрузки не попадают никогда. Идентификация — через `candidate_sk` + `vacancy_id` |
| Резюме кандидата (текст или ссылка) | ПДн в свободной форме, плюс объём. Для задачи «бюджет каналов» не нужно |
| Только дошедшие до оффера | Убивает знаменатель — конверсия каналов становится неисчислимой. Развёрнуто в п. 3 README |
| Зарплатные ожидания кандидата | Заполнено в 34% карточек и не валидируется. Дало бы ложную точность в бюджетных расчётах. Предложил отдельно вернуться, если нужен именно этот разрез |
| ФИО рекрутера, ведущего вакансию | ПДн и риск чтения выгрузки как оценки людей. Задача — про каналы, не про рекрутеров. Если нужна нагрузка на рекрутера — отдельный запрос с руководителем в согласующих |
| Данные за 2025 год «для сравнения» | Пришло уже после согласования состава. Не включили: миграция E-Staff была в ноябре 2025, стадии до и после не сопоставимы напрямую. Нужен отдельный разбор маппинга стадий — записано как отдельная задача, в эту выгрузку не тянем |
