# Саммари: база знаний поддержки HR-аналитики + агент в n8n

> Снимок состояния на 2026-08-04. Не переписывается по мере изменений в проекте —
> для актуальной картины смотреть `CLAUDE.md`, `README.md` и остальные файлы `docs/`.

## Что за проект

Репозиторий-источник данных для агента поддержки HR-аналитики (`romuney/support-`). В канал Teams приходит 10+ обращений в день, ведёт джун (Серёга). Задача — собрать базу, на которой можно обучить агента отвечать на типовые вопросы, и сам агент в n8n.

---

## 1. Структура репозитория

**Железное правило: у каждой папки ровно один автор.** Нарушение = бот и человек затирают правки друг друга.

| Папка | Автор | Что там | Как часто |
|---|---|---|---|
| `cases/` | Серёга (джун) | По файлу на каждое закрытое обращение | Каждый день |
| `exports/` | Серёга | По папке на каждый **запрос на выгрузку данных** (не хранилище файлов!) | По необходимости |
| `kb/curated/` | Руководитель | Проверенные статьи — **единственное, чем агент может отвечать как фактом** | По пятницам |
| `kb/derived/` | Только бот | Автосводки: каталог отчётов, глоссарий, пробелы, кластеры | Не нужно, пока кейсов < 50 |
| `kb/proposals/` | Бот предлагает, человек мёржит | Черновики статей при 3-м повторе темы | Не нужно, пока кейсов < 50 |
| `templates/` | — | Болванки для копирования кейса/выгрузки | Почти никогда |
| `docs/` | — | Инструкции, план | Редко |
| `starter/` | — | **Чистый скелет без демо-данных** для боевого репозитория, копируется как есть | — |

### Важные уточнения по терминам

- **`exports/` ≠ «куда класть выгруженные файлы».** Это папка про согласованные заказчиком запросы на данные: README (что выяснилось при уточнении) + fields.md (согласованные поля) + query.sql + result.md. Исходные файлы выгрузок (xlsx/csv) в репозиторий **не кладутся вообще** — они в `.gitignore`.
- Кейс типа `export` в `cases/` — это две строки со ссылкой на папку в `exports/`, не полноценный кейс.
- **Никаких ПДн никогда**: ФИО, телефоны, почты, зарплаты — ни в кейсах, ни в SQL, ни в примерах. Только роли и суррогатные ключи.

### Упрощение (важно!)

Изначально всё было расписано с `derived/`, `proposals/`, пятничным ритуалом как обязательным процессом — **это было избыточно на старте**. Реальная механика сейчас:

**Серёга пишет кейсы в `cases/` → раз в неделю руководитель смотрит на повторы → превращает повторы в статьи в `kb/curated/` → агент отвечает по статьям.**

`derived/` и `proposals/` — автоматизация для момента, когда корпус (50+ кейсов) перестанет охватываться глазами. Пока не нужны.

## 2. Git — минимум для тех, кто не работал

Три слова: **коммит** (сохранение с подписью) → **push** (отправить на сервер) → **pull** (забрать чужие изменения). Ветки не нужны — работаем в `main`, столкнуться негде (разные файлы).

Проще всего для джуна на старте — **через веб-интерфейс GitHub**: Add file → Create new file → вставить содержимое по шаблону → Commit changes. Это уже полноценный коммит, ничего устанавливать не нужно.

Подробная инструкция для двоих (Git с нуля, пятиминутный разбор дня Серёги, разбор выгрузки, пятничный ритм) лежит в **`docs/how-we-work.html`** — самостоятельный HTML, открывается в браузере.

## 3. Промпт для импорта исторических обращений из канала

Файл: **`docs/prompt-import-channel.md`** (и копия в `starter/docs/`).

Задача: разобрать выгрузку обращений за месяц (id, автор, тип, вопрос, решение) и получить из неё кейсы.

**Ключевая логика (после правки):** делить строки не по признаку «есть решение / нет решения», а по признаку **«осталось ли от ответа что-то переиспользуемое»**. Обращение может быть закрыто («скинул файл в личку»), но для базы знаний в нём пусто — и это НЕ пробел в знаниях, просто ответ не записан.

Критерий: *сможет ли посторонний человек по одному тексту ответа решить такую же задачу сам?*

Результат промпта — 5 блоков:

1. **Кейсы** — вопрос + пригодный ответ → в `cases/`
2. **Темы без пригодного ответа** — НЕ пробелы автоматически; разбираются человеком: часть дописывается как кейс (ответ был, просто не записан), часть реально уходит в `gaps.md`, часть выбрасывается
3. Заголовки для анализа повторов (финальный отдельный запрос — группировка тем, 3+ повтора → кандидат в статью)
4. Запросы на выгрузку — отдельный список, решение по ним в канале почти никогда не пишется, придумывать нельзя
5. Выброшенное — с причиной

Запускать **пачками по 20–30 строк** (на длинном файле модель начинает выдумывать и терять строки). Импортированные кейсы помечаются `source: channel-import` + `external_id`, при конфликте уступают кейсам, написанным вручную.

## 5. Сборка агента в n8n

Гайд: **`docs/n8n-flow1.md`** (написан под GitHub API — актуальная реализация уже под **GitLab**, ниже — рабочая версия).

### Правило #1: агент не пишет в канал сам

Готовит черновик → уходит джуну → джун проверяет и отправляет. Автоотправку включать только после того, как черновики две недели подряд уходят без правок.

### Правило #2: предзагрузка vs инструмент — не путать

- **`kb/curated/`** — только **предзагрузкой** в системный промпт, никогда как Tool. Это источник истины, должен быть в контексте всегда. Если сделать инструментом — агент иногда решит не звать его и ответит из головы.
- **`cases/`** — наоборот, как **Tool** (поиск по кейсам), их будет много, в промпт не влезут, ищутся по надобности. При подключении как tool — прямо в описании инструмента написать, что это прецеденты, не источник истины.

### Правило #3: статьи и кейсы — разные переменные в промпте

Если свалить в одну кучу, агент выдаёт разовое объяснение из старого кейса за утверждённое определение. В системном промпте разделены блоками `=== СТАТЬИ (можно утверждать) ===` и `=== ПРЕЦЕДЕНТЫ (не правила) ===`.

### Собранная на практике цепочка (GitLab-нода)

```
When chat message received → GitLab (Get a file) → Code (base64 decode) → AI Agent
```

**GitLab-нода:**

- Operation: **Get a file** (не Create! Create — это запись файла, требует Content/Commit Message/Branch и упадёт, если пустые — это и произошло на скриншоте)
- Project ID: `257353`
- File Path: `kb/curated/playbook-export.md`
- Binary File: выключено

**Нода Code** (GitLab отдаёт content в base64):

```javascript
return [{ json: { text: Buffer.from($json.content, 'base64').toString('utf8') } }];
```

Проверено на реальном запуске — сработало, `content` действительно приходит закодированным.

**AI Agent:**

- Text: `{{ $('When chat message received').item.json.chatInput }}`
- System Message: правила + `=== СТАТЬИ === {{ $json.text }}`

### Системный промпт (полный текст — в `docs/n8n-flow1.md`)

Ключевые правила: отвечать только из источников; не выдумывать цифры/даты/названия без ссылки на файл; никаких ПДн; запрос на выгрузку не решается ответом — выдаётся чеклист согласования; расхождение цифр между системами почти всегда = разница в определениях, не ошибка данных.

Формат ответа — всегда 4 блока:

```
ЧЕРНОВИК ОТВЕТА: ...
ИСТОЧНИКИ: пути к файлам
УВЕРЕННОСТЬ: высокая / средняя / нет ответа
ЧЕГО НЕ ХВАТИЛО: <только если не высокая — формулировка как недостающее знание>
```

Блок «ЧЕГО НЕ ХВАТИЛО» — рабочий инструмент: раз в неделю собираешь все такие строки, повторившиеся идут в очередь на статьи в `kb/curated/`. Это и замыкает цикл.

### Три обязательных теста после сборки

1. Вопрос с ответом в подключённой статье → должен ответить по существу со ссылкой на файл.
2. Вопрос про выгрузку → чеклист согласования, не готовый ответ.
3. **Вопрос, ответа на который в подключённых файлах точно нет** → должен честно сказать «в базе ответа нет». Это главный тест — если тут сочиняет, промпт не работает, дальше двигаться нельзя.
