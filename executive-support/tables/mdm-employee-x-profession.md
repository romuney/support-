# dds.mdm_employee_x_profession

## Что описывает

Прямая связь сотрудника с профессией.

**Возможное пересечение с `t-employee-profession` не подтверждено.**
`t-employee-profession` (`dds_dic.employee_profession`) — справочник
профессий, к которому сотрудник приходит только через мост
`dds_dic.employee_specialization`. Эта таблица (`dds.mdm_employee_x_profession`,
другая схема) выглядит как более прямая связь сотрудник↔профессия, но
не проверено, дают ли обе цепочки одинаковый результат для одного и того
же сотрудника. До проверки владельцем — не считать их взаимозаменяемыми
и не выбирать между ними произвольно.

## Ключи для связывания

Ключ связи с `t-emp-structure` не подтверждён явно — по аналогии с
остальными таблицами ожидание `mdm_employee_rk`. Обязательное условие
джойна:

```sql
-- на стороне t-emp-structure
WHERE last_day_flg = 1
```

`last_day_flg = 1` даёт актуальный срез на один день (см. `t-emp-structure`,
раздел «Срез атрибутов») — без него результат размножится на всю историю
сотрудника.

**И со стороны САМОЙ этой таблицы обязателен фильтр версии.** Схема `dds`,
а весь слой DDS версионный (подтверждено владельцем 2026-08-31, см.
[`../process/sql-conventions.md`](../process/sql-conventions.md)):

```sql
-- на стороне dds.mdm_employee_x_profession
WHERE valid_to_dttm = '5999-01-01'
```

Раньше этого условия здесь не было, и запрос по таблице возвращал все
исторические версии связи: связь, снятая год назад, приходила наравне
с действующей. Ошибка тихая — ни падения, ни странного вида у результата.
Точное имя и тип флага удаления (`deleted_flg`) — по инвентарю в каталоге.
