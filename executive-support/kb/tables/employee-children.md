# chrono_peoplehub_masterid.individualchildren_public

## Что описывает

Данные о детях сотрудников.

## Гранулярность строки

Не подтверждено — предположительно один ребёнок = одна строка, на
сотрудника может быть несколько строк. Уточнить у владельца витрины.

## Первичный ключ

Не подтверждено — уточнить у владельца витрины.

## Ключи для связывания

Ключ связи с `t-emp-structure` не подтверждён явно — уточнить у владельца
витрины. Фильтр `birthdate <= fire_dt` (см. ниже) предполагает джойн
с таблицей, где есть `fire_dt` сотрудника (`t-emp-structure` или
`t-legal-position`), но точное поле связи (`mdm_employee_rk` или иное)
не подтверждено.

## Срез атрибутов

**Обязательный фильтр:**

```sql
WHERE isdeleted = FALSE
  AND birthdate <= <fire_dt сотрудника>
```

`birthdate <= fire_dt` — ограничивает выборку детьми, рождёнными до даты
увольнения сотрудника (в источнике условие дано как `birthdate <= s.fire_dt`,
где `s` — алиас соединяемой таблицы сотрудника; какая именно это таблица,
не подтверждено).

## Период и глубина истории

Не заполнено — уточнить у владельца витрины.

## Как обновляется

Не заполнено — уточнить у владельца витрины.

## Категорически нельзя

1. **Забыть `isdeleted = FALSE`** — в выборку попадут удалённые записи.
2. **Выгружать в любом виде, включая агрегаты по конкретному сотруднику** —
   см. «Персональные данные».

## Персональные данные

Данные о детях сотрудников — персональные данные повышенной
чувствительности (несовершеннолетние). **В выгрузки не попадают никогда**,
ни поимённо, ни агрегатом по конкретному сотруднику, даже с суррогатным
ключом. Любой запрос по этой витрине — эскалация руководителю группы
до начала работы, см. `kb/process/routing.md`. Агрегированная статистика
(например, число сотрудников с детьми по подразделению для расчёта льгот)
согласуется отдельно и не является дефолтным сценарием использования.

## Связанные сущности

`t-emp-structure`
