# prod_v_emart.legal_position_d

## Что описывает

Все оформления сотрудников в юрлицах: основные позиции, совместительство, ГПХ,
декретные позиции. Корректный источник для численности по **юридической**
структуре.

## Гранулярность строки

Одна строка = одно оформление сотрудника × один день.

**Один сотрудник может иметь несколько строк на одну дату.** Комбинации:
основное оформление + совместительство в том же юрлице, декретная позиция +
ГПХ, и другие. Это главное отличие от `t-emp-structure`, где строка одна.

## Первичный ключ

`mdm_employee_rk` + `business_dt` + позиция. Уникальности по
`(mdm_employee_rk, business_dt)` **нет**.

## Ключи для связывания

| С чем | По каким полям |
|---|---|
| `t-emp-structure` | `mdm_employee_rk` + `business_dt` |

## Поля

Состав полей, типы и описания — в Data Detective, ключ `dd_urn` в реестре.
Здесь только смысловая разметка, которой в DD нет.

| поле | тип среза | что важно знать |
|---|---|---|
| `mdm_employee_rk` | постоянный | ключ сотрудника, единственный допустимый для джойна |
| `business_dt` | партиция | дата среза |
| `last_day_flg` | флаг | служебный признак строки, не атрибут сотрудника |
| `last_state_flg` | флаг | последнее состояние по сотруднику по его последнему периоду работы. По уволенному — дата увольнения, для текущих — как `last_day_flg`. Для перечисления **всех** увольнений — `company_fire_flg` в `t-emp-structure` |
| `fire_dt` | атрибут | дата увольнения (расторжения договора) по конкретному оформлению. Одна строка — одно оформление, поэтому у человека с несколькими оформлениями своих `fire_dt` несколько. Факт увольнения из компании — `company_fire_flg`, не эта дата |
| `main_legal_position_flg` | на дату | 1 = основная позиция, 0 = совместительство и ГПХ. Без этого фильтра сотрудник считается несколько раз |
| `lvl{N}_legal_unit_nm/_rk`, N = 1..10 | на дату | значимы все уровни, в отличие от управленческой структуры |

Состав полей подтверждается через `get_table_info`, значения перед фильтром —
через `select distinct`.

### Уровни юридической структуры

N = 1..10, **все уровни значимы** — в отличие от управленческой структуры, где
уровни 1 и 2 игнорируются. Поиск начинается с того уровня, который назвал
заказчик. Чаще всего используется `lvl3_legal_unit_nm`.

## Срез атрибутов

На дату строки. Актуальность — `last_day_flg = 1`, не `business_dt = current_date - 1`.

`last_day_flg = 1` существует **только у текущих сотрудников** — это последний
загруженный день витрины. У уволенного строки кончаются раньше (в дату
увольнения), и `last_day_flg = 1` для него не заполнен. Последнее состояние
уволенного — `last_state_flg = 1`.

## Даты увольнения по сотруднику

**Дата расторжения договора** по основной позиции по умолчанию берётся из
`t-emp-structure` — это вопрос про человека, а не про позицию, и там дата
увольнения лежит сразу по основной позиции (`legal_fire_dt`, связывается
с `fire_dt` этой витрины). В `legal_position_d` идём, когда нужны все
оформления / договоры, а не основной — выбор по `rc-structure-choice`, Шаг 0.

Здесь дата расторжения — поле `fire_dt`, по одному на оформление (строка =
одно оформление). Последнее состояние уволенного — `last_state_flg = 1`:

```sql
select lp.mdm_employee_rk, lp.fire_dt
from prod_v_emart.legal_position_d lp
where lp.mdm_employee_rk = 88841   -- мастер ID сотрудника
  and lp.last_state_flg = 1;        -- последнее состояние (у уволенного — дата увольнения)
```

**У повторных наймов дат увольнения несколько.** Человек приходил, уходил,
снова приходил и снова уходил — на каждое оформление своя `fire_dt`. Фильтр
`last_state_flg = 1` оставляет только последнюю дату; нужны все — фильтр
убирается.

**НЕ применять к уволенным `last_day_flg`.** Он отмечает последний загруженный
день витрины и у уволенного не заполнен — запрос по `last_day_flg = 1` вернёт
пусто. Для уволенного нужен `last_state_flg = 1`. У человека с несколькими
оформлениями (совместительство, ГПХ) строк несколько, и в каждой своя `fire_dt`;
основной договор — фильтр `main_legal_position_flg = 1`. Факт увольнения из
компании — `company_fire_flg` в `t-emp-structure`, не дата.

## Как обновляется

Ежедневно, с возможной задержкой.

## Категорически нельзя

1. **Считать `count(*)` там, где нужны люди.** Из-за нескольких оформлений на
   сотрудника `count(*)` даёт число договоров, а не численность. По умолчанию —
   `count(distinct mdm_employee_rk)`.
2. **Забывать `main_legal_position_flg = 1`** при выгрузке «сотрудников
   подразделения», если заказчик не сказал, что нужны все оформления.
3. **Искать в этой витрине поля, которых в ней нет.** `residential_city_nm`,
   `emp_specialization_desc`, `emp_stream_desc` и прочие HR-атрибуты лежат
   в `t-emp-structure` — нужен джойн.
4. **Использовать её для управленческой отчётности**, найма и оттока — для этого
   `t-emp-structure`, см. `rc-structure-choice`.
