# Что берём из базы знаний, а что из Data Detective

У агента поддержки два источника метаданных, и они не пересекаются. Правило
одно: **инвентарь — из DD, смысл — из базы знаний.**

| Что | Источник | Почему так |
|---|---|---|
| Имена полей, типы данных, описания полей, DDL, партиции, размер таблицы | Data Detective, онлайн | Меняется без нашего участия. Владельцы правят описания у себя, и это сразу видно агенту |
| Гранулярность строки, первичный ключ, правила джойна, «категорически нельзя», тип среза поля, формулы метрик, рецепты | База знаний `kb/` | DD этого не знает и знать не будет: это договорённости команды, а не свойство схемы |

## Почему инвентарь не дублируется в git

Список полей, скопированный в статью, устаревает в день добавления новой колонки
и после этого врёт молча: агент отвечает уверенно и неправильно. Ровно тот
случай, который в [`../../CLAUDE.md`](../../CLAUDE.md) назван опаснее отсутствия
ответа.

Из этого следует и рабочий вывод для команды: если описания поля не хватает,
**правильное действие — попросить владельца дописать его в DD**, а не заводить
описание у себя. Описание в DD увидят все потребители таблицы, описание
в нашей статье — только мы.

## Что такое «тип среза» и почему он остаётся в git

Единственная характеристика поля, которую мы всё же держим у себя. DD отвечает
на вопрос «что это за поле», но не на вопрос «можно ли по нему фильтровать
за период».

| тип среза | что значит |
|---|---|
| постоянный | не меняется за всё время существования записи |
| партиция | дата строки |
| на дату | историческое значение атрибута в этот день |
| событие | 1 только в день события, за период суммируется |
| флаг | служебный признак строки, не атрибут сотрудника |
| атрибут | значение-константа в строке |

Путаница между «на дату» и «событие» — источник самых частых неверных цифр:
отток, посчитанный по `company_fire_dt` вместо `business_dt`, выглядит
правдоподобно и при этом неверен.

## Реестр: колонка `dd_urn`

В [`../index.md`](../index.md) у каждой строки есть `dd_urn` — ключ объекта в DD.
Три возможных состояния строки:

| путь | dd_urn | что это значит |
|---|---|---|
| есть | есть | Основной случай. Смысл из статьи, поля из DD |
| нет (`—`) | есть | Статья не написана, но объект зарегистрирован. Агент отвечает по метаданным DD и прямо пишет, что смысловой статьи нет |
| есть | нет (`—`) | Сущности в DD нет: рецепт, метрика, регламент |

Второе состояние — способ покрыть таблицу до того, как у кого-то нашлось время
написать статью. Одна строка в реестре дешевле статьи и уже даёт агенту поля
и описания.

## Правило при конфликте

Статья и DD расходятся — **прав DD** во всём, что касается состава полей, типов
и описаний. Прав git — во всём, что касается правил расчёта.

Заметил расхождение — сообщает о нём в ответе, а не выбирает молча. Это то же
поведение, что и для случая «реестр ссылается на несуществующий файл».

## Ограничение на объём

Ультраширокие витрины содержат сотни колонок. Полный список полей в контекст
не запрашивается: сначала фильтр по подстроке (параметр `search` в DD), и только
если фильтр не подошёл — список целиком. Если ответ обрезан по лимиту, агент
обязан сказать, сколько полей скрыто, а не выдавать часть за полный состав.

Техническая сторона — эндпоинты, URN, ключи связей — описана вне репозитория,
в контексте флоу бота: DD не относится к знанию HR-домена.
