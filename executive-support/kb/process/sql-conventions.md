# Правила написания SQL по HR-витринам

Соглашения, обязательные для любого запроса к HR-витринам: в выгрузке, в отчёте,
в разовой проверке. Смысловые правила по конкретным данным — в статьях
`kb/tables/` и `kb/recipes/`.

## Запрет: без проверки метаданных SQL не выдаётся

Запрос нельзя отдавать, пока не выполнено всё три:

1. Для **каждой** таблицы из `FROM` / `JOIN` / CTE вызван `get_table_info`.
2. Все используемые поля дословно есть в ответе `get_table_info`.
3. Для **каждого значения**, попадающего в `WHERE`, выполнен
   `select distinct <поле>` — подтверждено существование и точное написание.

```sql
select distinct <поле>
from <таблица>
where last_day_flg = 1
order by 1;
```

Угадывать имена полей, номера уровней иерархии и значения справочников нельзя.
«Скорее всего поле называется так» — источник самых дорогих ошибок: запрос
выполняется, цифра получается, и она неверная.

## Джойны только по ключам

Соединение — только по `*_rk`. По текстовым `*_nm` — никогда.

```sql
-- ✅ ПРАВИЛЬНО
join cte2 on cte1.mdm_employee_rk = cte2.mdm_employee_rk

-- ❌ НЕПРАВИЛЬНО
join cte2 on cte1.unit_name = cte2.unit_name
```

Названия дублируются, меняются при реорганизации, отличаются регистром
и пробелами. Ключи есть для всех уровней структуры и для сотрудника.

## Оконные функции и границы периода

`WHERE` применяется **до** оконных функций. Если фильтр обрезает границу
периода, `LAG` и `LEAD` вернут `NULL`, и метрика посчитается неверно.

```sql
-- ❌ НЕПРАВИЛЬНО: фильтр до lag(), декабрь отрезан
select
    month_dt
    , lag(hc_cnt) over (partition by unit_rk order by month_dt) as prev_month_hc
from monthly_headcount
where month_dt >= date '2026-01-01'

-- ✅ ПРАВИЛЬНО: оконная функция в CTE, фильтр во внешнем запросе
with raw as (
    select
        month_dt
        , lag(hc_cnt) over (partition by unit_rk order by month_dt) as prev_month_hc
    from monthly_headcount  -- все месяцы
)
select * from raw
where month_dt >= date '2026-01-01';  -- фильтр ПОСЛЕ lag()
```

Проверка: нужен ли предыдущий период для расчёта — расширить диапазон на ±1
период до применения `WHERE`. Это критично для текучести, MoM и retention.

## Язык и оформление

| Где | Язык |
|---|---|
| Идентификаторы, алиасы, имена CTE и таблиц | только латиница, `snake_case` |
| Строковые литералы в кавычках | кириллица разрешена |
| Комментарии `--` и `/* */` | кириллица обязательна |

Каждое поле и выражение в `SELECT` сопровождается коротким русским комментарием
справа. Для флагов — что означает `1`. Для вычислений — бизнес-смысл.

`AS` без обработки поля не ставится: имя совпадает с именем в источнике.
`AS` допустим при вычислении, агрегации, `CASE`, касте, конфликте имён
при джойне или по явной просьбе заказчика.

## Разбиение на временные таблицы

Три и более логических блока — вместо одного запроса с множеством CTE делаются
отдельные параграфы с временными таблицами.

| Шаг | Действие |
|---|---|
| 1 | Заголовок параграфа — на русском, отражает суть: `-- Численность на конец 2025` |
| 2 | Имя временной таблицы — на английском: `hc_end_2025` |
| 3 | В начале каждого параграфа `drop table if exists` |
| 4 | `create table <имя> as select ...` — без указания схемы, платформа подставит сама |
| 5 | Финальный параграф — только `SELECT` с джойнами, без CTE |

Все промежуточные параграфы должны быть запущены до финального и не удаляются —
это аудит-трейл и возможность отладки. Метрики в финальном `SELECT`
оборачиваются в `coalesce(..., 0)`, чтобы после джойна не осталось `NULL`.

Пример последовательности: численность на конец прошлого года → численность
сейчас → найм за период → отток за период → финальный `SELECT` с `full join`
по ключам уровней.

## Работа с параграфами

- Каждая проверка `select distinct` — отдельный новый параграф в конце ноутбука,
  запускается сразу.
- Итоговый SQL — отдельный последний параграф, обязательно запускается.
  Падает — исправить и перезапустить; нерабочий SQL не отдаётся.
- Проверки и финальный запрос не объединяются.
- `get_table_info` вызывается инструментом, **не** в параграфе.

## Экономия контекста при чтении результата

Вывод финальной выгрузки не читается: он занимает контекст без пользы.
Не читать `output`, если запрос — финальная выгрузка без агрегатов и `LIMIT`,
если в `SELECT` больше пяти колонок без `GROUP BY`, или если заказчик
не просил показать данные.

Вместо чтения — сообщить статус запуска. Для проверки добавляется отдельный
параграф-агрегат **до** финальной выгрузки, и читается только его вывод:

```sql
select
    count(*) as total_rows
    , count(*) filter (where <поле> is null) as null_cnt
    , count(distinct <ключ>) as unique_cnt
from (/* основной запрос */) t;
```

Читать вывод можно, если заказчик прямо попросил показать данные, если стоит
`LIMIT 10-100` для примера, или если это проверка качества.

## Порядок работы над запросом

1. `get_table_info` по каждой таблице — инструментом.
2. Новый параграф: `select distinct` по каждому полю для `WHERE`, запуск.
3. При неоднозначности — **один** уточняющий вопрос и остановка.
4. Секция «CHECK: проверка метаданных и значений» в ответе.
5. Разбиение на временные таблицы, если блоков три и больше.
6. Финальный параграф с русскими комментариями, запуск, проверка
   работоспособности.
7. Две-три строки пояснения и краткое резюме результата.

## Персональные данные

ФИО, телефоны, почты, даты рождения, зарплаты, табельные номера, реквизиты
документов не выгружаются никогда — независимо от доступов заказчика. Наружу
идут суррогатные ключи и роли. Запрос ПДн — эскалация руководителю группы,
см. [`routing.md`](routing.md) и [`export-playbook.md`](export-playbook.md).
