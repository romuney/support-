### Разведка DD — импортировать `DD Recon.json` и запустить руками

Пять ручных запросов больше не нужны: они собраны в воркфлоу
`bot/DD Recon.json` (сборщик `build_dd_recon.py`, Code-ноды покрыты
`test_recon.mjs`). Импортировать **новым** воркфлоу — он ничего не вызывает
по id, — запустить вручную и прочитать вывод трёх нод:

| нода | что в ней |
|---|---|
| `Shape recon` | где у отчёта лежит владелец, рядом напечатан эталон из фидбека |
| `Build bridge` | готовые строки `\| ключ ссылки \| dd_urn \|` и покрытие: сколько из 10 ключей эталона нашлось |
| `Search probe` | форма тела и ответа `POST /search/query` |

Мост строится **со стороны витрин** (ключ связи `notes` — «отчёты, читающие
таблицу»), а не поиском по названиям: форма `/related/{key}` подтверждена
живым запросом, тело `SearchRequest` не подтверждено ничем. Проба поиска стоит
в цепочке ради ответа сервера — 400 прогон не сломает, а текст ошибки обычно
называет ожидаемые поля.

`entityFields` не используется: с 2026-08-24 он не отдаёт ни `summary`,
ни `attributes` — ни у отчётов, ни у колонок.

Вопрос, на который отвечает разведка: **где у отчёта лежит владелец.**

И сразу сверка с эталоном — фидбек аналитика даёт готовые пары, по трём
достаточно:

| отчёт | кого тегает аналитик |
|---|---|
| [CrossData] Лидерский снепшот | i.rastokin |
| Активность в GitLab | Aliya Kolomeets |
| Амбассадорство сотрудников | s.kopytov |

URN добываются `POST /search/query` по названию. Совпало на трёх — владелец
берётся из DD и в git не дублируется. Не совпало — значит в DD технический
владелец ноутбука, а тегать надо другого человека, и тогда владелец остаётся
в git как исключение.

## 3. С чего продолжать работу — реестр отчётов (P1)

Половина канала: 11 обращений из 49 решаются одной строкой «отчёт называется
так-то, владелец такой-то», ещё 13 — тем, что дежурный звал эксперта по теме.

**Решение принято: владельцы тянутся из DD, в git — только мост.**

Новая таблица «Отчёты Proteus» в `kb/index.md`, две колонки:

```
| ключ ссылки | dd_urn |
```

Ни названия, ни владельца — они приезжают из карточки DD в момент ответа.
Мост не протухает: ключ ссылки и URN не меняются, меняется то, что лежит
по URN. Колонка `владелец` допустима только как исключение — когда в DD
владельца нет или он не тот, кого тегают.

Отдельного файла не заводим: `kb/index.md` уже читается нодой `Get a file`,
`Plan` уже разбирает из него таблицы, и прецедент есть — «Самостоятельные
выгрузки» тоже матчатся кодом, а не моделью. Одна правка в довесок:
**исключить новую таблицу из проекции реестра для роутера** — 30 строк
«ключ → URN» ему не нужны, матч делает код. Заодно из проекции уедут
и «Самостоятельные выгрузки», за которые сейчас платим токенами.

## 5. Правило, которое стоило четырёх находок

Три отказа из четырёх — это **ручная правка в интерфейсе n8n**,
разошедшаяся со сборщиком. Ни один не виден по виду флоу, и ни один
не ловится чтением кода: диск был прав во всех четырёх случаях.

**При симптоме «бот отвечает странно» — первым делом экспортировать
воркфлоу из n8n и сравнить с диском**, а не перечитывать сборщик.

И второе: `prompt_version` — хеш только промптов. Отказ во флоу он не видит
в принципе, отсечку в логе даёт только при правке промптов. Сейчас он
сменился с `a04eed84` на **`3813aceb`** — по этому полю отделяются ответы
до и после починки.
