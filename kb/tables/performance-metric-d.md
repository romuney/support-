# prod_v_sse_crossdata.performance_metric_d

## Что описывает

Продолжительность активной работы сотрудника по дням. Отвечает на вопрос
«сколько человек фактически работал», а не «был ли он оформлен» и не «стоял
ли рабочий день в табеле».

Это **вычисленная метрика**, а не факт из одной системы: она собирается
из очищенных и объединённых сигналов восьми источников.

| Источник | Что даёт |
|---|---|
| DLP (SearchInform) | активность на рабочем ПК |
| VPN (Cisco) | подключение к корпоративной сети |
| RDP / AD | сессии удалённого доступа, блокировки и разблокировки экрана |
| VDI (VMware) | работа через виртуальный рабочий стол |
| Коммуникации (Zoom, Slack, Talk) | звонки и сообщения |
| Системы разработки (Jira, GitLab, Wiki) | коммиты, правки, комментарии |
| Почта | отправка писем |
| СКУД | вход и выход по офисным пропускам |

Отсюда главное свойство: **отсутствие активности в витрине не означает, что
человек не работал.** Оно означает, что ни один из восьми источников его
в этот день не увидел — у сотрудника без корпоративного ПК, без VPN и без
пропуска картина будет пустой при полном рабочем дне.

## Гранулярность строки

Одна строка = один сотрудник × один день.

## Ключи для связывания

| С чем | По каким полям |
|---|---|
| `t-emp-structure` | `mdm_employee_rk` + сопоставление дат (ниже) |

```sql
ON  mdm_employee_rk = mdm_employee_rk
AND calendar_dt = CAST(work_exit_date_formatted AS DATE)
```

**Условие записано так, как его дал владелец, и НЕ подтверждено инвентарём.**
Из формулировки не видно, какое из двух полей на какой стороне джойна стоит,
а `work_exit_date_formatted` — текстовое (отсюда `CAST`). Перед первым
использованием состав полей обеих витрин надо посмотреть в Data Detective
и убедиться, что поля именно там, где ожидаются. Догадка здесь дороже
проверки: неверная сторона даёт не ошибку, а молча пустой или размноженный
результат.

Связка по дате обязательна в любом случае: без неё строки размножатся
на каждый день истории сотрудника.

## Поля

Состав полей, типы и описания — в Data Detective, ключ `dd_urn` в реестре.

| поле | что важно знать |
|---|---|
| `mdm_employee_rk` | ключ сотрудника |
| `calendar_dt` | день, за который посчитана метрика |
| `duration_hour` | **продолжительность активной работы в часах** — то самое поле, если спрашивают «сколько часов» |

## Категорически нельзя

1. **Читать пустой день как «не работал».** См. «Что описывает»: это значит
   «ни один источник не увидел активности».
2. **Джойнить без условия по дате** — размножение строк.
3. **Складывать `duration_hour` с табельными часами `t-attendance`.** Табель
   отвечает на вопрос «какой это был день по кадровому учёту», эта витрина —
   «сколько было активности». Разные величины, суммировать и сравнивать
   напрямую их нельзя.
4. **Выдавать за учёт рабочего времени.** Это аналитическая метрика,
   а не табель и не основание для кадровых решений.

## Персональные данные

Метрика построена на данных о поведении конкретного человека — это
чувствительная категория даже там, где признак в каталоге не проставлен.

Типовой сценарий — агрегаты по подразделению или динамика без привязки
к людям. Разрез по конкретным сотрудникам согласуется с руководителем группы
до начала работы: не отказ, но и не дефолтный сценарий. Общие правила —
[`../process/export-playbook.md`](../process/export-playbook.md).
