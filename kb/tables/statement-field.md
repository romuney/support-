# prod_v_sdp_edms_statement.statement_field

## Что описывает

Содержимое заявлений сотрудников: не сам факт заявления, а **что именно
в нём написано**. Одна строка — одно заполненное поле одного заявления.

Смысл витрины в связке трёх полей: `field_nm` — наименование поля
(«Дата рождения», «Адрес места жительства по паспорту»), `field_type_nm` —
тип данных в исходной системе (обычно `String` или `Date`), `field_txt` —
фактическое значение, то, что человек написал в заявлении.

## Гранулярность строки

Одна строка = одно поле одного заявления. У одного `statement_id` строк
столько, сколько полей заполнено.

**Гранулярность не гарантирует уникальности.** Внутри одного заявления
встречаются ДУБЛИ по `field_nm` с разными значениями — подтверждено данными:
у одного `statement_id` дважды стоит «Адрес места жительства по паспорту»
с разными адресами. См. «Категорически нельзя».

## Первичный ключ

`id` — UUID **строки**, а не заявления. Это первая ошибка, которую здесь
делают: соединять по `id` нельзя, он ничего не адресует за пределами этой
витрины.

## Ключи для связывания

| С чем | По каким полям |
|---|---|
| основная таблица заявлений | `statement_id` |

```sql
ON statement.statement_id = statement_field.statement_id
```

Самой таблицы заявлений в этом реестре нет — зарегистрирована только витрина
её полей. Понадобится сама шапка заявления (кто, когда, какого типа) —
это отдельная сущность, и её надо завести.

`contract` — бизнес-идентификатор заявления, годится для связи с внешними
системами. `__contract_version__` — его версия.

## Поля

Состав полей, типы и описания — в Data Detective, ключ `dd_urn` в реестре.
Здесь только смысловая разметка, которой в DD нет.

| поле | что важно знать |
|---|---|
| `statement_id` | ключ заявления. **Единственное**, по чему соединяют |
| `id` | UUID строки витрины, не идентификатор заявления |
| `field_nm` | наименование поля. Бывают лишние пробелы и разный регистр — фильтровать через `TRIM(LOWER(field_nm))` |
| `field_txt` | значение поля. **Всегда текст**, даже даты и числа |
| `field_type_nm` | тип в исходной системе: `String`, `Date`. Не тип колонки в витрине — она текстовая |
| `contract` | бизнес-идентификатор заявления для связи с внешними системами |
| `processed_dttm` | когда запись попала на этот слой. По нему разбираются дубли |

Технические поля с двойным подчёркиванием, о которых надо знать две вещи:
`__partition__` и `__offset__` **всегда равны −1** — данные переложены,
а не читаются из живого топика Kafka, и как курсор они не годятся;
`__timestamp__` дублирует `processed_dttm` и самостоятельной информации
не несёт. `__src_processed_dttm__` — время обработки в источнике,
`__instance_id__` и `__topic__` — атрибуты Kafka.

## Как достать конкретное поле

Одно поле одного заявления:

```sql
WHERE statement_id = :statement_id
  AND TRIM(LOWER(field_nm)) = 'дата рождения'
```

Несколько полей одного заявления в ОДНУ строку — разворот через `MAX(CASE …)`
с группировкой по заявлению:

```sql
SELECT statement_id
     , MAX(CASE WHEN TRIM(LOWER(field_nm)) = 'дата рождения'
                THEN field_txt END) AS birth_dt_txt
     , MAX(CASE WHEN TRIM(LOWER(field_nm)) = 'адрес места жительства по паспорту'
                THEN field_txt END) AS address_txt
FROM prod_v_sdp_edms_statement.statement_field
GROUP BY statement_id
```

## Даты здесь — текст

`field_txt` текстовое поле целиком, включая даты. По данным формат
`DD.MM.YYYY`, но **варианты возможны**, и на это надо закладываться:

```sql
TO_DATE(field_txt, 'DD.MM.YYYY')
```

Сравнивать даты строками (`field_txt >= '01.01.2025'`) нельзя: в формате
`DD.MM.YYYY` лексикографический порядок не совпадает с хронологическим,
запрос выполнится и вернёт неверный отбор молча.

## Категорически нельзя

1. **Соединять по `id`.** Это UUID строки витрины. Ключ заявления —
   `statement_id`.
2. **Брать значение поля без дедупликации.** Внутри одного заявления
   встречаются два значения одного `field_nm`. Берём последнее по
   `processed_dttm`:

   ```sql
   ROW_NUMBER() OVER (PARTITION BY statement_id, TRIM(LOWER(field_nm))
                      ORDER BY processed_dttm DESC) = 1
   ```

   Без этого агрегат задвоится, а точечный отбор вернёт случайное из двух —
   и по виду результата это не заметно.
3. **Фильтровать `field_nm` дословно.** Лишние пробелы и разный регистр —
   только `TRIM(LOWER(field_nm))`.
4. **Сравнивать `field_txt` как дату или число** без явного приведения.
5. **Использовать `__partition__` / `__offset__` как курсор** — они всегда −1.

## Персональные данные

Витрина по построению состоит из персональных данных: паспортные сведения,
адреса, даты рождения — всё это лежит в `field_txt` открытым текстом.

Запрета на выгрузку нет — есть требование согласовать доступ, и по этой
витрине оно относится к содержимому целиком, а не к отдельным полям.
В составе файла такие поля помечаются 🔒, см.
[`../process/export-playbook.md`](../process/export-playbook.md).
Сами значения в переписке не пишутся: сказать, что поле есть и требует
согласования, можно; привести адрес или дату рождения в треде — нет.
