# Карточка отчёта в Data Detective: как достать и как следить за актуальностью

Выжимка для соседнего репозитория, где нужно собрать карточки отчётов из папок
**Офис Исполнительного Директора / CrossData / Executive Reports** и держать их
свежими. Всё ниже — из этого проекта: подтверждённое живыми прогонами помечено
датой, выведенное из спецификации (`openapi` в корне) помечено отдельно,
непроверенное названо непроверенным.

**Дата проверки — это срок годности, а не история.** 2026-08-06 карточка
колонки отдавала `summary` и `attributes` по `entityFields`; 2026-08-24 тот же
запрос к тому же объекту отдал только идентификаторы. Сервис меняется
независимо от нашего кода: когда живой прогон расходится с записанным здесь,
верить надо прогону.

Base URL: `https://dd.t-tech.team/api/v3`
Авторизация: credential n8n «Spirit (Devplatform) Service Account API»
(`devplatformApi` / `spiritToken`). В этом проекте id живёт в одном месте —
`bot/build_dd_flow.py`, `DP_CRED`; вторая копия однажды разъехалась молча
и уронила бы разом каталог и чтение статей.

На каждой HTTP-ноде обязательны три настройки, и каждая закрывает свой тихий
отказ:

```
followRedirects: false   // иначе страница логина приезжает как HTTP 200 с HTML
fullResponse:    true    // без statusCode отказ неотличим от пустого ответа
neverError:      true    // 404 по одному объекту не роняет прогон по остальным
```

---

## 1. Что такое отчёт в DD

URN устроен как `urn:dd:<systemType>:<systemName>:<type>:<id>`:

| объект | systemType | systemName | type | пример |
|---|---|---|---|---|
| дашборд Proteus | `reports` | `reports` | `report` | `urn:dd:reports:reports:report:1728` |
| ноутбук Helicopter | `reports` | `helicopter` | `note` | — |
| витрина Greenplum | `tables` | `greenplum` | `table` | `urn:dd:tables:greenplum:table:emart.mdm_employee_structure_d` |

URN всегда кодируется `encodeURIComponent`, точки не трогаются.

Подтверждённые примеры отчётов (лежат в реестре `executive-support/kb/index.md`):
`report:1728` — «HR Executive — Детальные списки», `report:1845` — «HR Executive
Report».

**Ключ ссылки Proteus и id в URN не связаны никак.** У «Активности в GitLab»
URN `report:aktivnost-v-gitlab`, а ссылка `/dashboard/35005/`; у отчёта 1728
наоборот — URN числовой, ссылка `/dashboard/hr-executive-detail-employee`.
Вывести одно из другого нечем — отсюда и нужда в мосте, см. § 7.

## 2. Главное: `entityFields` мёртв, карточка собирается из суб-ресурсов

`GET /entity/{urn}?entityFields=displayName&entityFields=summary&entityFields=attributes`
возвращает **только** `id / urn / system / type / fqn`. Подтверждено дважды:
2026-08-13 на отчёте, 2026-08-24 на колонке — то есть это поведение эндпоинта,
а не особенность типа сущности. То же и в ответе `/related/{key}`: `entityFields`
там игнорируется, приходят только идентификаторы.

Проектировать на `entityFields` нельзя. Всё содержательное берётся отдельными
запросами к суб-ресурсам.

## 3. Пять запросов, из которых собирается карточка отчёта

| запрос | что даёт | статус |
|---|---|---|
| `GET /entity/{urn}/markdown` | смысл отчёта: блоки `summary`, `how_to_read`, `additional_info` | живой прогон 2026-08-13 |
| `GET /entity/{urn}/attribute` | владелец, канал поддержки, команда | живой прогон 2026-08-27 |
| `GET /entity/{urn}/link` | ключ ссылки Proteus (`{"reports": {"url": "…/superset/dashboard/hr-executive-detail-employee"}}`) | живой прогон 2026-08-27 |
| `GET /entity/{urn}/related/source_tables` | витрины, на которых построен отчёт | живой прогон 2026-08-27: три витрины на `report:1728` |
| `GET /entity/{urn}/summary` | короткая подпись | по спецификации; на отчёте не проверялось (на таблице работает) |

Дополнительно, по спецификации и не проверено на отчётах: `/tag`, `/code`,
`/table`, `/notification`, `/history` (§ 8), `/related` (§ 6),
`/metrics-group` (кто пользуется отчётом).

Рабочая реализация — узлы `dd_report_markdown`, `dd_report_attrs`,
`dd_report_links`, `dd_report_sources` и шейпер `Shape report meta`
в `bot/build_dd_flow.py`. Оттуда же берутся помощники распаковки.

### Порядок запросов

В n8n они выстроены **цепочкой**, а не веером: у ноды-шейпера уже есть
входящее соединение, и параллельные ветви запустили бы его дважды на одну
порцию данных. В обычном коде это ограничение не действует — четыре запроса
идут параллельно.

## 4. Три ловушки распаковки

Каждая из трёх однажды дала **пустой результат, неотличимый от «данных нет»**.

**1. Значение атрибута лежит в `.data`, сам атрибут — обёртка `{type, data}`.**
`type` бывает `text`, `enum`, `text-list`, `enum-list`, `number`, `boolean`,
`datetime`; у списочных `data` — массив. Без распаковки значение уезжает
строкой `[object Object]`.

**2. В ответе `/related/{key}` элемент массива — это СВЯЗЬ, сущность вложена
в `entity`:**

```json
{ "totalCount": 267,
  "data": [ { "relationId": "…",
              "entity": { "id": "…", "urn": "…", "system": "…",
                          "type": "COLUMN", "fqn": "emart.table.column" } } ] }
```

Поиск `fqn` на верхнем уровне не находит ничего, и инвентарь получается пустым.

**3. `totalCount` сверяется с числом полученных элементов.** Расходятся —
список неполный, и об этом надо сказать вслух, а не молча отдать первые N.

Портируемые помощники (`bot/build_dd_flow.py`, `COMMON_JS`):

```js
function unwrap(body) {                       // массив под одной из известных обёрток
  if (Array.isArray(body)) return body;
  if (!body || typeof body !== 'object') return [];
  for (const k of ['items', 'data', 'content', 'entities', 'result', 'results']) {
    if (Array.isArray(body[k])) return body[k];
  }
  for (const v of Object.values(body)) {
    if (Array.isArray(v) && v.length && typeof v[0] === 'object') return v;
  }
  return [];
}

function nodesOf(body) {                      // связь → сама сущность
  return unwrap(body).map((x) =>
    x && typeof x === 'object' && x.entity && typeof x.entity === 'object' ? x.entity : x);
}

function attrData(attrs, key) {               // { type, data } → значение
  const a = attrs && typeof attrs === 'object' ? attrs[key] : undefined;
  if (a === undefined || a === null) return '';
  const d = a && typeof a === 'object' && 'data' in a ? a.data : a;
  if (d === null || d === undefined) return '';
  if (Array.isArray(d)) return d.join(', ');
  if (typeof d === 'object') return '';
  return String(d);
}

function httpFail(res, label) {               // отказ, названный своей причиной
  const code = res && res.statusCode;
  if (code === undefined || code < 400) return null;
  if (code === 401) return `${label}: HTTP 401 — истёк Service Account`;
  if (code === 404) return `${label}: HTTP 404 — неверный URN либо нет такой связи`;
  return `${label}: HTTP ${code}`;
}
```

`/markdown`, `/attribute` и `/link` возвращают **словарь «ключ → payload»**, а не
массив: `{ summary: {data: "…"}, how_to_read: {data: "…"} }`,
`{ report_developer: {type: "text", data: "…"} }`, `{ reports: {url: "…"} }`.

## 5. Что именно доставать из карточки

### Атрибуты: подтверждённые ключи и угаданные

Подтверждены живым прогоном 2026-08-27 на `report:1728`:

| ключ | что это |
|---|---|
| `report_developer` | владелец отчёта |
| `developers_team`, `data_team` | команда |
| `support_channel` | канал поддержки — «куда писать по отчёту» |

Ключи `period` и `status` шейпер печатает, но они **угаданы** и живым ответом
не подтверждены: может не быть вовсе.

**Урок, который дороже самих ключей.** Разведка искала владельца регулярным
выражением по угаданному списку слов, ни одно из четырёх реальных имён под него
не подошло — и она отрапортовала «владельца в каталоге не видно», имея его
на руках. Поэтому правило: **печатать список ВСЕХ ключей, пришедших в ответе**,
а не только те, что ищутся. Значения остальных можно не тянуть — важно, чтобы
их существование было видно.

### Markdown-блоки

Подтверждены `summary`, `how_to_read`, `additional_info`. Печатать надо **любой
пришедший ключ**, а не три по имени: новый блок, заведённый владельцем позже,
не должен требовать правки кода.

Пустой ответ — это пробел на стороне владельца отчёта («блоки не заполнены»),
и он отличается от отказа ручки. Слитые в один диагноз, они отправляют чинить
не то.

### Витрины-источники

`/related/source_tables` на `report:1728` вернул `usr_cross_data.functional_role_d_br`,
`emart.mdm_employee_structure_d`, `hrmart.summary_evaluation`.

**Обратного пути нет.** У витрины двенадцать ключей связей — `cuts, notes, terms,
columns, samples, consumers, guillotine, notes_sens, jira_issues, data_products,
data_processes, physical_tables` — и **ни один не отдаёт `REPORT`** (`notes` —
ноутбуки Helicopter, `consumers` — сервисы). От витрины к дашборду в каталоге
пути нет ни при каком лимите; попытка построить мост с этой стороны собрала ноль
пар из 1782 и была удалена.

### Что из этого класть в git, а что брать онлайн

Граница этого проекта, и она же должна действовать в соседнем репозитории:

| | откуда |
|---|---|
| название, владелец, канал поддержки, витрины-источники, состав полей | **каталог, онлайн** — меняется без нашего ведома, копия протухнет молча |
| смысл, правила расчёта, гранулярность, запреты, что с чем джойнить | **git** — этого в каталоге нет и не будет |
| **мост «ключ ссылки Proteus → dd_urn»** | git — он единственный не протухает: меняется то, что лежит по URN, а не сама пара |

## 6. Поиск отчёта: `POST /search/query`

Тело (схема подтверждена спецификацией, поле `text` — живым прогоном 2026-08-27):

```json
{ "text": "Активность в GitLab",
  "limit": 20, "offset": 0,
  "filters": { "type": ["REPORT"],
               "systemType": ["reports"],
               "systemName": ["reports"] } }
```

| поле | |
|---|---|
| `text` | **именно `text`.** Перебором это стоило трёх проб |
| `limit` / `offset` | по умолчанию 20 / 0, пагинация работает: `offset: 100` отдал вторую страницу целиком из новых |
| `filters` | словарь «ключ → **массив** строк», ключи свободные (`additionalProperties` в спеке); проверены `type`, `systemType`, `systemName` |
| `sessionId` / `requestId` | uuid, не обязательны |

Ответ — массив `SearchCard`: `urn`, `fqn`, `system`, `type` (обязательные),
`displayName`, `summary`.

**Что работает:** поиск по названию. `{"text": "Активность в GitLab"}` первым же
результатом вернул нужный URN.

**Что НЕ работает:** поиск по ключу ссылки (`{"text": "hr-executive-detail-employee"}`
→ пусто) и по числовому ключу (`{"text": "35005"}` → чужая таблица).

**Поля `searchText` в этой ручке не существует вовсе** — оно принадлежит
`POST /search/facets/{facetKey}/filters`.

### Правило проб против этого сервера

На неизвестное поле в теле сервер отвечает **200 и молчит**, отдавая выдачу
по умолчанию. Значит проба, рассчитанная на громкую ошибку («400 назовёт
ожидаемые поля»), бесполезна: разница между «поле сработало» и «поле
проигнорировано» видна **только сравнением двух ответов** — с полем и без.
Это надо закладывать в каждую пробу сразу.

### Ложное совпадение лечится сверкой, а не настройкой поиска

Поиск только предлагает кандидатов, решает `/link`: совпал ключ ссылки — тот
самый отчёт, не совпал — не он. Похожее название так не пройдёт. Не нашлось
ничего — сказать «отчёта по этой ссылке в каталоге нет», а не предлагать
ближайший: неверное название отчёта хуже отсутствующего.

## 7. Папка: что известно, чего нет и как это выяснить

**Ни одного живого прогона по папкам в этом проекте не было.** Понятия «папка»
в спецификации нет вовсе: слова `folder` в `openapi` не встречается. Писать код
перечисления «на веру» нельзя — код, который не работает и выглядит рабочим,
это ровно тот класс отказа, от которого защищена вся остальная конструкция.

Что API даёт на самом деле — два пути, вверх и вниз.

### Вверх: `GET /tree/{urn}/parents?depth=10`

Есть в спецификации: «возвращает список родителей, отсортированный от ближнего
к дальнему», ответ — массив `Parent { urn, id }`, `depth` от 1 до 10
(по умолчанию 2). Это и есть иерархия, в которой живут «Офис Исполнительного
Директора → CrossData → Executive Reports». Живым запросом не проверялось.

### Вниз: `/related` у сущности-папки

`GET /entity/{urn}/related` отдаёт **словарь ключей связей** с описанием
каждого: `relation {type, direction}`, `entity {type, system}`, `limit`.
Ключи не угадываются — сначала разведка, потом рабочий запрос
`GET /entity/{urn}/related/{key}?limit=…&afterUrn=…` (курсорная пагинация).

Готового ключа не нашлось — `POST /entity/{urn}/related-by-query`, тело
`RelationsConditional`: обязательные `type` (например `CONTAINS`) и `direction`
(`src_dest` / `dest_src` / `bidirectional`), необязательный фильтр
`entity {type, system}`.

### Процедура разведки — четыре шага

Шаг 0 обязателен: **взять один отчёт, про который точно известно, что он лежит
в нужной папке.** Без этого разведка ответит на другой вопрос.

1. `GET /tree/{report_urn}/parents?depth=10` — увидеть цепочку родителей и
   забрать URN папки «Executive Reports» и её родителей. Пусто или 404 — путь
   вверх не работает, идти к шагу 4.
2. `GET /entity/{folder_urn}/related` — посмотреть, какие ключи есть у папки
   и какой из них имеет `entity.type = REPORT`.
3. `GET /entity/{folder_urn}/related/{key}?limit=500` — дети. Сверить
   `totalCount` с числом пришедших; больше лимита — пагинация через `afterUrn`.
   Ключа с `REPORT` нет — `POST /entity/{folder_urn}/related-by-query`
   с `{"type": "CONTAINS", "direction": "src_dest", "entity": {"type": "REPORT"}}`.
4. Заодно: `POST /search/facets/{facetKey}/filters` с телом
   `{"searchText": "", "limit": 100}`. `SearchFilters` — свободный словарь,
   поэтому у поиска **может** быть фасет папки, и тогда перечисление сводится
   к одному фильтру в `/search/query`. `facetKey` придётся угадывать
   (`folder`, `parent`, `path`, `space`, `group`); несуществующий фасет отвечает
   404 — здесь ошибка как раз громкая, в отличие от `/search/query`.

### Запасной путь, который работает наверняка

Если ни один шаг не дал перечисления: **список названий отчётов даёт человек**,
дальше по запросу на отчёт — поиск по названию (§ 6), сверка кандидата
через `/link`, подтверждение папки через `/tree/parents`. Два-три запроса
на отчёт, для трёх десятков отчётов это работа на один прогон.

### Чего делать не надо

**Не перечислять каталог целиком** с фильтром `systemType: reports`. Технически
это работает — фильтр отдал 100 дашбордов из 100, `offset` отдавал новые
страницы, — но в DD лежат отчёты **всех команд компании**, это десятки тысяч,
разреза по домену у нас нет, и первая тысяча будет произвольным срезом, в
котором наших почти наверняка нет. Такой сбор выходит одновременно огромным
и пустым. Эта фаза была написана и удалена — записано, чтобы никто не собрал
её заново.

## 8. Сбор всех карточек: стоимость и батчи

Одна карточка — 4–6 запросов. Тридцать отчётов — примерно 150 запросов, то есть
разовый прогон, а не то, что делается на каждое обращение.

Батч-**чтение** в API ровно одно: `POST /entity/batch/related`, тело
`BatchRelatedEntitiesByKey { urns[], key, limit, entityFields, relationFields,
search }` — одним запросом собирает связи (например `source_tables`) сразу
по списку отчётов. Но `entityFields` в related-ответах игнорируется, поэтому
описания, атрибуты и markdown всё равно тянутся поштучно.

`POST /api/v3/batch` — **не для чтения**: это транзакционные мутации
(`put-entity`, `put-attribute`, `put-markdown`, `post-relation`, …).

## 9. Актуальность: `GET /entity/{urn}/history`

Ручка есть в спецификации, живым прогоном не проверялась — проверить первым
делом. Параметры: `limit` (обязательный, по умолчанию 100, максимум 10000),
`afterDate` / `beforeDate` / `aroundDate` в формате date-time.

Ответ — массив `EntityHistory`:

| поле | |
|---|---|
| `operation` | `IU` (вставка/обновление) или `D` (удаление) |
| `type` | что менялось: `ENTITY`, `ATTRIBUTE`, `MARKDOWN`, `SUMMARY`, `LINKS`, `TAG`, `CODE`, `TABLE`, `NOTIFICATION` |
| `blockKey` | ключ конкретного блока или атрибута |
| `oldData` / `newData` | было / стало |
| `updatedAt` | время |
| `updatedBy` | `Account`: `user`, `service`, `kafka-topic`, `kafka-topic-datasource` |

Это ровно то, что нужно для слежения: **один запрос на отчёт вместо
перечитывания всей карточки**, и сразу видно, что именно поменялось —
переписал ли владелец `how_to_read` или сменился `report_developer`.

Схема слежения:

- на каждый отчёт хранить `dd_urn`, `checked_at`, `last_change_at` и хеш
  снапшота карточки;
- крон-прогон: `history?afterDate={last_change_at}&limit=100` по каждому URN;
  пришли события — перетянуть только те суб-ресурсы, чей `type`/`blockKey`
  задет, и обновить `last_change_at`;
- **три исхода разводятся, а не сливаются в один**: «изменений не было»,
  «ручка отказала» (401/404/5xx) и «отчёта больше нет». Слитые вместе, они
  дают самый дорогой вид молчания — устаревшая карточка выглядит свежей.
  Тот же класс ошибки, из-за которого «каталог не ответил» и «объект
  не доехал до вызова» пришлось разводить отдельными флагами;
- **хеш снапшота — страховка на случай, если `/history` окажется неполной**
  или её форма разойдётся со спецификацией. Пока живого прогона нет, считать
  надо оба сигнала и сравнивать: расхождение и есть ответ, можно ли доверять
  истории;
- рядом с каждым записанным фактом — **дата проверки**. Не для истории:
  это срок годности. `entityFields` работал 2026-08-06 и не работал
  2026-08-24, и единственное, что позволило это заметить, — записанная дата.

## 10. Чек-лист первого прогона в соседнем репозитории

Каждый пункт — с ожидаемым ответом; расхождение важнее совпадения.

1. `GET /entity/{urn}/markdown` на `urn:dd:reports:reports:report:1728` →
   словарь с `summary` / `how_to_read` / `additional_info`. Пришли только
   идентификаторы — сломался ещё один эндпоинт, дальше не строить.
2. `GET /entity/{urn}/attribute` → среди ключей `report_developer`
   и `support_channel`. Напечатать **все** ключи ответа, а не искать четыре
   известных.
3. `GET /entity/{urn}/link` → `{"reports": {"url": "…"}}`, ключ ссылки Proteus.
4. `POST /search/query` с `{"text": "<название отчёта>"}` → искомый URN
   в первых результатах. Проверить парой «с фильтрами / без»: сервер молчит
   о неизвестных полях, и отличить работающий фильтр можно только сравнением.
5. `GET /tree/{urn}/parents?depth=10` → цепочка родителей до «Офис
   Исполнительного Директора». **Это главный неизвестный шаг**, с него
   начинается вся задача про папки.
6. `GET /entity/{urn}/history?limit=20` → массив событий с `updatedAt`
   и `blockKey`. Форма разошлась со спецификацией — слежение строить
   на хешах снапшотов.
