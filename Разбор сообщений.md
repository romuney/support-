ТЗ для аналитика — заказчику не отправлять
ТАБЛИЦА: prod_v_emart.mdm_employee_structure_d — основная витрина сотрудников (одна строка = сотрудник × день).

ГРАНУЛЯРНОСТЬ: одна строка = один сотрудник × один календарный день (mdm_employee_rk + business_dt). Для актуального среза — last_day_flg = 1.

ФИЛЬТРЫ: last_day_flg = 1 (последний загруженный день; актуальный срез). Если заказчик выберет другой вариант — заменить на диапазон по business_dt. Для ответа на первый вопрос — уточнить гранулярность.

ПОЛЯ:

сотрудник → mdm_employee_rk
управленческий юнит → lvl{N}_mapped_management_unit_nm (N = 3..13; где N — нужный уровень, уточнить, если у заказчика есть конкретика; по умолчанию — все уровни, либо уточнить)
функциональный юнит → поле из prod_v_emart.functional_role_d. Для этого нужен джойн. Если не известно, какие уровни (lvl{N}_functional_unit_nm) — уточнить у заказчика.
ДОСТУП: метаданные по functional_role_d не получены, доступ проверить перед выгрузкой.

ДЖОЙНЫ: prod_v_emart.mdm_employee_structure_d e → prod_v_emart.functional_role_d fr по e.mdm_employee_rk = fr.mdm_employee_rk и e.business_dt = fr.business_dt. Флаг last_day_flg ставить у обеих таблиц.

ЧТО ПРОВЕРИТЬ:

Контрольная сумма: численность по выгрузке должна сходиться с дашбордом (в разрезе управленческих/функциональных юнитов).
Проверка гранулярности: GROUP BY mdm_employee_rk HAVING COUNT(*) > 1 для t-emp-structure должен вернуть 0 строк (если берём last_day_flg = 1). Для functional_role_d — ожидаемо > 0 (у сотрудника несколько ролей), поэтому после джойна строк на сотрудника может быть несколько — предупредить заказчика.
Если данные нужны не на актуальный срез, а за период — уточнить дату фильтрации (business_dt), нужны ли уволенные, срез атрибутов на дату события или текущий.
