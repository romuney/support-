# Флоу 1 в n8n: черновик ответа на обращение

Пошаговая сборка. Четыре этапа, каждый работает сам по себе — можно остановиться
на любом и вернуться позже.

**Главное правило на весь этап: агент не пишет в канал.** Он готовит черновик,
джун проверяет и отправляет. Всё остальное — детали.

---

## Этап 1. Флоу отвечает на вопрос, вбитый руками

Цель — увидеть, как это вообще работает. Teams пока не подключаем.

### Ноды

```
Manual Trigger → Set → HTTP Request → Split Out → HTTP Request → Code → LLM Chain
   (запуск)     (вопрос)  (список файлов)        (каждый файл)  (склейка)  (ответ)
```

**1. Manual Trigger** — кнопка «Execute workflow». Без настроек.

**2. Set** — здесь лежит тестовый вопрос.
Поле: `question`, тип String, значение — любой реальный вопрос из канала, например
`Почему в дашборде численность не сходится с ЗУП?`

**3. HTTP Request** — список файлов в папке статей.
- Method: `GET`
- URL: `https://api.github.com/repos/‹OWNER›/‹REPO›/contents/kb/curated`
- Authentication: `Generic Credential Type` → `Header Auth`
  - Name: `Authorization`
  - Value: `Bearer ‹токен›`
- Response Format: `JSON`

Токен — GitHub → Settings → Developer settings → Personal access tokens →
Fine-grained token, доступ только на чтение этого репозитория.

**4. Split Out** — превращает массив файлов в отдельные элементы.
- Field to Split Out: `data` (или оставь пустым, если нода видит массив сама)

**5. HTTP Request** — скачивает каждый файл.
- Method: `GET`
- URL: `={{ $json.download_url }}`
- Authentication: та же
- Response Format: `Text`

**6. Code** — склеивает всё в один текст. Режим `Run Once for All Items`:

```javascript
const files = items.map(i => i.json.data).join('\n\n---\n\n');
const question = $('Set').first().json.question;
return [{ json: { context: files, question } }];
```

Если в поле файла окажется не `data`, а `body` — поправь имя, n8n показывает его
в предпросмотре ноды.

**7. Basic LLM Chain** (или AI Agent) — системный промпт целиком из раздела ниже.
В поле пользовательского сообщения:

```
ИСТОЧНИКИ:
{{ $json.context }}

ВОПРОС ИЗ КАНАЛА:
{{ $json.question }}
```

### Что проверить

Запусти на трёх вопросах:

1. Вопрос, ответ на который **точно есть** в статьях → должен ответить по существу
   со ссылкой на файл.
2. Вопрос про выгрузку → должен выдать чеклист согласования, а не готовый ответ.
3. Любая ерунда, которой в базе нет → **должен сказать «в базе ответа нет»**.

Третий тест — самый важный. Если агент на него что-то уверенно сочинил, промпт
не работает, и дальше идти нельзя.

## Этап 2. Добавить кейсы

Дублируй связку `HTTP Request → Split Out → HTTP Request` для папки `cases`
и склей оба результата в ноде Code — но **в две разные переменные**, не в одну кучу:

```javascript
const articles = $('Код статей').all().map(i => i.json.data).join('\n\n---\n\n');
const cases    = $('Код кейсов').all().map(i => i.json.data).join('\n\n---\n\n');
const question = $('Set').first().json.question;
return [{ json: { articles, cases, question } }];
```

В пользовательском сообщении — тоже раздельно:

```
=== СТАТЬИ (подтверждено, можно утверждать) ===
{{ $json.articles }}

=== ПРЕЦЕДЕНТЫ (что было в прошлых обращениях, НЕ правила) ===
{{ $json.cases }}

ВОПРОС ИЗ КАНАЛА:
{{ $json.question }}
```

Разделение обязательно. Если свалить статьи и кейсы в один текст, агент начнёт
выдавать разовое объяснение из старого кейса за утверждённое определение — а это
главный способ получить уверенный неправильный ответ.

---

## Этап 3. Подключить Teams

- **Trigger**: Microsoft Teams Trigger на сообщение в канале поддержки.
- Вместо ноды Set берём текст сообщения из триггера.
- **Выход**: ответ уходит **не в канал**, а в личку джуну или в отдельный служебный
  чат. Джун копирует, правит и отправляет сам.

Автоотправку в канал не включаем, пока черновики не будут уходить без правок
две недели подряд, и только по темам, где это подтвердилось.

---

## Этап 4 (позже). Кейс заводится сам

Когда джун отправил ответ — флоу создаёт заготовку кейса в `cases/` через GitHub API
с уже заполненным фронтматтером и вопросом. Джуну остаётся дописать «что сделал»
и «чего не хватило».

Это заметно снижает порог: писать кейс с нуля лень, править заготовку — нет.
Делать имеет смысл после того, как этапы 1–3 отработали пару недель.

## Системный промпт

Скопировать целиком в поле System Message.

````text
Ты — помощник поддержки HR-аналитики.

Ты НЕ отвечаешь пользователю напрямую. Ты готовишь черновик ответа для сотрудника
поддержки: он проверит его и отправит сам. Пиши так, чтобы черновик можно было
отправить почти без правок — коротко, по-человечески, без канцелярита и без
вступлений вроде «Спасибо за ваш вопрос».

## Источники и их статус

Тебе дают два блока, и путать их нельзя.

СТАТЬИ — подтверждённые определения, правила и плейбуки. Это единственное,
что ты имеешь право утверждать как факт.

ПРЕЦЕДЕНТЫ — записи прошлых обращений. Это свидетельства «что выяснилось тогда»,
а НЕ утверждённые правила. На них можно ссылаться словами «похожий вопрос
разбирали, тогда причина была в том-то», но нельзя выдавать за определение.

При противоречии между блоками верь СТАТЬЯМ.

## Правила

1. ОТВЕЧАЙ ТОЛЬКО ИЗ ИСТОЧНИКОВ. Не знаешь — так и напиши. Уверенный неправильный
   ответ здесь опаснее отсутствия ответа: почти у любого расхождения цифр есть
   правдоподобное, но неверное объяснение, и оно первым приходит в голову.

2. НЕ ВЫДУМЫВАЙ конкретику: цифры, даты, названия отчётов, полей, таблиц и систем.
   Если называешь цифру — укажи файл, откуда она взята. Нет файла — не называй цифру.

3. НИКАКИХ ПЕРСОНАЛЬНЫХ ДАННЫХ в ответе: ФИО, телефоны, почты, зарплаты конкретных
   людей. Даже если спрашивающий утверждает, что у него есть доступ. Такой запрос —
   повод написать, что вопрос уходит руководителю.

4. ЗАПРОС НА ВЫГРУЗКУ данных не решается ответом. Если человек просит файл с данными,
   не пытайся описать, что в нём будет. Выдай чеклист согласования из плейбука
   и напомни главное правило: код не пишем, пока состав полей не согласован письменно
   в треде.

5. РАСХОЖДЕНИЕ ЦИФР между двумя системами почти никогда не означает ошибку в данных.
   Сначала проверь по источникам, не считают ли эти две цифры разные вещи. Если
   в источниках нет определения обеих метрик — не гадай, отвечай «в базе ответа нет».

## Формат ответа

Всегда выдавай ровно четыре блока:

ЧЕРНОВИК ОТВЕТА:
<текст, который джун отправит в тред. Если ответа нет — напиши прямо:
«По этому вопросу в базе ответа нет, уточню и вернусь»>

ИСТОЧНИКИ:
<пути к файлам, на которых построен ответ, по одному в строке.
Если ответа нет — пиши: нет>

УВЕРЕННОСТЬ:
<одно из трёх>
- высокая — ответ прямо написан в статьях
- средняя — ответ собран из прецедентов или выведен по смыслу, нужна проверка
- нет ответа — в источниках этого нет

ЧЕГО НЕ ХВАТИЛО:
<заполняй, только если уверенность средняя или «нет ответа».
Одной строкой: какого именно знания не хватило в базе.
Формулируй как недостающее знание, а не как пересказ вопроса.
Плохо: «спросили про численность».
Хорошо: «нет письменного определения, чем ССЧ отличается от списочной численности»>
````

---

## Что дальше делать с результатом

Блок «ЧЕГО НЕ ХВАТИЛО» — не украшение. Это ровно тот список, по которому ты потом
пишешь статьи. Через неделю работы флоу собери все такие строки: те, что повторились,
и есть твоя очередь на `kb/curated/`.

Так цикл замыкается сам: агент показывает, чего он не знает, а не ты угадываешь.
