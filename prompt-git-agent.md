# Промпт для агента: провести правки базы знаний в `master`

Задание для агента, который выполняет git-операции в репозитории
`executive-support`. Скопировать блок «ЗАДАНИЕ» целиком и передать агенту.

Контекст, который стоит знать перед запуском:

- **Цель — не «закоммитить», а довести правки до `master`.** Бот в n8n читает
  файлы через GitLab-ноды, в которых ветка **не указана**, то есть читается
  ветка по умолчанию — `master` (`origin/HEAD → origin/master`). Пока правки
  лежат в feature-ветке, агент поддержки продолжает читать старые статьи,
  и любой тест проверяет не то, что починили.
- **`master` защищён**: только feature-ветка и MR. MR создаётся вручную по
  ссылке, которую GitLab печатает после `git push`.
- Remote — **HTTPS** (`https://gitlab.tcsbank.ru/cross/executive-support.git`),
  не SSH. Это важно: в песочнице tclaude закрыт `~/.ssh`, и push по SSH упал бы
  на `Host key verification failed`, а по HTTPS может пройти. Отдельно: `git push`
  требует подтверждения пользователя на каждый вызов.

## ЗАДАНИЕ

```
Ты работаешь с репозиторием базы знаний HR-аналитики.

РЕПОЗИТОРИЙ
Путь:     /Users/r.kazantsev/Documents/Проекты Nessy/Support/executive-support
GitLab:   cross / executive-support  (https://gitlab.tcsbank.ru/cross/executive-support)
Remote:   HTTPS, не SSH
Ветка:    feature/kb-update-employee-profession (текущая)
Базовая:  master — ЗАЩИЩЕНА, напрямую в неё не пишем

ВАЖНО ПРО ВЕТКИ: в репозитории накопилось несколько параллельных feature-веток
с разным содержимым kb/index.md (feature/dd-metadata-integration,
kb/add-metrics-and-recipes, kb/split-by-entity-type,
feature/channel-import-jul-aug-2026). Не переключайся на них и не трогай —
задание строго про feature/kb-update-employee-profession. Переключение на
master голым git checkout/git pull без MR — то, из-за чего в этом репозитории
уже дважды терялись правки: файл выглядел «сброшенным», хотя на деле просто
показывал другую ветку.

ЗАЧЕМ ЭТО ДЕЛАЕТСЯ
Воркфлоу n8n читает статьи через GitLab-ноды, в которых ветка не указана, —
значит читается master. Правки, лежащие в feature-ветке, для бота не существуют.
Цель задания — довести их до master через MR.

ЧТО НУЖНО СДЕЛАТЬ

1. git checkout feature/kb-update-employee-profession, затем проверь
   состояние: git status, git log --oneline origin/master..HEAD.
   Ожидается: рабочее дерево чистое (коммитить нечего), один коммит в ветке,
   которого нет в master — «kb/index.md: добавлены r-hr-executive-report
   и t-employee-profession + таблица самостоятельных выгрузок», один
   изменённый файл kb/index.md. Если состояние другое — не действуй по
   инструкции слепо, сначала скажи, что расходится.

2. Прогони валидатор из корня репозитория:
      python3 validate_kb.py
   Он должен закончиться «OK: N сущностей, M доменов». Если есть ОШИБКА —
   останавливайся и покажи вывод: реестр разошёлся со статьями, коммит
   (если он ещё не сделан) делать нельзя.

3. Коммитить не нужно — правка уже в единственном коммите на ветке.
   Если увидишь незакоммиченные изменения kb/index.md — это отдельная
   ситуация, не по этому шаблону: останавливайся и опиши, что видишь,
   не додумывай коммит-сообщение сам.

4. Запушь ветку (идемпотентно — если уже запушена, git ответит
   «Everything up-to-date», это нормальный исход, а не ошибка):
      git push -u origin feature/kb-update-employee-profession
   Это действие требует подтверждения пользователя — дождись его, не обходи.
   Если push зависает или падает на авторизации (credential manager просит
   интерактивный вход) — не жди и не повторяй вслепую, сразу скажи об этом
   пользователю: значит эту команду должен выполнить он сам в своём терминале,
   где авторизация уже проходила.

5. Если ветка уже была запушена (см. п.4) — MR по ней мог быть уже открыт.
   Спроси пользователя или проверь на странице репозитория в GitLab, прежде
   чем присылать «ссылку на создание MR» — если MR уже есть, вместо этого
   пришли ссылку НА НЕГО.
   Иначе — из вывода push возьми ссылку на создание MR и отдай её пользователю
   вместе с готовым заголовком и описанием MR (на русском).
   MR сам не создавай и не пытайся мержить: master защищён, вливает человек.
   Заголовок и описание должны объяснять ЗАЧЕМ правка, а не перечислять диффы:

   Добавлены две сущности в реестр базы знаний и разметка для рекомендации
   самостоятельной выгрузки. t-employee-profession — справочник профессий
   (джойн через мост employee_specialization, с фильтром актуальной версии).
   r-hr-executive-report — отчёт с аналитикой динамики HR-метрик (численность,
   найм, отток, переводы), смысл которого живёт в DD, а не в статье. Новая
   таблица «Самостоятельные выгрузки» размечает отчёты-трансформеры, которые
   бот предлагает коллеге вместо (или до) обычного согласования выгрузки.

   В описание включи, что в MR уходят и более ранние коммиты ветки —
   статья про employee-profession, правка routing.md про продукты клиентов —
   они тоже ещё не в master (или уже там, если предыдущий MR уже влит —
   проверь по git log origin/master перед тем, как писать описание).

ЧЕГО НЕ ДЕЛАТЬ
— Не пушить в master и не создавать ветки от master.
— Никакого git push --force, git reset --hard, git rebase, git commit --amend
  по уже запушенным коммитам.
— Не коммитить стор dp CLI, если он появится в статусе: config.json,
  cache_version.json, plugins/, access_token.json, lock. Это артефакт запуска dp
  из каталога, а не часть репозитория.
— Не править содержимое статей. Задание только про git-операции: файлы уже
  подготовлены и проверены.
— Не менять .gitignore, .gitlab-ci.yml, policy.yml.
— Не выполнять git config --global: в песочнице ~/.gitconfig закрыт на запись,
  настройки задаются на уровне репозитория.

ЧТО ОТДАТЬ В ОТВЕТЕ
1. Вывод валидатора (одной строкой).
2. Хеш и сообщение созданного коммита.
3. Результат push: прошёл или нет, при ошибке — точный текст.
4. Ссылку на создание MR + заголовок и описание, готовые к вставке.
5. Отдельно: что осталось сделать человеку.

Если на любом шаге факты расходятся с этой инструкцией — останавливайся
и говори, что не сошлось. Молча подстраиваться нельзя: тихая неверная работа
здесь дороже остановки.
```

## После того как MR влит

Проверка привязана к тому, что реально ушло в MR — при следующей задаче
переписать под неё, а не оставлять эту.

Для MR `feature/kb-update-employee-profession` — два независимых вопроса
в `Adapter Chat`:

```
какая профессия у сотрудника, через что джойнить
```

Ожидается упоминание моста `employee_specialization` и фильтра
`valid_to_dttm = '5999-01-01' and deleted_flg = 0` — если агент предлагает
джойнить `employee_profession` напрямую к витрине сотрудников, MR не влит
или реестр не обновился.

```
Cross Data | Выгрузка данных
...Напиши свой вопрос: нужна выгрузка ФИО и логинов моей команды
```

Ожидается, что черновик первым делом предложит попробовать самостоятельную
выгрузку через отчёт «HR Executive — Детальные списки», а не сразу чеклист
согласования. Пусто — либо MR не влит, либо `Support Bot Core.json`
не переимпортирован в n8n после последней правки `prompts/author.md`
(это отдельный шаг, к git не относится).

Более ранняя проверка (структура vs юридическая позиция, декрет) относится
к уже влитой задаче про `rc-structure-choice` и оставлена как пример
формата, не как актуальный чек-лист:

```
сколько сотрудников в декрете
```

Ожидается `mdm_employee_structure_d`, `active_type_nm = 'Декрет'`.
