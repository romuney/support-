# support_request — описание полей

Справка по колонкам вью `dl.usr_cross_data.support_request`
(`Support/telemetry/support_request.sql`). Одна строка = одно обращение
(тред с событием `request_created`).

## Шапка обращения

| Поле | Логика |
|---|---|
| `request_id` | = `thread_id`, ключ склейки — `root_id` треда Mattermost |
| `created_at` | `MIN(event_ts)` события `request_created`. Обращение — только тред с этим типом события; реплики и посты чужих тредов сюда не попадают (их число видно в отдельном диагностическом запросе как `threads_without_root`) |
| `created_date` | `created_at`, приведённое к дате — для группировки по дням |
| `kind` | Нормализованный тип обращения (`export`, `report_question`, `unknown` и т.д.), определён по префиксу `Cross Data \| <Тема>` в форме intake-воркфлоу. Порядок сопоставления префиксов — от длинных к коротким, иначе «Вопрос команде DWH HR» матчился бы как более общая тема |
| `topic` | Сырой текст темы, как он реально пришёл в сообщении. Совпадает с `kind` почти всегда, отличается только когда `kind = 'unknown'` — тогда `topic` хранит нераспознанный префикс, чтобы форму можно было расширить новой темой, а не гадать по логам |
| `ours` | `true` — обращение к нашей команде, `false` — к чужой (например, DWH HR). Проставляется классификатором темы в момент `request_created`; чужие обращения в наши метрики **не входят** (фильтр `ours` — ответственность потребителя запроса), но и не выбрасываются из лога — задним числом добрать нельзя |
| `posted_by` | `actor` корневого поста. Это **технический аккаунт intake-воркфлоу**, а не человек с вопросом — настоящий автор есть только в шапке формы («от пользователя @X»), и нормализатор её не парсит. Named gap, не поле |
| `permalink` | Ссылка на пост в Mattermost, собрана из `post.id` |
| `text_len` | Длина исходного текста сообщения в символах |

## Работа дежурного

| Поле | Логика |
|---|---|
| `state` | `'closed'`, если есть `closed_at`; иначе `'in_progress'`, если есть `taken_at`; иначе `'new'`. Порядок проверки важен — переоткрытое обращение (см. `reopened`) `closed_at` теряет и падает обратно в `in_progress` |
| `reopened` | `true`, если последним по времени событием из пары «поставили/сняли закрывающую реакцию» было снятие. При совпадении миллисекунды тай-брейк считает обращение **открытым** — незакрытое видно дежурному, ложнозакрытое — нет, это дешевле по цене ошибки |
| `taken_at` | **Первое** добавление реакции `:loading:` за всю историю треда. Снятие `:loading:` это поле не сбрасывает вообще — дежурный снимает его, ставя закрывающую реакцию, а не «расхотел брать в работу» |
| `taken_by` | Кто поставил эту первую `:loading:` |
| `closed_at` | Время **последнего** добавления закрывающей реакции (`:done_checkmark:` или `:im_red_cross:`), при условии что это последнее событие в паре добавление/снятие. Если последним было снятие — `NULL` |
| `closed_by` | Кто поставил закрывающую реакцию |
| `resolved` | `true` — закрыто `:done_checkmark:` (решено), `false` — `:im_red_cross:` (закрыто нерешённым). `NULL`, если не закрыто |

## Метрики времени

| Поле | Логика |
|---|---|
| `reaction_time_sec` | `taken_at − created_at`. Самая быстрая на изменения и понятная людям метрика |
| `lead_time_sec` | `closed_at − created_at`. Что чувствует заказчик — **включает** ожидание в очереди |
| `cycle_time_sec` | `task_finished_at − task_created_at` (из T-Tracker). Чем управляет команда — очередь **не** включает. Расхождение с `lead_time_sec` — длина очереди, обычно это и есть предмет разговора |
| `first_reply_sec` | `first_reply_at − created_at`. Прокси-сигнал на случай, когда дежурный ответил в тред, но реакцию `:loading:` не поставил |

## Связка с трекером

| Поле | Логика |
|---|---|
| `task_key`, `task_url` | Ключ/ссылка задачи, разобранные из ответа бота в треде (`task_linked`). Ключ принимается **только** из ссылки бота по шаблону — регулярка по любому похожему тексту («HR-2» в вопросе) дала бы связь с несуществующей задачей |
| `tracker` | `tracker` / `jira` / `unknown` — T-Tracker vs jira3 vs не определился по URL |
| `task_linked_at` | Время события `task_linked` |
| `task_status` | Последний известный статус задачи — **снапшот**, не история: у T-Tracker нет `/history`/`/changelog`, коллектор видит только то, что застал на опросе (раз в 15 мин) |
| `task_is_final` | Финальность по `finish_at` трекера (`aux.type = finish`), а не по названию статуса — их 76 штук на инстанс |
| `task_created_at`, `task_finished_at` | Точные времена от трекера — единственное, что T-Tracker отдаёт надёжно независимо от частоты опроса |
| `task_error` | Ошибка опроса (нет доступа к спейсу, задача удалена). Явно называется, чтобы не выглядеть как «статус не менялся» |

## Ответ бота

| Поле | Логика |
|---|---|
| `bot_answered_at` | `MAX(event_ts)` события `bot_answered`. Пишется узлом «To Ingest» в адаптере КАНАЛА (в ядре его нет намеренно: сабворкфлоу возвращает данные последнего узла). Ответы из лички сюда не попадают — у `Adapter DM` узла Ingest нет |
| `confidence_claimed` | Уверенность, которую заявила модель, до всяких понижений |
| `confidence_key` | Уверенность после понижения **кодом** по фактам (нет материалов → «нет ответа»; вопрос про отчёт без статьи и без подбора роутером → «нет ответа»/«средняя»; `router_error`/`parse_error` → «средняя» и т.д.) |
| `confidence_downgraded` | `true`, если `confidence_claimed` заполнено И отличается от `confidence_key`. Частота понижений — метрика качества промпта автора |
| `domains` | Домены реестра, которые искал роутер бота — **факт работы бота**, а не оценка обращения. Пустой список значит «роутер домен не определил», это тоже сигнал, заглушкой не подменяется |
| `articles_read` | Сколько статей базы знаний было прочитано |
| `dd_count` | Сколько объектов метаданных (таблиц/отчётов) запрошено у Data Detective |
| `parse_error` | Заполнено, если разбор ответа модели сломался (пустая строка превращена в `NULL`) |
| `router_error` | Ошибка роутера (аналогично, `NULLIF` пустой строки) |
| `prompt_version` | Версия промпта, которым бот отвечал — для калибровки по времени |

## Оценка кнопкой и текстовый фидбэк

| Поле | Логика |
|---|---|
| `draft_useful` | Оценка **черновика джуном** (кнопка стоит под черновиком в `~stonis_hakcs_2`), не оценка автора вопроса — это другая, пока не разведённая метрика (`answer_helpful`), потому что `channel_id` в payload вебхука кнопок не пишется |
| `feedback_at` | Время последней оценки. Повторное нажатие **переписывает** оценку того же человека, а не добавляет вторую |
| `feedback_voters` | Число уникальных людей, поставивших оценку (кнопки нажимают единицы — знаменатель для честной метрики среди тех, кто оценил) |
| `feedback_text` | Развёрнутый текстовый комментарий из диалога, открытого кнопкой |

## Переписка и здоровье данных

| Поле | Логика |
|---|---|
| `human_replies` | Число ответов реального человека в треде |
| `bot_replies` | Число ответов бота в треде |
| `first_reply_at` | Первый `human_replied`, где `actor ≠ posted_by` — то есть реальный ответ дежурного, а не автора-технического аккаунта |
| `unknown_reactions` | Число реакций `reaction_added`/`reaction_removed` вне словаря `EMOJI` — про доверие к данным, не про сами метрики |
| `reaction_types_inferred` | `true`, если тип события реакции был домыслен (снятие пришло как добавление, потому что Mattermost не отдал имя события). Если так — «взято в работу», которое сняли, останется в метриках навсегда, и это стоит учитывать при интерпретации |

## Важно при использовании

- Обращения `ours = false` (чужая команда) нужно исключать фильтром на стороне
  запроса — витрина их не убирает.
- `bot_answered_at` / `confidence_*` / `domains` заполнены только по ответам
  В КАНАЛЕ: узел «To Ingest» стоит в адаптере канала, а у `Adapter DM` его нет
  вовсе, поэтому по личке эти колонки `NULL`.
- Синтаксис самой вью живым прогоном в Trino не подтверждён.
